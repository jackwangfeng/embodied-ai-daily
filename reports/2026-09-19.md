## 🇨🇳 国内

### ★ TOP 1（深度）· WM-Craftnet —— 在手内转笔式旋转，权重放了，**不用真手也能把整条链路跑通**

**出处**：<https://github.com/sharpa-robotics/WM-Craftnet>（14 ★，2026-09-10 建仓，09-18 仍在推）
**相关**：[项目主页](https://wmcraftnet.github.io) ｜ [arXiv:2609.07002](https://arxiv.org/abs/2609.07002) ｜
[HF 权重 SharpaIT/WM-Craftnet](https://huggingface.co/SharpaIT/WM-Craftnet) ｜ [Sharpa Wave 手](https://www.sharpa.com/pages/wave)

#### 是什么

上海 Sharpa Robotics 的 CoRL 2026 论文代码。做的是**灵巧手在手内旋转（in-hand rotation）**——
把一个物体捏在手里，绕指定轴连续转，不掉。

它的方法叫 **World Synesthesia Model（WSM，世界通感模型）**。名字花哨，做的事很朴素：
把四路信号——本体感觉（关节角）、**腕部深度相机（很脏）**、指尖触觉接触、上一步动作——
压进一个 Dreamer 式的循环状态空间模型里，**用干净深度图和奖励做监督**，
然后把这个状态 detach 掉直接喂给 actor-critic 策略。

关键在于**它不做想象式 rollout**。Dreamer 系一般要在隐空间里滚未来若干步再规划，
这里把 WSM 纯当表征用：策略只看当前隐状态。这让它在部署时和普通策略一样便宜。

**最值得看的一个结果**是深度重建：真机腕部相机拍到的深度是残缺、带噪、手指互相遮挡的，
WSM 的隐状态能重建出一张干净得多的深度图，还保住了手-物几何关系。项目页有并排对比动图。

仓库里给了什么（09-18 复核的目录）：

| 目录 | 内容 |
|---|---|
| `isaacgymenvs/` | 任务与训练配置（`WMCraftnetRotation.yaml` / `WMCraftnetPPO.yaml`） |
| `rl_games/` | 改过的 RL 框架 |
| `scripts/` | 5 个入口脚本：`test_wm_craftnet.sh`、`train_wm_craftnet_{x,y,z}.sh`、`test_wm_craftnet_y.sh` |
| `example_ckpt/` | 放权重和配套 yaml 的位置（权重本体在 HF） |
| `deploy/` | 真机侧，含 Sharpa Wave SDK 安装脚本 |
| `wsm/` | 世界模型本体 |

三组物体集：`set_z`（9 个杂形状，绕 z 轴，**也是 WSM 预训练那组**）、
`set_x4`（4 个接触受限形状，绕 x 轴）、`set_y`（9 个细长/工具类，绕 y 轴）。

#### 为什么现在值得做

1. **它把「预训练一个物理先验、换一组物体接着用」这件事变成了可复现的脚本。**
   README 明说：在 9 个 z 轴物体上训出来的 WSM 可以拿去初始化别的物体集的学习。
   这正是个人做得动的事——**你不需要从零训 x 轴那组，你从它的 z 轴 WSM 起步**。
2. **放了权重，而且明确写了权重和头的配置必须对上。** 发布的 checkpoint 用的是
   「本体感觉 + 深度」两个头的旧配置，训练默认却开了 6 个头（加了物体位姿、触觉接触、
   critic value、BPS 形状）。README 把关掉多余头的命令原样贴出来了。
   **这种「我知道你会踩这个坑」的写法在开源具身项目里不常见。**
3. **真机那一半你做不了，但那一半不是门槛。** Sharpa Wave 是 22 自由度五指手，
   人手尺寸，SDK 要单独下 deb 包。这条路对个人是关的。
   **但仿真那一半是完整的**——任务、奖励、物体、训练、评测、权重全给了。
4. 灵巧手在手内旋转是少数**评价指标天然客观**的任务：转了多少弧度、掉没掉、
   换个没见过的形状还转不转得动。不需要人工打分，不需要真机。

#### 个人怎么分步切进去

**前置**：一张 NVIDIA 卡（本机 RTX A4000 16G 够用，但见下面「坑」）、Linux、约 40 GB 磁盘。

**第 0 步 · 装环境（约 2–3 小时，大半在等下载）**

```bash
conda create -n wm-craftnet python=3.8 && conda activate wm-craftnet
conda install pytorch=2.1.0 torchvision torchaudio pytorch-cuda=11.8 -c pytorch -c nvidia
conda install -c fvcore -c iopath -c conda-forge fvcore iopath
conda install pytorch3d -c pytorch3d
pip install hydra-core gym numpy==1.22.2 tensorboardX tensorboard wandb \
            scipy imageio imageio-ffmpeg h5py trimesh rtree pillow ninja
```

Isaac Gym Preview 4 要去 <https://developer.nvidia.com/isaac-gym> 接受许可后手动下，
解压后 `cd isaacgym/python && pip install -e . --no-deps`。

**第 1 步 · 先把发布的权重跑起来（半小时）**

```bash
hf download SharpaIT/WM-Craftnet wm_craftnet_set_z.pth --local-dir example_ckpt
HEADLESS=true CHECKPOINT=example_ckpt/wm_craftnet_set_z.pth bash scripts/test_wm_craftnet.sh
```

**没显示器一定要 `HEADLESS=true`**，脚本默认开 viewer。这一步跑通，
说明 Isaac Gym、PyTorch3D、物体网格加载全对了——**这是整个流程风险最高的一关，先过它**。

**第 2 步 · 训一组小的，确认能收敛（一晚上）**

```bash
NUM_ENVS=128 MINIBATCH_SIZE=512 bash scripts/train_wm_craftnet_z.sh \
  task.env.cameraPolicy.worldModel.wm_pose_pred=False \
  task.env.cameraPolicy.worldModel.wm_tac_pred=False \
  task.env.cameraPolicy.worldModel.wm_value_pred=False \
  task.env.cameraPolicy.worldModel.wm_obj_pred=False
```

后面那四行是**把头关到和发布权重一致**。仓库默认给的是 `NUM_ENVS=256 / MINIBATCH=1024`
（按 32 GiB 主机内存调的），16G 显存 + 深度相机渲染下建议从 128 起步，
显存有富余再往上加。输出在 `runs/`。

**第 3 步 · 做一件原作者没做的事（1–3 天，这才是产出）**

三个方向，都不需要真机、都有客观数字：

- **跨物体集迁移的量化曲线。** README 声称 z 轴 WSM 能初始化别的物体集，
  但**没给「省了多少步」的曲线**。你只要跑两条 `set_y`：一条从零、一条从 z 轴 WSM 起步，
  把 reward-vs-iteration 画出来，就是一张原论文没有的图。**这是最省事、最容易被合的一条。**
- **六个头各值多少钱。** 默认开 6 个预测头，发布权重只用 2 个。中间那四个的消融
  （位姿 / 触觉 / value / BPS 形状，各关一个）仓库里没做。一次一个变量，四次训练。
- **扔没见过的形状进去。** `set_z` 是 9 个物体，你自己塞一个 STL（trimesh 已经是依赖），
  测零样本成功率。**这是最接近"泛化到底行不行"的诚实测法。**

**成本**：0 元（全是本机算力）。时间：装环境半天，第 1 步半小时，
第 2 步一晚，第 3 步 1–3 天。

#### 坑

1. **Isaac Gym Preview 4 是 2022 年的东西，Python 3.8 锁死。**
   在新系统上典型报错是找不到 `libpython3.8.so.1.0`——解法是
   `export LD_LIBRARY_PATH=$CONDA_PREFIX/lib:$LD_LIBRARY_PATH`。
   本机（驱动 590.48.01 / CUDA 13.1）跑 cu118 的 torch 靠的是向后兼容，
   **能跑但不在作者验证过的组合里**，出问题先怀疑这里。
2. **许可写得不干净。** README 的徽章写 Apache-2.0，**但 GitHub license API 返回
   `NOASSERTION`**——仓里有 `LICENSE` + `NOTICE` + `THIRD_PARTY_NOTICES.md` 三个文件，
   而且明说「物体网格、机器人资产和数据集可能有本仓库之外的条款」。
   **自己用没问题，要再分发先把 `THIRD_PARTY_NOTICES.md` 读完。**
3. **头配置不匹配是最容易犯的错。** 拿发布权重去跑默认（6 头）的测试脚本会直接维度不对。
   `test_wm_craftnet.sh` 是配发布权重的，`test_wm_craftnet_y.sh` 是配全头的，别混。
4. **深度相机是显存大头，不是网络。** Isaac Gym 的 camera sensor 每个 env 都要开渲染目标，
   16G 上 256 envs 很可能 OOM，而那跟模型多大没关系。先 128、再 192。
5. **HF 上那个权重仓当前 0 下载 0 like。** 不是说它有问题，
   是说**如果你卡住了，大概率没有前人的 issue 可抄**——预留自己 debug 的时间。

### 2 · 三足压电微型机器人 —— 机械模型 + 五关控制算法仿真，**装配体和 STEP 都发出来了**

**出处**：<https://github.com/shellinea/tripodal-microrobot>（3 ★，2026-09-12）
**相关**：`docs/MIL算法仿真教程.md`（逐行讲解） ｜ `simulation/motion_sim_L2.html`、`motion_sim_L4.html`（浏览器直接打开的交互动画）

- **做的是什么**：三条压电腿按 120° 径向分布。谐振点出推进力（OVS），
  低频弹跳减摩擦（LBS）；3 个单驱 + 3 个双驱共 6 个基向量，配 `K(θ)=sinθ/sin(120°−θ)`
  力分配和轨迹插补，实现**平面全向运动**。构型上力线过质心，
  **天生零旋转扭矩、零转弯半径**——这是它和轮式/腿式最不一样的地方。
- **为什么值得看**：它把控制算法拆成 **L1–L5 五个关卡**，每关一个 Python 脚本、
  一条明确的验收标准、一条对应的文献出处（补充材料 Fig. S4a / Note 2 / Fig. S4c-d /
  Note 5 式(8) / 主文 Fig. 5）。**这是把一篇论文的机理逐条做成可执行验证**，
  而不是"复现了，跑通了"。
- **个人怎么切进去**：仿真那半**只要 `pip install matplotlib pillow`**，
  `python simulation/L5_ptp.py` 就能看 PTP 闭环导航跑起来。
  机械那半 `model/` 里有 SolidWorks 导出的 STEP/STL，GitHub 网页上点 STL 能直接 3D 预览。
  切入点：L3（偏航漂移与 IMU 预回转补偿）目前是开环补偿，**换成闭环 EKF 是一天的活**。
- **坑**：作者的进度清单诚实但也说明了边界——**ESP32 固件、PCB、上位机联调三项都是未打勾的**。
  压电驱动要几十到上百伏的驱动波形，**真做硬件的成本和风险都远高于仿真那半**，
  别按「跑通仿真 = 能造一台」估。许可：仓里**没有 LICENSE 文件**，
  想用它的 STEP 做衍生设计先开 issue 问。
- **归类**：硬件（机械模型 + 压电驱动），仿真部分零成本可跑。

### 3 · Virtual-Dexterous-Hand —— 灵巧手抓取评测台，**用合成数据手套数据，真手套一只都不用买**

**出处**：<https://github.com/czx-not-456/Virtual-Dexterous-Hand>（2026-09-16，v0.4.6）
**相关**：`datasets/synthetic_glove_v1.csv`（8 组 × 600 帧） ｜ `experiments/benchmark_synthetic.py`（批量跑 + HTML 看板）

- **做的是什么**：数据手套 → 手部动作采集 → 虚拟灵巧手（MuJoCo）交互。
  但 **v0.4.0 起的核心是评测**：六个标准物体任务 `pinch / wrap / sphere / card / bottle / box`，
  每次运行自动产出 `CSV + summary.json`，指标包括接触率、**稳定接触率**、首次接触时间、
  连续稳定帧数、P95 延迟、关节 RMSE、指尖接触率、物体姿态漂移。
- **为什么值得看**：README 里那句自我限制写得比很多论文诚实——
  「当前模型手掌基座固定，因此 `success_proxy` 定义为"连续稳定接触代理"，
  **不等同于抓起并搬运成功率**。若后续加入手腕/机械臂自由度，再增加 lift / transport 指标。」
  **知道自己的指标在代理什么、并把它写在最显眼的地方**，这是能不能信这堆数字的分水岭。
- **个人怎么切进去**：`pip install -r requirements.txt` → `pytest -rA` →
  `python -m src.main --sim mujoco --render --input dataset --dataset datasets/synthetic_glove_v1.csv --dataset-trial 0 --task pinch --steps 600`。
  **零硬件、纯 CPU 也能看**。最直接的贡献：作者自己点名的下一步是加腕部/机械臂自由度，
  **把 `success_proxy` 升级成真正的 lift 指标**——MuJoCo 里加一个 6 自由度浮动基座是半天的活，
  但它会让整套指标的含义变了一个档次。
- **坑**：① **全部是模拟数据**，`synthetic_glove_v1.csv` 是生成的，
  不是真手套录的——迁移到真手套时，噪声模型和标定误差是完全没覆盖的一块。
  ② 文档以 PowerShell / Windows 路径为主（`D:\Vhand\...`），Linux 上要自己改。
  ③ 仓根目录有 **17 个 CHANGELOG / VALIDATION 文件**，版本演进读起来很碎，
  **直接从 `README.md` + `CHANGELOG_v0.4.2.md` 入手**，别从头翻。
  ④ 无 LICENSE。
- **归类**：软硬兼具（灵巧手模型 + 数据手套接口，但当前落点在仿真评测）。

#### 为什么现在值得做

1. **它把"一台开源机器人的机械部分应该长什么样"给出了一个完整答案。**
   绝大多数开源机器人仓只有 STL。这个仓有：
   - `hexapod_prototype.py` —— 参数化常量 + trimesh 孪生，**是每一个尺寸的唯一真源**
   - `_verify_prototype.py` —— **设计规则验证器**，`make verify-fast` 一条命令
   - `cad_step_test/build_step_first_test.py` —— BREP 实体构建器（STEP 优先，不是 mesh 优先）
   - `design_spec.yaml` —— 人能读的几何契约
   - `fastener_registry.py` —— 紧固件 BOM + 缓存网格
   - `strength/` —— 可选的 FEA 失效点校核（Gmsh + CalculiX）
   - `mesh_mujoco/build_mesh_model.py` —— **从 as-built CAD 生成 MuJoCo 模型**
   **最后这条是关键**：CAD 改了，仿真模型跟着改，不是两份手工同步的东西。
2. **成本真的在个人可承受区间。** $615 ≈ 4400 元，$1000 ≈ 7100 元。
   低端在标准里，高端略超——差别主要在舵机批次和打印耗材。
   作者原话：「有动力的建造者可以在一个周末让它在桌上走起来。」
3. **设计决策全部留了痕。** BOM 里能读到 Design B → C → D → E → F 的完整演进：
   为什么退掉了打印的 `servo_horn_adapter`（直接上购买的铝盘舵盘，每关节 Z 向省 4 mm）、
   为什么 +X 两颗螺丝自攻而 −X 两颗上热熔铜螺母（**因为 Φ8 热熔嵌件的凸台和舵机线缆出口物理上冲突**）、
   为什么 `coxa_bracket` 被折进了底盘板。**这种「为什么不是另一种做法」的记录比图纸值钱。**
4. **仓里还有两份 2026-09-05 的复盘**：`NEXT_ROBOT_MECHANICAL_LESSONS_2026-09-05.md`
   和 `NEXT_ROBOT_WIRING_LESSONS_2026-09-05.md`——**下一台要怎么改**，
   这是造过一台的人才写得出来的东西。

#### 个人怎么分步切进去

**路线 A · 零成本，只看不买（半天）**

```bash
git clone https://github.com/lukas/hexapod-cad && cd hexapod-cad
uv sync            # CAD 工具链：build123d / trimesh / pyvista / mujoco
make help
make build         # 重新生成 step_prototype/*.step 和 stl_prototype/*.stl
make verify-fast   # 跑设计规则验证器
make view-build    # PyVista 装配检查器：悬停看零件名，E 键爆炸视图，左键单独高亮
make view          # MuJoCo，完整物理 + 三角步态
```

`make view-build` 里悬停任一零件会在顶栏显示 `part_type Lx role`，
左键点一个零件其余全部降到 15% 不透明度——**这是看懂一台机器怎么装起来的最快方式**。
底部滑块 0.0–2.0 控制爆炸程度，左侧色块复选框按零件类型隐藏/显示。

> ⚠️ `make verify-fast` 里的线束可达性检查需要 `uv sync --extra sim`，
> 它会去读主仓 `../hexapod` 的关节契约。**`../hexapod` 是旧的会报
> `cannot import name 'servo_id'`**——这个报错不是你装错了，是 checkout 过期了。

**路线 B · 真造一台（2–4 周，其中打印占大头）**

1. **先下单舵机**（交期最长）。BOM 要 **20 颗 STS3215：18 用 + 2 备**，
   **明确要求"全部买同一批次"**——舵机批次间的机械公差会直接体现在腿的一致性上。
2. **主控是 Arduino Uno Q**（板载 Linux SoC + MCU）。
   注意这版 BOM **退掉了 Raspberry Pi、Arduino Mega 和 PCA9685**——
   STS3215 是半双工 TTL 总线智能舵机，Uno Q 直接驱总线，
   **没有外部降压、没有配电板，整个配电是 Wago 221 接线端子**。
   照老教程买 PCA9685 是白花钱。
3. **紧固件按 Design E**：每台 **72 颗 M3×8 SHCS**（36 颗进热熔铜螺母 + 36 颗自攻）
   + **36 颗 M3 黄铜热熔嵌件**（McMaster `94459A130`）。
4. **打印**。`make build` 出的 `stl_prototype/` 是派生产物，
   真源是 `step_prototype/*.step`。作者提过重印一条腿的全部连杆约 12 小时。
5. **胫节是 Ø8 mm 碳纤维管**，不是打印件；股节 `femur_link` 是**整根一体打印**
   （髋部叉臂 + Ø14 实心梁 + 膝部支架）。
6. 装完，用主仓 `lukas/hexapod` 的步态控制器和 RL 环境驱动它。

**路线 C · 最容易被合的贡献（半天到两天，几乎零成本）**

- **给 `make verify-fast` 补一条检查。** 验证器是这个仓的核心资产，
  而 `_verify_prototype.py` 里已有的规则（如 `check_servo_insertion_path`）
  给出了非常清楚的写法范式。**补一条"最小特征尺寸 vs 喷嘴直径"或"打印悬垂角"的规则，
  是这个仓最需要、门槛又最低的贡献。**
- **核一遍 MuJoCo 模型的惯量。** `mesh_mujoco/build_mesh_model.py` 从 CAD 生成模型，
  但**打印件的实际密度取决于填充率**，CAD 默认密度和 20% 填充的 PLA 差得远。
  量一个真实打印件的质量、反算等效密度、提回去——**半天，而且是这类项目的通病**。
- **BOM 里的链接全是 Amazon 搜索链接**（作者明说是因为 ASIN 会失效）。
  **补一份国内（淘宝/立创）对应型号的采购表**是纯体力活，但对中文读者价值极高。

#### 坑

1. **仓里没有 LICENSE 文件**（GitHub license API 返回 `NOASSERTION`）。
   主仓 `lukas/hexapod` 也要自己核。**造来自己玩没问题，要卖或者发衍生设计先开 issue 问。**
2. **0 star、刚拆出来、"This repo starts as a snapshot"。**
   CAD 的提交历史还留在主仓里。**这不是一个有社区的项目**，
   遇到问题基本只能读代码，别指望有人回 issue。
3. **PROTOTYPE.md 开头就警告：实物可能和当前 CAD 不一致**，
   实际装机配置单独记在 `robots/hexapod-1.yaml`。**按 CAD 打印前先看那个文件。**
4. **BOM 里那句「不要换舵机型号，除非你准备好重新测量并重新生成所有打印支架」是认真的。**
   整套连杆是围绕 STS3215 那个 40×20×40 mm 外壳 + 25T 输出花键 + 20 mm 铝盘舵盘尺寸做的。
   换成 DS3225 之类要重画。
5. **舵盘是 20 mm 铝盘（MG995/MG996R 类，Amazon B07D56FVK5），不是塑料四臂舵盘**，
   4 × M3 直接攻进铝里。买错这个，所有连杆都装不上。
6. **`XHORN_BOLT_PCD = 14.0` 是按"孔圈直径"理解的**，作者自己在注释里留了话：
   「如果卡尺量出来是 14 mm 见方而不是直径，改一行常量和螺栓角度即可。」
   **拿到舵盘先量，别直接打印。**

### 2 · urdf-usd-bridge —— 补上 URDF 转出来那台机器人「缺的动力学」，**而且是量过的**

**出处**：<https://github.com/fermarc98/urdf-usd-bridge>（2026-09-17，v0.1.0）
**相关**：[PyPI](https://pypi.org/project/urdf-usd-bridge/) ｜ `docs/BENCHMARK.md`（84 格完整表） ｜ `docs/HOW_IT_WORKS.md`

> 📌 **这条直接回答了 [09-18 那期](./2026-09-18.html)列的第 12 个口子**——
> 「写一个从 CAD 质量属性反算惯量并与 URDF 逐项比对的独立小工具，目前没有开源实现」。
> 一天之后就有了一个，而且做得比那个描述更远。

- **问题是什么**：URDF 转出来的机器人**运动学是忠实的，动力学是欠定的**。
  没有驱动增益、没有 armature、有时没有惯量张量，偶尔还有关节被焊死。
  **而三个物理后端（PhysX / Newton / MuJoCo）各自用不同方式补这些洞**——
  同一个文件在三个引擎里是三种行为。
- **它做什么**：三条命令。`inspect` 报告哪些物理量**真的在**、
  哪些是**schema 兜底**、哪些是**被显式写过的**（「写过的 0」和「没写」含义不同）；
  `fix` 从机器人自身几何推导 PD 增益、armature 和惯量张量，恢复被转换器焊死的关节限位，
  **以 `over` prim 的形式写进原文件之上的新图层**——原文件一个字节不改，
  图层可以 diff、可以 mute、可以手调；`convert` 一条龙。
- **为什么值得看 —— 它把数字摆出来了**：

  | 机器人 | 后端 | 转换器输出 | 修复后 |
  |---|---|---|---|
  | **SO-101 臂** | PhysX | 发散（3.71 rad） | **0.105 rad** |
  | **SO-101 臂** | MuJoCo | 发散 | **0.105 rad** |
  | SO-100 臂 | PhysX | 2.19 rad | **0.302 rad** |
  | Unitree Go2 | PhysX / Newton / MuJoCo | 2.79 / 发散 / 发散 | **0.029 rad** |

  14 个机器人 × 3 个后端，保持姿态的漂移**改善 35 格、变差 0 格**，
  **19 次在转换器输出上发散的运行在修复后收敛**。跨后端一致性从 7.9e-2 rad 到 7.6e-5 rad。
- **然后它主动说了两件新闻稿会删掉的话**：**14 个基线在 Newton 上全部发散，修复只救回 9 个**；
  以及**有一个调参常数扫了一百倍量级、发现毫无差别**，这条被记录下来而不是埋掉。
- **个人怎么切进去**：
  ```bash
  uvx --from 'urdf-usd-bridge[core]' urdf-usd-bridge inspect robot.usda
  ```
  一条命令，**什么都不用永久安装**。拿你自己那台臂的 URDF 跑一遍 `inspect`，
  看它报什么。作者明说语料只有**两个来源的 12 台真实机器人**——
  **加一台新机器人进语料、报出前后漂移数字，是这个项目最缺、也最容易做的贡献**。
- **坑**：① **v0.1.0 只在 Linux 上验证过**。macOS 能 `inspect`/`fix` 但**不能 `convert`**
  （`usd-exchange` 没有 macOS wheel）。② **Debian/Ubuntu 上裸 `pip install` 会被 PEP 668 拒绝**，
  README 专门写了这一段，并且明确说 `--break-system-packages` 在跑 ROS 的机器上是个坏主意——**听它的**。
  ③ `usd-core` 是 30 MB 原生 wheel，**和 Isaac Sim / ROS 自带的 OpenUSD 会打架**，一定要进 venv。
  ④ 完整基准需要 Isaac Sim 6.1 + Newton + GPU，**但 `inspect` 和 `fix` 只依赖 numpy + usd-core**，
  这两条在任何机器上都能跑。⑤ 作者自己把「Limits」放在 README 顶部让你先读——照做。

### 3 · DeliveryGym —— 让视觉语言模型去当快递员，**64 场留出班次、CPU 一小时几千局、一个能当钱花的分数**

**出处**：<https://github.com/mk322/DeliveryGym>（2026-09-18，MIT）
**相关**：[arXiv:2609.19801](https://arxiv.org/abs/2609.19801) ｜ [HF 数据 mk322/DeliveryGym-albums](https://huggingface.co/datasets/mk322/DeliveryGym-albums)（7.8 GB）

- **做的是什么**：一个 VLM 当快递员。它每一回合看到几张照片——
  路口各个方向的街景、画着路线的手机、订单条、时钟、自己的笔记——
  然后输出一条想法和一个工具调用（`walk_to(街名, 方位)`）。
  送到一单赚 `3.00 + 0.01 × 米数`，准时全额、迟到部分、没送到为零。
  **调度员每送完一单就补新单**，所以一个班次是一个队列对着一个时钟——
  **你在手上这单花掉的时间，就是下一单少掉的钱**。
- **为什么值得看**：
  1. **分数是钱，不是成功率。** 这让"绕远路"和"慢"这两种失败第一次在同一个标度上可比。
  2. **两条参考策略同时发布**：一个只读文字的快递员，一个直接读路网图的快递员。
     **两条都在同样的 64 场留出班次、同样 60 回合上跑，都在 CPU 上一分钟跑完**——
     所以任何一个数字**天生带着地板和天花板**。这比「我们比 baseline 高了 3 个点」有信息量得多。
  3. **waypoint 赛道是离线、确定性的照片相册，CPU 上一小时能跑几千局。**
     不需要 GPU、不需要渲染引擎。
  4. Any-point 赛道才需要 Unreal（实时巴黎场景，`walk_to_pixel(视图, u, v)`）——
     **两条赛道分开，是为了让没有 UE 的人也能完整参赛。**
- **个人怎么切进去**：Python 3.11+，MIT 许可，仓里有 `docs/RUNNING.md`（环境 API）
  和 `docs/TASK_DESIGN.md`（任务设计）。先跑两条参考策略拿到上下界，
  再把你自己的模型塞进去（本机 16G 跑得动的开源 VLM 都行），
  **报一个和那两条参考策略并排的数字**。相册 7.8 GB，先看有没有子集下载。
- **坑**：① **7.8 GB 相册**是硬门槛，网不好先算时间。
  ② 这是"具身智能"里偏**规划/长程决策**的一侧，**没有关节、没有力**——
  如果你要的是操作或运动控制，这条不是你要的。
  ③ Any-point 赛道要 Unreal Engine，**个人跑不动就老实只打 waypoint 赛道**，
  作者把它设计成可以只打一条。

### 🌍 国外 · Local Mesh —— 把「图 → 网格」整条搬进自己那张卡，**一次生成 0 元**

**出处**：<https://github.com/Jackicus/Local-Mesh>（2026-09-14）
**相关**：[TripoSR](https://huggingface.co/stabilityai/TripoSR) ｜ [Hunyuan3D-2mini](https://huggingface.co/tencent/Hunyuan3D-2mini) ｜ [TRELLIS](https://github.com/microsoft/TRELLIS)

**做什么**：一个桌面应用（Electron + three.js + uv 管的 Python worker）。
丢一张图进去，出一个网格。**不上云、不要账号、不上传**。

它替你做的是最烦的那一段：**读你显卡的 compute capability，装匹配的 PyTorch**，
每个模型的依赖装进各自的环境（`~/.local-mesh/env`），**不碰系统 Python**。

模型表（README 原表，按显存从小到大）：

| 模型 | 参数 | 显存 | 许可 | 备注 |
|---|---|---|---|---|
| TripoSR | ~0.5B | ~4 GB | MIT | 几秒一个网格，适合预览 |
| Hunyuan3D 2 mini | 0.6B DiT | ~5 GB | 腾讯混元社区许可 | 每 GB 质量最好；有 turbo 和标准两版 |
| Hunyuan3D 2 | 1.1B | ~6 GB | 腾讯混元社区许可 | mini 的教师模型，表面更干净 |
| TripoSG | 1.5B | ~7.5 GB | MIT | 几何接近 SOTA；8 GB 卡上很紧 |
| Hunyuan3D 2.1 | 3.3B | ~10 GB | 混元 3D 2.1 社区许可 | 这里几何最锐利；要 12 GB 卡 |
| Step1X-3D Geometry | 1.3B | ~10 GB | **Apache-2.0** | 这个体量里**许可最宽松**的一个 |
| TRELLIS image-large | 1.2B | ~16 GB | MIT | 稀疏体素隐变量；最细也最吃显存 |
| Mock | – | – | – | 程序化网格，不下载不用 GPU，**用来先跑通整条路** |

**为什么值得看**：

1. **16 GB 这张卡（本机 RTX A4000）在这张表里是天花板位置**——
   除了 TRELLIS 要贴着上限跑，其余七个全部有富余。**这是少有的"本机配置正好够"的场景。**
2. **成本论点在这里是硬的**：一次生成的边际成本是**电费**。
   对照下面国内那条，同样一个摆件走 API 路线是「文生图 + 图生 3D」两次付费调用。
   **如果你要批量试 20 个造型，本地跑的经济性不是省一点，是差一个量级。**
3. **它有真正的队列**：丢一个文件夹的图进去走人。一个 worker 保持模型常驻、
   报告显存、每次跑完释放、闲置时卸载、能干净地取消。
   **这是把"生成"当生产流程而不是当 demo 的写法。**
4. **管线是节点图**（图 → 去背景 → 模型 → 清理 → 导出），可以存成 profile 复用；
   模型设置由注册表生成，**加一个模型是几行代码**。

**个人怎么切进去**（本机，约 1 小时 + 下载时间）：

```bash
git clone https://github.com/Jackicus/Local-Mesh && cd Local-Mesh
npm install && npm run dev
```
然后在应用里：**Models → Set up environment**（一次性）→ 在模型卡上
**Download weights** + **Install dependencies** → **Generate**，拖一张图进去。
输出落在 `~/.local-mesh/outputs`。

> **先跑 Mock 模型**——它不下载任何权重、不用 GPU，但会把队列、worker 和查看器
> 整条路走一遍。**几个 G 的权重下下来才发现 Electron 起不来，是最亏的那种失败。**

**要求**：Node 20+、`git`、`uv` 在 PATH 上、NVIDIA 驱动。
本机需要 `. /workspace/cuda/env.sh`（见 `/workspace/CLAUDE.md`），
**每轮新进程都要重新 source**。

**跑一个件大概多少钱**：
- **API token：0 元。** 整条生成链路在本地。
- **电费**：A4000 满载约 140 W，TripoSR 一个网格几秒、Hunyuan3D 2 mini 一个约几十秒，
  **按一度电 0.6 元算，跑 100 个网格的电费在 1 元以内**。
- **真正的成本是首次下载**：七个模型全下约 30–40 GB，以及一次性的 torch 环境（几 GB）。
- **但这只是"生成"那一段**。如果你用一个 agent 来写提示词、挑图、判断结果，
  **那部分的 token 费照算**——本地化省掉的是几何生成，不是对话。

**坑**：
1. **生成出来的是实心 mesh，不是参数化模型。** 拿去打摆件可以，
   **拿去做"要塞东西进去"的配合件不行**（没有内腔、没有真孔、尺寸不可控）。
   这一点下面国内那条说得更清楚。
2. **许可要一个一个看。** TripoSR / TripoSG / TRELLIS 是 MIT，
   Step1X-3D 是 Apache-2.0，**但三个 Hunyuan3D 走的是腾讯社区许可**——
   商用条款和 MIT 完全不是一回事。README 把许可列进了模型表，**用之前点进去读**。
3. **无 LICENSE 文件**（应用本身），0 star，2026-09-14 建仓。
4. **"任何 NVIDIA 卡"要打个折**：4 GB 卡只有 TripoSR 能用，
   而 TripoSR 的质量定位是"预览"。**想要能打印的质量，起步是 Hunyuan3D 2 mini（5 GB）。**
5. 没有 NVIDIA 卡时它退回 CPU torch——**能跑 Mock 和 TripoSR，别的别想**。

### 🇨🇳 国内 · 想啥印啥（thought-to-3d-print）—— **一句话到拓竹里能打开的模型**，而且它会先分岔再动手

**出处**：<https://github.com/WILLBETHEKINGSOONORLATER/thought-to-3d-print>（2 ★，2026-09-15）
**相关**：`SKILL.md`（主流程） ｜ `references/parametric-modeling.md`（路径 B 的全部规则） ｜ `scripts/param_shell.py`、`stl_fix.py`

**做什么**：给 AI 助手装的一份 Skill。整个仓只有 7 个文件：
`SKILL.md` + 一份参考文档 + 三个 Python 脚本。**终点明确停在「模型在 Bambu Studio 里打开」，不做切片。**

**它最值得抄的一点，是开工前先问的那个岔路**：

| | **路径 A · 场景件** | **路径 B · 精确配合件** |
|---|---|---|
| 用户要的是 | **"像什么"** | **"装得下什么、哪里透气"** |
| 典型 | 摆件、手办、公仔、挂件 | 外壳、收纳盒、支架、任何要塞东西进去的件 |
| 做法 | 文生图 → 图生 3D | 参数化建模（写数字 → 算几何） |
| **怎么和用户对齐** | AI **列出形状细节选项**让你挑 | AI **列出尺寸表**让你确认 |

README 里那句话是整份文档的核心论点：

> **为什么配合件不能靠"生成"？** 因为生成出来的东西是实心的，
> 没有内腔、没有真孔、尺寸也没法精确控制——**东西塞不进去，麦克风也收不到声**。

**"图比文字准，数比图准"**——场景件用图对齐，配合件用数对齐。
它知道该拿哪种东西给你确认。**这是这条链路上做对了的项目和做错了的项目的分界线**，
上面那条 Local-Mesh 的第 1 个坑说的是同一件事。

**第二问是打印机型号**，因为打印体积直接决定模型会不会超尺寸
（A1 mini 180³ / A1·P1·X1 系 256³ / H2S 340×320×340 / H2D 350×320×320 / H2C 330×320×320）。
它还明确写了**不要问喷嘴直径**——「默认 0.4 mm 就行，用户不懂问了也是白问」。
**这是把"该问什么、不该问什么"当成设计决策来写，而不是让模型自由发挥。**

**个人怎么切进去**：

1. 下载 ZIP，把文件夹拖进你的 AI 助手，说「装上这个技能」。**约一分钟，不装 Python、不开终端。**

### 🇨🇳 国内 · Dexmal Realtime-VLA 三件套 —— **把 π0 的一次前向压到 20 ms**，而且是能直接 copy 走的单文件

**出处**：<https://github.com/dexmal/realtime-vla>（★616，MIT）
**同系**：[realtime-vla-v2](https://github.com/dexmal/realtime-vla-v2)（★156，MIT）｜
[realtime-vla-flash](https://github.com/dexmal/realtime-vla-flash)（★108，Apache-2.0）
**论文**：[arXiv:2510.26742 Running VLAs at Real-time Speed](https://arxiv.org/abs/2510.26742) ｜
[arXiv:2603.26360 Realtime-VLA V2](https://arxiv.org/abs/2603.26360) ｜
[arXiv:2605.13778 FLASH](https://arxiv.org/abs/2605.13778)
**权重**：[Dexmal/RealtimeVLA-Flash](https://huggingface.co/Dexmal/RealtimeVLA-Flash)

#### 是什么

Dexmal（原力灵机，`dexmal.com`，也是 Dexbotic ★2070 那家）做的一条**专门解决「跑不快」**的线，三级递进：

| 仓库 | 解决哪一层 | 关键数字（RTX 4090） |
|---|---|---|
| `realtime-vla` | **kernel 层**：给 OpenPI 的 π0 / π0.5 手写 Triton 推理核 | π0 一次前向：1 视角 **20.0 ms** / 2 视角 **27.3 ms** / 3 视角 **36.8 ms** |
| `realtime-vla-v2` | **部署栈**：标定、执行器、控制、学出来的速度选择 | 真机双臂任务比常规基线快 **约 3×**，接近硬件极限 |
| `realtime-vla-flash` | **算法层**：给扩散式 VLA 做投机推理（业界第一个） | 2 视角 **7.8 ms**，>125 Hz；任务级平均 **3.04×** |

v1 那篇论文的招牌 demo 是**接一支掉下来的笔**，端到端 sub-200 ms、30 FPS 推理——
这个任务没法靠「预测一段轨迹然后闭眼执行」蒙过去，必须真的连续看、连续改。

#### 为什么这条值得先读

**因为它把「实时」拆成了三个可以分别下手的问题，而不是一句口号。** 很多号称实时的工作只动其中一层，
读完不知道自己的瓶颈在哪。这三个仓库的表格直接告诉你：kernel 优化能把 45.8 ms 打到 29.2 ms，
再往下要靠算法（投机解码）而不是继续抠核。

还有个很实在的好处：**v1 的用法是「把单文件复制进你自己的工程」**——
`pi0_infer.py` / `pi05_infer.py` / `dm0_infer.py`，不是让你装一个框架。
它还附了 `test.py` 做 **Triton vs JAX 的 MAE 逐维对比**，
也就是说你可以先证明「加速没有改变数值」再上机，这在换 kernel 的活里是最该有、又最常被省掉的一步。

#### 个人怎么切进去（本机 A4000 16G 的现实版）

1. **先别碰机器人**。v2 里带一个 `mock` 配置，能把 server/client 整条代码路径跑通，**不需要任何真机**。
   先跑 `mock`，把时间轴日志（它用 rerun 的 `.rrd`）打出来看清楚「观测什么时候到、动作什么时候发」。
2. **测你自己这张卡的真实数字**。直接跑 `test.py` 和 flash 的 `scripts/spec/pi0_benchmark.py`。
   **不要抄 4090 的数**：A4000 显存带宽 448 GB/s，约为 4090 的 0.44，
   这类访存受限的核**换算过来大致要乘 2～2.5**——预期 2 视角在 **60～70 ms** 量级，
   也就是 **15 Hz 左右**，而不是 README 里的 30 Hz。
3. **这本身就是一个能交出去的产出**：仓库的 benchmark 矩阵只有 4090 / 5090 两列，
   **没有任何 Ampere 专业卡的数**。把 A4000（sm_86）那一列补上、连带 `test.py` 的数值一致性结果，
   就是一个干净、能复现、一天能做完的 PR 或 issue。成本 0 元。

#### 坑

- **它加速的是前向，不是整条链路。** v1 的 20 ms 是「一组观测 → 一段动作」，
  相机采集、图像预处理、序列化、机器人通信全不在里面。真机上这些加起来常常比推理本身还大——
  v2 存在的理由就是这个，别只读 v1 就以为自己实时了。
- **显存要算清楚**：π0 / π0.5 是 3B 级，bf16 权重约 6.5 GB。本机这张 A4000
  **基线已经被别的进程占了约 4.4 GB**，剩下约 11.6 GB，2 视角能跑但不宽裕，3 视角要先把卡腾出来。
- **v1 最后一次 push 是 2026-02-10，v2 是 03-31** ——不是活跃在更新的项目，是已经稳定的底座。
  提 PR 前先看 issue 有没有人应答，别默默做完发现没人合。
- **要 PaliGemma tokenizer 和转好的 checkpoint**（`converted_checkpoint.pkl`），
  不是 `pip install` 完就能跑，权重那一步要自己走 OpenPI 的流程。

### 🌍 国外 · FlashVLA —— 让模型**一边执行一边解下一段**，延迟降 2.6× 而成功率还涨了

**出处**：<https://github.com/z-lab/flashvla>（★43，Apache-2.0，2026-09-15 仍在推）
**论文**：[arXiv:2608.27384](https://arxiv.org/abs/2608.27384)（CoRL 2026，Zekai Li / Jiaming Tang / Zhijian Liu）
**相关**：[项目页](https://z-lab.ai/projects/flashvla/) ｜
[权重 z-lab/flashvla-pi05-libero](https://huggingface.co/z-lab/flashvla-pi05-libero) ｜
[VLASH](https://github.com/mit-han-lab/vlash) ｜ [LeRobot](https://github.com/huggingface/lerobot)

**做什么**：流匹配（flow-matching）VLA 的动作解码要迭代好几步，于是执行时会「停一下、算一段、再动」。
FlashVLA 维护一个**流式动作缓冲区，里面同时挂着几段处于不同噪声水平的 chunk**，
用 **chunk-wise 因果注意力**一起解——新的一段在旧的一段还在被执行时就开始去噪。
参数 `d` 表示「当前 chunk 结束前多少步启动下一次推理」，`d=0` 是同步，`d≥1` 就是重叠。

**数字（这是它最硬的地方）**：

| 基准 | π0.5 | + FlashVLA | 变化 |
|---|---|---|---|
| LIBERO 平均成功率 | 96.9 % | **98.3 %**（`d=2`） | **+1.4** |
| LIBERO 单步耗时 | 53.8 ms | **20.6 ms** | **2.62×** |
| RoboTwin 2.0（50 任务） | 86.0 % | **90.6 %** | **+4.6** |
| SmolVLA 上迁移 | 80.1 % / 41.2 ms | 80.1 % / **29.7 ms** | 持平提速 1.39× |
| LingBot-VLA 上迁移 | 85.8 % | **89.3 %** | **+3.5** |

**这个组合很反直觉，也正是重点：异步通常是拿精度换速度，这里两样都涨了。**
原因说得通——同步执行时动作是「用旧观测算出来的」，等算完再发已经过期；
重叠之后每段动作对应的观测更新，**「不停顿」本身就是一种精度**。

**个人怎么切进去**：`sim_eval/libero/eval.sh` 一行起评测，**权重是放出来的，纯仿真，不要机器人**。
最值得做的是**把 `d` 从 0 扫到 3、画出成功率-延迟曲线**——论文只给了 0/1/2 三个点。
换 SmolVLA（450M，本机很轻松）做同样的扫描，是个一天量级、结论明确的复现。
延迟基准 `benchmarks/benchmark_latency.py` 支持 `--num_views=1/2/3`。

**坑**：

- **它的对比表里第三行就是上面那条国内的工作**（RTX 4090 / 2 视角：π0.5 45.8 ms → +Realtime-VLA 29.2 ms
  → +FlashVLA 26.7 ms）。**两者是叠加关系不是竞品**，别以为选了一个就不用另一个。
  同时也说明**FlashVLA 单独的增量只有 29.2→26.7**，真正的大头在 kernel 那层——
  读表的时候别把 2.62× 全算到算法头上，那个数是端到端、含了底座的。
- **π0.5 在 A4000 上是 3B**，显存同上一条的账；先用 SmolVLA 那条路把流程跑通更稳。
- **RoboTwin 2.0 要 server/client 两个 conda 环境 + SAPIEN**，装起来比 LIBERO 麻烦不少，先做 LIBERO。
- 成功率的涨幅在 LIBERO 上是 +1.0～1.4，**这个量级要多 seed 才说得清**，仓库支持多 seed sweep，用它。

### 📌 专题分析：这条线现在真正的分歧在哪（3 点）

**1. 「实时」正在从工程问题变回算法问题。**
2025 年的做法是抠 kernel（Realtime-VLA v1 就是典型），能拿到 1.5～2×，然后到头。
今年这批工作——投机解码（FLASH）、流式解码（FlashVLA、StreamingVLA）、免训练异步（FBFM）——
都是**改推理的组织方式而不是改算子**，而且能叠在 kernel 优化之上。
判断一条新工作值不值得看，先问一句：**它的基线里有没有已经做过 kernel 优化？** 没有的话那个加速比是虚的。

**2. 异步不再被当成「精度的代价」，而是精度的来源之一。**
FlashVLA 在 LIBERO 和 RoboTwin 上都是延迟降、成功率涨；2608.01880 的横评把话说得更死——
掉点掉在时间轴没对齐，不掉在异步本身。这是今年和去年最大的观念差别：
**开环执行一段陈旧动作，本来就是一种误差**，之前大家只是没把它算进账里。

**3. 真正还空着的是第 4 类：高频非视觉传感器进闭环。**
上面七篇里有六篇在讨论「视觉观测 → 动作」的时序，只有 TacForcing 碰了
**执行途中的触觉反馈改写正在跑的动作**，而它目前只有项目页没有代码。
这其实是最符合「连续输入传感器感知信息」这个描述的一类——
触觉和力是 kHz 级的，视觉是 30 Hz 级的，**两者的时间尺度差两个数量级，怎么塞进同一个策略里没有公认答案**。
本期主线国内 TOP 1 那条 **WM-Craftnet**（见上）恰好是个反例：它把指尖触觉和深度图一起压进循环状态空间模型——
**用一个 RSSM 当所有模态的公共时钟**。这条路和上面那批「给动作解码做异步」是完全不同的解法，
下期起会作为第 3 / 4 类的主条目跟进。

## 📈 趋势观察

**1. 「设计规则验证器」这周从 3D 打印链路溢出到了机械设计本身。**
hexapod-cad 的 `_verify_prototype.py` 做的事，和专题里那些 DfAM 检查器是同构的：
**把"这样设计会出事"变成一条能在 CI 里跑的断言**。
而且它给出的范式比打印链路那边成熟——`check_servo_insertion_path`
这种"热熔嵌件凸台和舵机线缆出口物理冲突"的规则，
**是把一次真实的装配失败固化成了代码**。
这条线值得盯：**开源机器人仓里，有验证器的和只有 STL 的，正在拉开差距。**

**2. 惯量张量这个洞，一周之内被从两个方向各捅了一下。**
09-18 我们把「从 CAD 质量属性反算惯量并与 URDF 比对」列为无人实现的缺口。
本期 urdf-usd-bridge 从**几何**推导惯量并写成可 diff 的 USD 图层，
hexapod-cad 从 **as-built CAD** 生成 MuJoCo 模型。
两者都没有直接解决"打印件填充率导致的密度误差"——
**这仍然是那个洞里最后没被堵上的一块**，而且它是实测就能解决的（见国外 TOP 1 路线 C）。

**3. 「把数字和它的地板天花板一起给」正在变成一种可识别的写法。**
本期三条：DeliveryGym 同时发两条参考策略作上下界；
urdf-usd-bridge 报 35 格改善 / 0 格变差，**并且主动说 Newton 上 14 个全发散只救回 9 个**；
tailong-wu 的 microduck-mjbatch（见下面口子 3）把 ball-balance 的半成功原样报出来。
**共同点是：单个数字没有意义，区间和失败案例才有。**
这和 09-17 real2sim-droid、09-18 dexterous-astra 的写法是一脉的。
**看到只报一个孤零零的 SOTA 数字的仓，默认打折。**

**4. STS3215 正在变成开源机器人的事实标准舵机。**
本期国外 TOP 1（18 颗）、RyanXXYC/Pounce（Feetech STS 总线工具，见下面口子 5），
加上历期反复出现的 SO-101 / LeRobot 生态——**同一颗舵机、同一套半双工 TTL 协议**。
这件事的实际意义是：**标定工具、供电经验、失效模式、甚至二手件，开始可以跨项目复用。**
如果你要挑一个硬件生态入坑，这是目前证据最足的那个。

**5. 世界模型这一周在国内这一侧密集出货，但可动手的只有一个。**
`shengshu-ai/Motus2`（41 ★，自进化通用世界模型 / 灵巧操作）本期 star 数最高，
**但仓里只有一个 README.md，没有代码、没有权重**——不满足「技术可达成」，故未列入。
`RCL-Robotics/Awesome-World-Action-Models`（37 ★）是列表。
**真正给了代码和权重的是本期国内 TOP 1 的 WM-Craftnet。**
提醒一句：这一波"世界模型 + 具身"的项目页做得都很漂亮，**点进 Code 标签页再决定要不要投入时间。**
