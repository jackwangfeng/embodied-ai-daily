1️⃣ 【深度】Daniel-rmc/ManiLoop —— 不是又一个仿真玩具，是一台「谁都别想蒙混过关」的闭环评测机

是什么。 ManiLoop（MIT，2026-09-16 建仓，中英双语 README）把 GPT 类通用模型和 LeRobot 类学习策略放进同一个 MuJoCo 回路，浏览器里选任务、连模型、逐步执行、回看轨迹。 内置 pick_place / push 两个自建任务（ARX X5 与 Franka Panda，各两种桌面布局）， 外加官方 LIBERO 的 130 个任务（spatial / object / goal / 90 / 10 五个 suite）。

和昨天那条 embodied-jev 长得像，但目的不是一回事，这点值得说清楚，否则你会装错工具：

embodied-jev（09-22） ManiLoop（本期）
任务来源 自建三任务 自建 2 个 + 官方 LIBERO 130 个
控制器 / 成功判据 自定义 LIBERO 官方 Panda + OSC_POSE + check_success，20 Hz
主要用途 看懂「观察→决策→执行」闭环 公平对比不同策略，并导出可复用的 LIBERO episode
版本钉死 — LIBERO 钉到 commit 8f1084e3、robosuite 1.4.0、MuJoCo 2.3.7

它的诚实性设计和 embodied-jev 是同一个路子，但更硬： 策略的输入里不包含物体真值、仿真接触、奖励和成功信号；独立评测器可以读仿真状态并中止 episode， 而模型自己声明的 done 不算成功判据；改指令文本不会改变任务的评测器。

作者自己放的四模型对照（2026-09-16，同一 libero_spatial task 0 / init 0 / seed 0， 「把盘子和调料碗之间的黑碗放到盘子上」）是这么写的：

模型 官方任务结果 策略调用 本地模型推理 控制步 仿真秒 墙钟秒
GPT-6 Astra 成功 46 — 706 35.30 667.33
SmolVLA 成功 78 2 78 3.90 —
ACT 预算内未成功 500 5 500 25.00 66.13
Diffusion Policy 成功 79 10 79 3.95 57.35

它自己先把这张表否掉了一半：README 明说「策略调用」在 GPT 和本地策略上含义不同 （GPT 是每个高层动作一次服务请求，本地策略是每控制步一次 select_action，多数命中已有动作队列）； SmolVLA 那次网页跑没保留与 CLI 同定义的墙钟；执行路径、预算、后台负载都不同，不能当速度排名； ACT 的失败「是这个 checkpoint 在这个初始化下的结果，不是对 ACT 的结论」。 另外 每次推理时物理都是暂停的 —— 也就是说这张表测不出延迟，它只测「能不能做完」。 （想测延迟请看本期专题二那两条。）

上面这组数跑在 Apple M4 / 24 GiB 统一内存 / PyTorch MPS 上。折算到本机 A4000： 本地策略（SmolVLA 450M、ACT、Diffusion Policy）显存占用都在 2–4 GB 量级， A4000 剩下的 ~11.6 G 绰绰有余，CUDA 下推理会比 M4 的 MPS 快，不是瓶颈。

为什么现在值得做。 LIBERO 的平均成功率已经被刷到 98% 附近（本期专题二那条 vla-edge-policy 有这个数）， 在成功率上再争 0.5 个点是大实验室的事。但**「同一个任务、同一个初始化、同一个官方判据下， 不同路线的模型各自是怎么失败的」这一格，公开数据里基本是空的** —— 因为没人愿意搭一个 连自己都能被判失败的台子。ManiLoop 把这个台子搭好了，而且不需要 GPU、不需要权重、不需要 API key 就能先跑起来（Step 1 的 python -m maniloop demo 是纯手动控制）。

三个虚拟环境分得很干净，这是它能跑起来的关键： .venv（3.12，主程序）/ .venv-libero（3.10，LIBERO 及其钉死依赖）/ .venv-vla（3.12，LeRobot 推理）。

坑与风险。

  • Python 版本是硬的：主程序要 3.12，LIBERO 要 3.10。装到一个环境里必炸，别图省事。
  • maniloop demo 打开页面不等于开始推理，但 benchmark 一跑就开始烧配额，README 专门提醒了这点。
  • 选了模型 ID 不代表它支持视觉和结构化动作 —— 接上去报错多半是这个，不是代码问题。
  • 物理在推理时暂停，所以这个台子不能用来测延迟，别拿它的墙钟秒去论证「谁更快」。

1️⃣ 【深度】ahmedsleem109/WorkshopRobot —— 「把 10 号扳手拿给我」：6 GB 显卡上跑完的端到端具身系统，外加一份罕见的失败解剖

是什么。 WorkshopRobot（MIT，2026-09-21 建仓）是一套 语言指令驱动的移动操作系统：你打一句 "bring me the 10mm wrench"，MuJoCo 里的 Unitree Go2 + Z1 臂走到工作台，用 VLM 找到扳手，从工具架上取出，跨过一个 12 cm 的台阶，交到人手上； 拿不到就说清楚为什么拿不到。

关键前提写在 README 第一行：全程在一张 6 GB 消费级显卡（RTX 3060 笔记本）上训练并评测完， 没有 API key、没有云、没有集群。折算到本机 A4000 16G（基线被占 ~4.4 G、剩 ~11.6 G）， 显存有接近一倍的富余，训练时间约为 3060 笔记本的 0.5–0.7 倍。这是本季度最容易在本机完整复现的端到端系统。

四层，每层一份契约：

"bring me the 10mm wrench"
  → orchestrator（状态机）  按可观测门推进：底盘到站了吗？locate 返回点了吗？夹爪握住了吗？
      ├ navigate_to  Layer 3：RL 行走策略（纯 numpy，50 Hz）
      ├ locate       Layer 1：Qwen3-VL-2B 出点 → 腕部深度 → 3D
      ├ grasp/place  Layer 2：SmolVLA，或脚本化示教器
      └ ask_human    指令歧义或工具不在时

编排器只在可观测的门上推进，从不在「脚本大概成功了」上推进 —— 这一句是整个系统能出结果的原因。

根因有两个互相独立的部分：搬运摆动占了关节 1 平方运动量的 91%，把真正决定抓取成败的 3–5 mrad 逼近运动淹没了；以及 pick 和 place 共用一个归一化器，而 place 在单个 10 Hz tick 里带 2.4 rad 的 IK 跳变。 三处修正（只训精细阶段、只训 pick、用分位数归一化替代 mean/std）之后：
