## 🇨🇳 国内

### ★ TOP 1（深度）· PhysBrainEvalKit —— 把 28 个空间 / 具身 benchmark 收进同一条命令，而且允许你只有一张卡

**是什么。**

一套**面向视觉语言模型的空间与具身智能评测工具包**，9 月 8 日建仓，9 月 15 日还在推，21 星。
作者是 **DeepCybo · 中关村学院 · 中关村人工智能研究院**（这三个署名印在模型卡的 logo 图上，
不是我推断出来的）。它是在开源的 [EmbodiedEvalKit](https://github.com/pickxiguapi/EmbodiedEvalKit)
基础上扩出来的，这次放出的是：**28 个 benchmark 的适配器、统一的 HuggingFace 推理接口、
点定位类任务的统一指标协议，以及一个「模型常驻 + 分片」的执行器。**

配套模型是 **PhysBrain 1.5**，以 **Qwen3-VL** 为骨干，扩了动作 token 和视觉状态 token，
把语言回答、结构化空间输出、末端执行器轨迹、未来世界状态**全部写成离散 token**，
用同一个自回归目标训练，没有任务专用头。HF 上放了 **8B 和 2B 两个尺寸**
（8B 23 个赞 / 207 次下载，2B 12 个赞 / 152 次下载，均为本文写作时的数字），
另有一个可以直接在浏览器里传图试的 Space。作者报告 8B 在这套 28 项的组合上**总分 72.5**，
自称在被评的开源模型里排第一。

28 个 benchmark 的名单和数据源在 README 里逐行列了 HF 仓库地址，覆盖三类：

| 类别 | 代表 | 数量 |
|---|---|---|
| 沿用 EmbodiedEvalKit 协议 | ERQA、EgoPlan2、SAT、BLINK、CV-Bench、VSI-Bench、EmbSpatial、COSMOS、RoboVQA、VLABench… | 12 |
| **点定位 / grounding（改用统一 micro-F1）** | Part-Affordance-2K、PIOBench、PixMo-Points、PointBench、RefSpatial-Bench、RoboAfford、RoboRefit、RoboSpatial-Home、VABench-Point、Where2Place | 10 |
| 工具包之外、沿用各自官方规则 | ERQA-PLUS、ViewSpatial、MindCube、MMSI-Bench、3DSRBench、Q-Spatial-Bench | 6 |

**为什么现在值得做。**

具身 VLM 这一年最大的问题不是没模型，是**没有一把公认的尺子** —— 每篇论文报的 benchmark 组合不同、
prompt 不同、点定位的判对标准更是各写各的。这个仓做的事情就是把这些**钉死**：
统一输入协议、统一 prompt 模板、**贪心解码（`temperature=0.0`、`top_p=1.0`、`top_k=-1`、`seed=3407`）**、
benchmark 级和分片级的 `--resume`。只有 MMSI-Bench 是故意的例外，它显式开采样
（`--mmsi-temperature`、`--mmsi-seed`）。

对个人的意义在另一处：**这套东西整个社区都没有「在消费级单卡上到底能跑哪些、要多久、要多少显存、
数据集一共多大」这张表。** 作者用的是多卡分片跑法（`--gpus 0,1,2,3 --models-per-gpu 2`），
README 里没有任何单卡数字。**这张表就是你能交出去的第一份东西**，它不需要你有新想法，
只需要你有一张卡和耐心，而且它对后面每一个想复现的人都有用。

**个人怎么分步切进去。**

**Step 0（5 分钟，0 元）——** 先别装环境。打开
[HF Space demo](https://huggingface.co/spaces/DeepCybo/physbrain1-5-8b-demo)，
传一张你自己场景的图，试试它的空间理解、具身推理和点定位。**如果这个模型的能力和你关心的事没关系，
后面几步就别做了。**

**Step 1（约 1 小时）—— 环境。** Python 3.10+，作者用 3.11 验证。

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

分片启动器额外要 Bash、`taskset`、`nvidia-smi`。
⚠️ **FlashAttention 版本会影响分数**：作者写明 PhysBrain 1.5 是在 **FA4** 上训的，
用 FA4 评测结果正常，**用 FA2 会有小幅波动**（作者称在可接受范围内）。
你如果用 FA2，报数字时要注明。

**Step 2（半小时）—— 选模型，这一步决定你能不能在 16 G 卡上跑完。**

| 候选 | bf16 权重量级 | A4000 16 G |
|---|---|---|
| `DeepCybo/PhysBrain1.5-2B` | 约 4–5 GB | ✅ 宽裕，可以 `--models-per-gpu 2` |
| `Qwen/Qwen3-VL-4B-Instruct` | 约 8–9 GB | ✅ 单 worker 可跑，长视频 benchmark 要留余量 |
| `DeepCybo/PhysBrain1.5-8B` | 约 16 GB | ❌ bf16 放不下，要量化或 offload（作者未提供量化配置） |

（权重量级是按参数量 × 2 字节的**估算**，不含 KV cache 和视觉 token 的激活，实际峰值更高；
以你自己 `nvidia-smi` 看到的为准。）

**建议的第一枪：`PhysBrain1.5-2B` + `--only ERQA,PointBench`。**
一个多选题类、一个点定位类，正好各覆盖一种指标路径。

**Step 3（时间取决于网络）—— 先 dry-run，再下数据。**

```bash
export HF_HOME=/data/huggingface          # 指到大盘，别用系统盘
export HF_DATASETS_CACHE=/data/huggingface/datasets
bash scripts/eval_qwen3vl.sh \
  --model-path /models/PhysBrain1.5-2B --model-name pb15-2b \
  --output-base /results/pb15-2b --gpus 0 --models-per-gpu 1 \
  --cpu-per-worker 4 --only ERQA,PointBench --dry-run
```

⚠️ `--dry-run` **只验证模型配置和 CLI 参数并打印计划，不下载数据、不检查数据集文件** ——
这是 README 明说的，别把它当成「预检通过」。
**28 个数据集加起来有多大，官方没公布** —— 这是你能交出去的第二个数字。

**Step 4（跑全量）—— 去掉 `--dry-run`，加上 `--resume` 和固定的 `--run-id`。**
中断之后用同一个 `--run-id` 重启可以复用未完成的分片。单卡就 `--models-per-gpu 1`。

**Step 5（出表）——** `python scripts/summarize_benchmark_scores.py --help` 做聚合，
然后把「显存峰值 / 每个 benchmark 的墙钟时间 / 数据集体积 / FA2 与 FA4 的差」写成一个 issue 交回去。
**这一步才是产出。**

**成本与时间。** 全程**没有 API token 开销**（模型全在本地跑）。
自有 A4000：只有电费和时间，2B 跑完 28 项的量级估计是**一整天到两天**（作者未给单卡基准，
这是按 VLM 评测的一般吞吐做的量级猜测，不是实测）。
要跑 8B 的话，租一张 4090/A100 按市面 **¥2–4/小时**估，先用 `--only` 把流程跑通再包时段。

**坑与风险。**

1. ⚠️ **仓里没有 LICENSE 文件。** 这是它最大的风险：`gh repo view` 返回的许可是空。
   README 只写了「数据集许可由各自所有者管辖」，**没说代码本身按什么许可发布**。
   用之前先开 issue 问作者，别默认可用。
2. **点定位的分数不能和各 benchmark 的官方数字对比。** 那 10 个任务作者改用了
   **统一的 micro-averaged F1**（同时衡量预测有效性和目标覆盖），这是他们自己的协议，
   见 `docs/final_point_metrics_protocol.md`。
3. **两个轨迹类 benchmark 报的是 100−NRMSE**，为了让「越大越好」一致 —— 读表时别按原指标理解。
4. **只有 HF backend。** 分片启动器目前不支持 vLLM / SGLang（模型卡里说模型本身兼容，
   但**这套评测的执行器不支持**），吞吐上不去就是不去。
5. **数据集许可各不相同**：28 个数据集各自的访问条款要逐个看，商用前尤其如此。

### 2 · OptiDuck —— 把 microduck 搬到一块 ¥150 的 Radxa 板子上，外加一份 149 KB 的中文踩坑教程

**先说清楚它和前两期那两条 microduck 的区别**（避免你觉得在看重复内容）：

| 期 | 条目 | 讲的是 |
|---|---|---|
| 09-12 | Microduck 装机教程 | **整机 BOM 与装配**，核价约 ¥3700–4200 |
| 09-13 | microduck-playground | **四组可复现 RL 实验 + ONNX 策略 + 打印件** |
| **本期** | **OptiDuck** | **换一块 SBC（Radxa ZERO 3W）从零 bring-up**，以及子模块工程的组织方式 |

**是什么。** 一个 **umbrella 仓**：本体只放文档和归档，三块代码以 git submodule 引入 ——
上板软件栈（[pollen-robotics/microduck](https://github.com/pollen-robotics/microduck) 的本地变体，
一堆 Rust daemon：`robotd`/`configd`/`btd`/`padd`/`updaterd` 加 `robotctl`/`duckctl` CLI）、
RL 训练仓（[microduck_rl](https://github.com/pollen-robotics/microduck_rl) 的变体，
mjlab + MuJoCo 任务、HD1910 舵机台架标定、BAM 作动器辨识）、
结构硬件（[JoyandAI/OpenMicroDuck](https://github.com/JoyandAI/OpenMicroDuck)，SolidWorks CAD + BOM）。

主控从官方路线换成了 **Radxa ZERO 3W（RK3566 / 2 GB）**，跑 Radxa OS（Debian 13，6.1 内核），
舵机总线走 UART2，姿态传感器走 I2C4，步态策略在 MuJoCo 里用 RL 训完导出 ONNX 上板。

**真正的价值在那份 149 KB 的中文教程**（仓根目录那份「Radxa ZERO 3W 零基础部署调试教程」），
第 0 节直接叫「踩坑血泪史（必看！帮你节省 2~3 小时）」，七条都是**只有真上过手才写得出来的**：

1. **电源不够 → 内核能起来，但 TF 卡物理设备根本识别不到**
2. Windows 上烧 Armbian 镜像的已知 bug → **分区表被清掉**
3. Armbian 设备树里只有通用 `radxa-zero3`，**没有 ZERO 3W 专用 dtb**
4. PowerShell 的 `$env:USERPROFILE` 展开坑
5. SSH `Connection refused` → 板子上压根没装 `openssh-server`
6. initramfs 里 `ls /dev/mmcblk*` 两种情况的区别
7. **重启后 Wi-Fi 不自动连 → 开机即失联**（凭据被存进了用户密钥环）

第 6 节还有一段值得单独读的：**先跑 7 条诊断再动手**（启动配置文件叫什么、`/dev/ttyS2` 在不在、
**舵机总线上有没有 getty 在抢串口** ← 这条最阴），然后 6.7 节把它抽象成方法论：
「换一块新板子 / 换个新机器人，怎么自己设计 bring-up」。**这一节和 microduck 没关系，
对任何 SBC 机器人都成立。**

**个人怎么切进去。** 最低成本路线是**先只买板子**（Radxa ZERO 3W 零售价 ¥150 上下，
按你自己的渠道核价）：照教程烧卡、配好免密登录、跑那 7 条诊断、跑 `setup-board.sh`，
**这一步就能验证你会不会踩那七个坑，而且一个舵机都还没买。**
再往上才是整机（以 OpenMicroDuck 的 BOM 为准，量级参考 09-12 那期的 ¥3700–4200 核价）。
纯仿真的话，`microduck_rl` 里 HD1910 的 BAM 参数已经拟合进
`vendor/bam/bam/params/hd1910/*.json`，**不下载原始标定数据也能训**。

**坑。**

- **许可是混的**：软件 Apache-2.0，但 **OpenMicroDuck 的 CAD 与文档是 CC-BY-NC-SA-4.0，非商用**。
- **子模块要两步提交**：子仓 push 完，还得回主仓 `git add <子模块路径> && git commit` 把指针推上去，
  否则别人 clone 到的还是旧 commit。README 把这条单独写了一节，说明作者自己被咬过。
- **大文件不在 git 里**：HD1910 标定原始数据约 426 MB、训练权重归档约 405 MB，走 Release 附件，
  clone 下来是没有的。
- ⚠️ **仓根目录有一个 56 字节的小文本文件，文件名显示它记录的是作者自己的远程登录地址。**
  我没有打开它，也不建议你去看 —— **但把这类文件提交进公开仓是个坏习惯**，值得给作者提一个 issue。
- 新仓（9 月 15 日建），1 星，作者本人还在推。

  **以 STEP/STL 为准，别照着照片认零件**。
- 11 个舵机同时动的峰值电流不小，电源余量按 5 A 起步考虑。

### ★ TOP 1（深度）· RLE-Bench —— 给「编码 agent 当机器人学习工程师」出了一份资格考试，其中两题不用 GPU

**是什么。**

9 月 14 日放出的**基准**，**MIT 许可**，33 星，在线排行榜已经开了。
它问的问题是：**编码 agent 能不能干机器人学习工程师（Robot Learning Engineer）的活？**
不是「能不能控制机器人」，而是**开发策略、搭感知系统、设计本体**这一整套工程工作。

九个任务族，四类：

| 任务 | 类别 | 要做的事 | 要 GPU 吗 |
|---|---|---|---|
| task01 | 交互控制 | agent 在环，解厨房操作任务 | 是 |
| task02 | 交互控制 | **给未来的任务搭可复用的工具与技能**（评分方式：另一个全新 agent 拿你造的工具去解一个没见过的任务） | 是 |
| task03 | 交互控制 | 解具身推理挑战 | 是 |
| task04 | 策略开发 | 训人形全身动作跟踪策略，交 ONNX | 是（参考预算 1×RTX 5090） |
| task05 | 策略开发 | **在限量 replay 预算下训 VLA**（NanoVLA Recipe） | 是（参考预算 1×H100） |
| task06 | 感知估计 | 对抗性传感下估物体位姿 | 视变体而定 |
| **task07** | 感知估计 | **清料箱**：磁吸 Franka 把 12–16 个冲压钢件收进料巢 | **否（纯 CPU）** |
| **task08** | 机械设计 | **设计一个麦轮移动底盘**，要同时扛住 Panda / UR5e / xArm7 三条臂 | **否（纯 CPU）** |
| task09 | 机械设计 | 遥操作硬件与软件协同设计（Gello 重力补偿） | 否 |

**评测方式是这套东西最硬的地方**：agent 在一个容器里干活、写产物到 `/logs/artifacts/`，
**verifier 是另一个独立镜像**，拿隐藏的 seed、隐藏的场景、私有的评分代码重跑。
以 task08 为例：verifier 把你交的 `robot.xml` 里的 `arm_*` 子树**删掉**，
换上可信的适配器和三条标准臂，跑 A–E 五个动力学场景 × 三个隐藏 seed，
再把你的 `controller.py` 放进 **uid 隔离的进程**里跑十二个货架目标、1 kg 和 2 kg 各一遍，
还会重放第一个目标**检查确定性**。最终分数是「三条臂里最差的那条」。
`validity` 里有两个 **gate**（模型能加载、结构连通），**挂掉就把总分封在 0.15**。

**为什么现在值得做。**

三个理由，按重要性排：

1. **它是本季度第一个把 agent 放进「有物理后果」的工程任务里、并且能自动打分的东西。**
   之前 09-15 那期写的 LLMs Robot Arena 是同一方向的浏览器擂台，但**那是表演赛**
   （1560 局、置信区间大面积重叠）；RLE-Bench 有隐藏 seed、私有评分、确定性重放和 gate。
2. **task07 / task08 / task09 纯 CPU。** 这意味着**门槛不是显卡，是 Docker 和耐心** ——
   对只有一张 16 G 卡（甚至没有卡）的个人来说，这是本期唯一一个「今晚就能开跑」的国外项目。
3. **RLE-Bench 2.0 正在公开征集任务**，明码写着**共同作者署名**和**高影响力贡献的现金奖励**
   —— 详见下面比赛一节，这是本期新发现的入口。

**个人怎么分步切进去。**

**Step 0 —— 先避开 README 的第一个坑。** README 里的安装命令写的是

### 3 · HuRo —— 把第一人称人类视频里的手臂抹掉、换上机器人，直接产出 LeRobot 数据集

**是什么。** CoRL 2026，**Apache-2.0**，9 月 12 日建仓，23 星，本周涨得最快的一个具身仓。
它做的事情一句话说完：**把 egocentric 人类视频转成机器人对齐的观测和动作轨迹**，
用来做 VLA 预训练。手部动作重定向成机器人关节轨迹，**把画面里的人手臂抠掉、把机器人渲染进去**，
源数据没提供的中间信号（相机几何、手姿、语言）**全部自己估**，所以不同标注水平的视频能统一成同一种格式。

作者用这条流水线造了 **HuRo 数据集：约 63 万条机器人化 episode、1.42 亿帧，来自五个人类视频源**。
效果数字：预训练规模上去之后，微调后的整体完成率 **51.5% → 80.3%**，
空间和视觉分布外的完成率 **34.9% → 72.2%**。

**这次放出来的是流水线，不是数据**（数据页还挂着 "Data coming soon"）。
十个阶段，`./run_pipeline.sh` 一把梭，**全部可断点续跑**，
输出依次是 `_intr` / `_contact` / `_contact_refined` / `_hand` / `_extr` / `_chunked` / `_lerobot`。
最后那个就是 **LeRobot V2.0 数据集**。

**怎么切进去。** 这是本期**唯一一条「没有机器人也能产出训练数据」的路**：

1. 拍或找 egocentric 视频 —— **30 fps、短边 256 px、时长 30 秒到 30 分钟**。README 给了现成的转换命令：
   ```bash
   ffmpeg -i raw.mp4 -vf "fps=30,scale='if(gt(iw,ih),-2,256)':'if(gt(iw,ih),256,-2)'" \
       -c:v libx264 -crf 18 -an clips/raw_30fps_256.mp4
   ```
   鱼眼和常规镜头都收，不用先去畸变。
2. 仓里 `examples/clips/` 自带两段**已经满足要求**的样例，**改都不用改就能跑**。
3. 想换机器人：`--robot_name`，默认 `allex`（`configs/allex.yaml`）。README 说加新机器人
   「基本上是配置工作」。

**坑。**

- ⚠️ **要 ≥24 GB 显存 + 支持 CUDA 12.8 的驱动，机器人叠加那一步还要 RT core。**
  **A4000 16 G 跑不动**，这是硬门槛。租一张 4090（约 ¥2–4/小时）跑两段样例验证流程，
  量级是**几十块钱**的事；批量处理才是真花钱的地方。
- **放出的代码不读源数据集自带的标注**，全部从视频自己估。想从第 N 阶段接入已有标注，
  你得自己按 `examples/README.md` 的格式把第 N-1 阶段的输出**连同 `.done` 标记**一起写出来 ——
  **没有标记的话，阶段可能把这个 clip 当成已丢弃**。
- **标定失败的 clip 是静默丢弃的**：不报错，唯一的记录是一个空的 `<clips>_intr/<clip>.json`。
  批量跑的时候记得统计空文件数，否则你不知道自己丢了多少。
- 只配了 allex 一个机器人；数据集尚未放出。

### 🌍 国外 · SignalEngine/3d-printing —— 七道门，其中一道算钱，一道用 OCR 读模型上的字

**是什么。** 一个人的 **Bambu Lab A1 工作区仓库**（master 分支，9 月 13 日建，0 星，
**没有 README 也没有 LICENSE**）。它有意思的地方不在项目本身，在
`skills/model-forge/` 这个 agent skill：**一套七道门的交付纪律，每道门都是一个真能跑的脚本**。

| 脚本 | 门 | 它到底检查什么 |
|---|---|---|
| `verify_model.py` | 硬检查 | 水密、绕向、体数、构建体积（256³）、体积、悬垂比例、床面接触、薄壁（面积加权采样）、质量估算。**还会 WARN「需要支撑」**：某层有 >50 mm² 的悬空（超过 50° 自支撑角），或 >2 mm² 的空中孤岛 |
| `render.sh` | 目视 | Xvfb 下用 f3d 真渲染出 iso/front/top/section 四张图，**然后必须用看图工具看** |
| `features.py` | 孔位 | 直接从 BREP（要 STEP）列出每个孔的直径、深度、轴向、在哪个面，`--expect holes.json` 可硬失败 |
| `fit.py` | 配合 | 两个零件之间的间隙 / 干涉 / 接触面积，固定 RNG 种子，**顶点并稠密表面采样**，所以棱边接触也读得出真实近零间隙 |
| `slice_gate.py` | 切片 + **报价** | **OrcaSlicer 无头真切**（A1、0.4 喷嘴、0.20 mm Standard、Bambu PLA Basic），报打印小时数、耗料克数与钱、机时费、**成本下限**，给 `--price` 还算**每机时毛利** |
| `text_check.py` | **文字** | 把网格切片，**逐切片、逐旋转、逐镜像做 OCR**，验证模型上的凸起文字真的读得出来 |
| `run_gates.sh` | 汇总 | 全部串起来，`ALL_GATES_OK` 才算过 |

**这期真正的新东西是两条：**

**(1) 成本第一次被写进了自动化的门。** `slice_gate.py` 在切片成功后固定打印一个成本块：
`print hours` / `material`（克 + 英镑）/ `machine`（英镑）/ `cost floor`（英镑），
给了 `--price` 还会算 `margin per printer-hour`。
只有在你传了 `--max-hours` / `--max-grams` / `--min-gbp-per-hour` 并且超标时才 `QUOTE FAIL` 退 1，
**不传就是纯信息，不影响 PASS**。`GATES.md` 里留了逐条证据：
奖杯件 `--max-hours 6` 时报 `print hours: 15.25` → FAIL；旋钮件 `--price 5` 时每机时 £13.50 → PASS。

**(2) OCR 文字门是我在这条链路上第一次见到有人做。** 作者在 `SKILL.md` 里写了这条规则的来历：
**「永远不要从 iso 视图判断文字」—— 2026-09-13 一次真实评审就被 iso 渲染图误导过**（那次文字其实是对的）。
负样例也做了：HELLO 板子 `--expect WORLD` → FAIL；HELLO 和 WORLD 挤在同一位置 → OCR 读不出 → FAIL。

`GATES.md` 更值得读的是**它的写法**：每条门都有 `CHECK` / `EXPECT` / `EVIDENCE`，
而且 EVIDENCE 里明确记了**实现前是 RED（退 2 `unknown gate`）、实现后是 GREEN**。
这就是仓里那句「门必须可证明能过、也可证明能挂 —— 两个方向都验过才可信」的落地。

**个人怎么切进去。**

1. **只抄 `slice_gate.py` 的报价块。** 你已经在用任何 text-to-CAD 流程的话，
   把「打印小时数 + 克数 + 成本下限」变成交付里的固定一行，**成本几乎为零，信息量很大**。
   OrcaSlicer 的无头装法 SKILL.md 里给了完整命令（下 AppImage → `--appimage-extract` →
   补 `libglu1-mesa`、`libwebkit2gtk-4.1-0`）。
2. **抄 `text_check.py` 的思路。** 任何带姓名、编号、logo 的件，交付前 OCR 验一遍。
3. **抄 `GATES.md` 的格式**，哪怕你手写门：`CHECK` / `EXPECT` / `EVIDENCE`，
   并且要求 EVIDENCE 里有「实现前是红的」这句。

**成本（含 API token）。** 这套流程里**花钱的只有 agent 本身**，
所有门（切片、渲染、OCR、BREP 分析）都是本地确定性脚本，**0 token**。
跑一个中等复杂度的件，按「一轮提问 + 建模 + 7 道门 + 1–2 次修正」估，
输入约 5–15 万 token、输出约 1–3 万 token（渲染图会显著推高输入），
按官方价目表 Sonnet 5（$3/$15）约 **$0.3–0.8 一个件**，Opus 5（$5/$25）约 **$0.8–2.0**。
**这是量级估算，不是账单**；缓存命中与否能差好几倍。
有意思的是：**作者自己也在仓里算这笔账** —— 他默认用订阅制的驱动（边际 0），
把按 token 计费的那条当溢出阀，并写了一句值得抄走的话：
**「每 token 便宜不等于每结果便宜」**（一个 $0.07/M 的模型在一个它最终没做出来的任务上，
烧掉的钱超过了当天全部高级用量）。

**坑。**

- ⚠️ **没有 LICENSE，也没有 README。** 这是别人的个人工作区，不是产品。
  **抄思路和脚本逻辑可以，整仓拿来用之前得问作者。**
- **脚本里的路径是作者服务器上的绝对路径**（`/root/3d-printing/.venv` 这类），照抄会全断，要自己改。
- **`verify_model.py` 默认 `--bodies 1` 会误杀多色件**（嵌进主体的字/logo 是独立壳），要手动传实际壳数。

### 🇨🇳 国内 · 3Dpriting-detect-agent —— 打印完之后那一步：YOLO 找缺陷、SAM 抠出来、本地 3B 模型出中文诊断

**是什么。** 9 月 11 日建仓、14 日还在推的**离线 3D 打印缺陷检测与诊断 agent**，**AGPL-3.0**。
作者在仓库描述里就把话说死了：**「目前项目只是一种方法尝试，性能尚不足以满足工业需求」** ——
这种自曝在本系列里一贯是加分项。

技术栈全是本地的：

- **LangGraph** 编排确定性流程（**不是让模型自己决定调哪个工具**）
- **自训练的 Ultralytics YOLO26 OBB 权重**（`models/yolo/yolo_best.pt`，**仓里直接带着**）找缺陷
- **SAM 2.1 Base+** 按检测框出掩码，或在视频里跟踪缺陷
- **BGE + BM25 + Qdrant** 三路检索本地 3D 打印知识库（**Qdrant 集合和 BM25 词表都在仓里**）
- **Qwen2.5-3B-Instruct** 生成最终中文诊断

**这个设计里最值得学的一句话，写在 README 第二段：**

> 「Qwen 不负责猜测应该调用哪个视觉工具。媒体类型、图片/视频路由、失败处理和结果视频开关**均由程序确定**。」

这正是本系列反复强调的那条线：**模型负责语言，程序负责判定。**
另一个细节也做对了：视频里的 `defect_count` 是**经过时序确认的缺陷事件数**，
不是逐帧检测框的简单累加；完整逐帧结果落在 `yolo_defect_events.json`，
LangGraph 状态里只存可 JSON 序列化的摘要和路径。

**个人怎么切进去。**

1. **`python download_models.py --dry-run` 先看下载计划**（会显示每个模型的官方许可证链接），
   再 `python download_models.py qwen bge` / `sam` 分批下。YOLO 权重不用下，仓里有。
2. **先跑图片那条路**（比视频便宜得多），用 `dataset/image/` 里的 Kaggle 样图。
3. 环境：作者验证过的是 **Python 3.12.11 + torch 2.10.0+cu128 + torchvision 0.25.0+cu128**，
   依赖版本全部钉死（langgraph 1.2.11、transformers 5.9.0、ultralytics 8.4.7、qdrant-client 1.19.0…）。
4. 想要自己的效果，**换掉那份 YOLO 权重**：用你自己打印失败的照片标一批 OBB 重训。
   这是这个仓最自然的二次开发点，也是作者说「性能不够」的直接原因。

**成本（含 API token）。** **token 费 0** —— 整条链路全本地，README 明说「代码不会在推理时联网」。
显存这边：Qwen2.5-3B（约 6–7 GB bf16）+ SAM 2.1 Base+ + YOLO + BGE 同时驻留，
**16 G 卡够用但不宽裕**，跑视频时要注意峰值。
真正的成本是**标注时间**：想让它在你自己的打印机上有用，得标几百张自己的失败件。

**坑。**

- ⚠️ **Qwen2.5-3B-Instruct 用的是 Qwen Research License，只允许非商用研究或评估。**
  项目自己是 AGPL-3.0，**AGPL + 研究许可权重的组合，商用基本堵死**。README 自己点出了这条。
- **`dataset/image/` 来自 Kaggle**，只作示例，许可注意事项在 `dataset/README.md`。
- **ultralytics 8.4.7 的包元数据在部分平台声明 `torch<2.10`**，和验证环境的 2.10 冲突。
  作者明确写了：**不建议用 `--no-deps` 硬绕**，应该挑一个同时满足两边的 torch/torchvision 组合再完整冒烟。
- 包名是 `langGraph`（大小写不规范），入口是 `python -m langGraph.agent`。
- 0 星、单人、方法验证阶段 —— 别指望拿来直接上产线，这一点作者比谁都清楚。

### 📌 专题分析：这周这条链路上真正变了的东西（4 点）

**1. 成本第一次变成了自动化的门，而不是事后的备注。**
前面几期的门都在问「这个件对不对」（水密、孔位、应力、配合）。
`slice_gate.py` 问的是**「这个件值不值」** —— 打印小时数、克数、成本下限、每机时毛利，
超了 `--max-hours` 就退 1。这是这条链路从「能做出来」往「做得起」迈的一步，
而且实现方式非常朴素：**真切一遍，读切片器的数字**。
对个人的含义：你手上任何一个 text-to-CAD 流程，**今天就能加这一行**。

**2. 「模型不决定调什么工具」正在成为这条链路的共识写法。**
国内那条把它写进了 README 第二段（路由、失败处理、开关全由程序定），
国外那条把它写成了 `GATES.md` 的红绿证据格式，
再往前数，09-11 的 dsh-print3d（6 个确定性工具 + 5 个知识包）、
09-14 的 flex-fab-agent（CP-SAT 求最优、agent 只负责对话和审批）也是同一件事。
**四个互不相识的作者收敛到了同一个架构：LLM 管语言和解释，确定性程序管判定和执行。**
这条链路上凡是反过来做的（让模型自由决定调用哪个几何工具），到现在没见到一个跑得稳的。

**3. 「打印前的门」和「打印后的诊断」这周第一次同时出现，但两边还没接上。**
理想的闭环应该是：`verify_model.py` 说「需要支撑」→ 切片时开树状支撑 →
打印完 YOLO 在照片里发现拉丝和翘边 → **把这个结果反馈回几何或切片参数**。
现在这个箭头是断的：国外那条不知道打完什么样，国内那条不知道这个件当初是怎么设计的。
**谁把它接上，谁就做出了这条链路上第一个真正的自修复回路** —— 这是本期最值得抢的一个坑，
而且两边都是开源的，不需要征得谁的同意。

**4. 一个反直觉的数据点：这条链路上最好的两个仓，这周都是 0 星。**
SignalEngine（0 星，没有 README 没有 LICENSE）和 3Dpriting-detect-agent（0 星，自曝不够工业级）。
**同期星数最高的 3D 打印相关仓是模型管理器和网站**。
这和 09-15 趋势里那条「低星 + 自曝边界 > 高星 + 全是绿勾」是同一个现象的又一次出现。
筛这条链路的仓，**看有没有 `GATES.md` 这种东西，比看星数准得多**。

## 📈 趋势观察

**1. 「agent 做机器人工程」这周从表演赛升级成了资格考试。**
09-15 写的 LLMs Robot Arena 是浏览器擂台（1560 局表演赛、置信区间大面积重叠、连 LICENSE 都没有），
本期的 RLE-Bench 是九个任务族、容器化、隐藏 seed、私有评分、确定性重放、gate 封顶，MIT 许可。
**一周之内，同一个问题的评测严谨度跨了一个数量级。**
更关键的是任务的选法：它没有只挑「控制机器人」，而是把**搭工具（task02）、设计本体（task08）、
协同设计遥操作硬件（task09）** 都算成了机器人学习工程师的活。
task02 的评分方式尤其漂亮 —— **你造的工具好不好，由另一个全新的 agent 拿去解一个没见过的任务来决定**。
这个指标很难刷。

**2. 单卡个人和这一轮前沿工作的距离，这周变得可量化了，而且不小。**
本期六条主线里，**明确写了显存或算力门槛的有三条**：
HuRo 要 ≥24 GB + RT core（A4000 16 G 出局）、
RLE-Bench 的 task04/task05 参考预算是 RTX 5090 / H100、
JEPLO 的 4096 envs 在 16 G 上要砍。
**但同一周也给出了三条绕过去的路**：RLE-Bench 的 task07/task08/task09 纯 CPU、
PhysBrain 1.5 放了 2B、JEPLO 带了预训练策略可以只做 sim-to-sim。
**结论对个人很实在：不要挑「训练」类任务，挑「设计 / 评测 / 工程」类任务** ——
后者这周的供给突然变多了，而且门槛是 Docker 不是显卡。

**3. 无 LICENSE 仍然是这个领域最普遍的一个硬伤，本期六条里占了三条。**
PhysBrainEvalKit（21 星）、JEPLO（12 星）、x-wbc（4 星，明说「未来代码和权重的许可尚未确定」）
都没有许可文件；加上专题的 SignalEngine，本期八条里四条没许可。
反过来看，**给出许可的那几条都很清楚**：RLE-Bench MIT、HuRo Apache-2.0、
nanshanbot/hand MIT、3Dpriting-detect-agent AGPL-3.0、OptiDuck 软硬分开（Apache-2.0 / CC-BY-NC-SA）。
**「提一个加 LICENSE 的 issue」仍然是这个领域投入产出比最高的贡献**，
本期下面的口子清单里又有三条是这个。

**4. 具身 VLM 开始有「统一尺子」的雏形，而且尺子是中文团队做的。**
PhysBrainEvalKit 把 28 个 benchmark 的输入协议、prompt、指标口径钉死，

**没有写金额，也没有写截止日期** —— 这两点我没核到，动手前请自己发邮件问）。

**为什么它对个人特别合适：你不需要 clone RLE-Bench，也不需要先提案。**
官方提供一个 **任务创作 ZIP 模板**（Harbor 模板，含可运行示例、作者指南、提交清单、本地检查），
解压后从 `AUTHOR_GUIDE.md` 开始，**可以当成一个独立的 Harbor 任务开发完再交**。

要交的东西（页面逐项列了）：

| 文件 | 内容 |
|---|---|
| `SUBMISSION.md` | 任务摘要、评分理由、资源需求、验证证据 |
| `task/instruction.md` | 给 agent 的简报：目标、输入、输出路径与格式、约束、**公开的评分契约** |
| `task/task.toml` | 任务身份与版本、产物交接、超时、agent 与 verifier 的资源 |
| `task/environment/` | agent 镜像的 Dockerfile、工具、公开资产（**只放 agent 可以看的**） |
| `task/tests/` | **独立的 verifier 镜像**、私有 harness、评分入口 |
| `task/solution/` | 可选的参考解（Oracle 运行用）；不给就要有其他可复现的可解性证据 |
| `author_checks/` | 给评分器的本地回归检查，**放在运行时镜像之外** |

本地验证环境：**Python 3.12 + Docker + Harbor 0.21.0**。
示例任务的预期 reward 是 **Oracle: 1.0 / Nop: 0.0**，
页面特意提醒：**命令跑完不等于结果有效，要去看 `result.json` 和 `verifier/reward.json`**。

你需要给出四类证据：**可解性**（参考解在声明的资源限额下的成绩）、
**评分正确性**（独立的指标检查、边界情况、同一产物重复评测）、
**健壮性**（缺失/畸形输出，以及针对指标的绕过尝试）、
**隔离性**（私有评测资产和参考解对普通 agent 不可见）。

**务实的判断**：这是个**几天到两周**量级的活，不是一晚上。
但它是本期唯一一个「有现金 + 有署名 + 对个人开放 + 不要求机构身份」的入口，
而且**你日常做机器人工程时踩的坑，本身就是素材**。
