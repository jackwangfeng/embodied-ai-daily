1️⃣ 【深度】Qi-hub-dot/microduck-locomotion-diagnosis —— 把一个 2164★ 项目里没人回答的 issue 复现、定位、修好

是什么。 microduck_rl 是 Pollen Robotics 给 Microduck （25 cm、约 800 g、14 个 Dynamixel XL330 的小双足）开源的训练代码，MuJoCo-Warp 做 GPU 物理、PPO 训到 50 Hz 再导 ONNX 上真机。 仓库里有个开放 issue #46：走路任务训不出来。 报告人用 4 张 L4 跑了七组对照实验，结论是策略收敛到原地站着、脚从不离地，这个 issue 至今没有回复。

这个仓库是一个人把它从头做完的完整记录：在 Windows 上跑通 → 复现失败 → 拆奖励定位原因 → 改掉 → 再测 → 最后发现项目自己的评估指标有系统性偏差。四件事每件都有落盘证据和源码行号。

为什么现在值得做。 这是个人参与开源具身项目性价比最高的那种姿势：不需要自己定义问题（issue 已经写好了）、 不需要硬件（纯仿真）、不需要说服谁（issue 摆在那里没人管），产出终点非常硬 —— 一条能被 maintainer 验证的 PR 或 issue 回复。

而且它给出的三条结论本身就有迁移价值，任何人调 legged locomotion 的奖励都会撞上：

  1. air_time 奖励的门控问题。 它的权重 3.0 是所有正项里最大的，但门控只比较有没有指令， 不问实际有没有前进 —— 被命令前进却原地踏步的策略照样拿满这份奖励（microduck 把 command_threshold 设成了 0.01）。改成按「实际水平速度达到指令 30%」门控后， error_vel_xy 从 0.43 降到 0.35。 注意作者这里和报告人的现象还不一样：报告人测到 air_time ≈ 0.002（脚从不离地）， 作者复现出的是 0.9997（脚一直在抬但不前进） —— 卡的位置不同，是一个更具体的漏洞。
  2. 前向 / 侧向误差等权是错的。 单独写脚本测「它到底走不走」：固定前进指令跑 20 秒， 路径走了 7–9.5 米、一千步只摔一次、轨迹平滑 —— 它会走，只是横着滑走。 逐步读身体系速度：恒定指令 (+0.30, 0.00) 下第 7 步前向 +0.112、侧向 −0.230，侧漂到了前向的两倍。 把侧向误差乘 3 倍、跟踪项权重 2.0 → 4.0，同一第 7 步侧漂降到 −0.044（五分之一），前向几乎没变， error_vel_xy 从 0.35 降到 0.21。
  3. 那个指标本身会高估误差约三倍。 把测量从 8 步延到 400 步看稳态：前向速度稳定在 0.23–0.27 （指令 0.30，跟踪率 77–90%），侧向在 ±0.06 内，逐帧稳态误差 0.07，而同一时刻日志里的 error_vel_xy 是 0.206。看实现就明白了 —— 它把五类指令模式（站住 / 只控朝向 / 世界系 / 只控前向 / 普通）的误差混在一起，还做整回合累积平均，把起步加速段（误差 0.30）和踉跄（0.17–0.24）都算进去。 盯着这一个数字，没法判断策略会不会走，这也解释了报告人为什么查不出是哪类环境在失败。

坑与风险。

  1. 仓库没有 LICENSE。 作者自己的分析文字和脚本默认保留所有权利，想引用或二次分发先开 issue 问。 上游 microduck_rl 的许可另算，提 PR 时以上游为准。
  2. 作者的环境是 Windows + RTX 4070。 上面第 2 步的 10 小时是他的口径，本机要按 ×2–2.5 折算。 4096 并行环境在 A4000 16G 上要先确认显存够 —— MuJoCo-Warp 的显存占用随环境数近似线性， 跑不起来就先降到 2048 并在结论里注明（并行数会影响 PPO 的样本效率，不要拿不同并行数的曲线直接对比）。
  3. 修复本身是有范围的，别过度宣称。 作者自己写明：air_time 的门控用的是「线性范数 + 角速度绝对值」， 所以被命令原地转身的环境也通过门控 —— 但转身时原地踏步本来就对，不算漏洞。 真正的漏洞只在「被命令前进却原地踏步」这一类。往 issue 里写的时候照抄这个范围说明。
  4. 接相机的三个坑他已经踩过了（深度图 (B,1,H,W) 不能和向量观测放同一扁平组，要单独成组 + concatenate_dim=0； 默认 obs_groups 不含 camera，不显式挂 CNN 会报 No 2D observations are provided； 平铺 MLP 处理不了 1024 维图像，要换 SpatialSoftmaxCNNModel 配 cnn_cfg）。做第 5 步直接抄，别重走。

2️⃣ DeRuiChen258/ACT-so101 —— ACT 全流程复现，TorchScript 导出到 C++ 新进程重载，12.69 ms

  • 是什么：SO-101 上的 LeRobot ACT 实验台，四段闭合：数据集审计 → CUDA 训练 → TorchScript 导出 → C++（LibTorch）在独立新进程里重新加载并前向，最后用 MuJoCo Menagerie 的 SO-ARM100 把真实抓取回放出来。 上游编排是一个 C++17 CLI（actlab），Python 只出现在数据集扫描、导出、离线评测、可视化这几个点。
  • 数字（全部实测、逐条有落盘证据）：训练 3000 步 loss 13.628 → 0.716，27 samples/s，峰值显存 3.69 GB，15.3 分钟； TorchScript 与官方 pipeline max_abs_diff = 0.0（freeze+reload 相对差 3.59e-4）； C++ 推理 mean 12.69 ms / p95 14.05 ms（warmup 5 + 30 次），C++ vs Python 最大绝对差 0.0445； 专家 vs 预测末端 MAE 0.1206 m；物理抓取在 1.00×/1.05×/1.10×/1.20× 四档尺寸下全部 HELD。
  • 本机口径：他的卡是 RTX 5070 Laptop（sm_120），模型只有 51.6 M 参数、峰值显存 3.69 GB —— A4000 16G 跑训练绰绰有余，折算约 30–40 分钟跑完 3000 步。推理侧折算约 25–32 ms， 仍然远高于 SO-101 的控制需求。这是本期最容易在本机一天内完整复现的一条。
  • 最该抄走的一条：infer_act 这个跨进程重载硬门禁。很多人的 checkpoint 只在训练脚本的 Python 进程里能跑， 一换进程就废；把「独立进程加载 .pt 并前向」做成流水线里的一道 PASS/FAIL，是部署前最便宜的一次体检。
  • 坑：① README 自己顶着一行免责：本项目未接真机、未接仿真环境，仿真成功率 / 真机成功率一律 NOT_MEASURED， 离线动作误差不等于任务成功率 —— 引用时别把 MAE 当成功率； ② LibTorch 是 2.12.0+cu132、训练侧是 torch 2.11.0+cu130，跨版本加载他实测通过，但换你自己的组合要重验； ③ 数据集路径写死在 configs/paths.yaml 里的作者目录，改自己的再跑。

3️⃣ N-B-Studio/5010-3DOF-Foc-kinematic-chain —— 三个 5010 云台电机做成的 FOC 三关节链，MIT，STEP 齐

  • 是什么：一条可复用的三关节串联 FOC 平台，既能当腿（髋 / 膝 / 踝），也能当 3-DOF 机械臂。 三个 5010 电机走 CAN 1 Mbps 分布式 FOC；主控 STM32H723 跑 1 kHz 外环 + 安全状态机 + UART 命令； 每个关节另配一颗独立的输出端编码器（AS5047P，挂在 STM32G030 编码器节点上），外加足底触点开关。
  • 为什么值得做：现在开源腿足几乎都直接上成品准直驱模组（RobStride / 宇树 / 本末），一条腿就四位数起。 这个仓库是少见的**「从航模云台电机自己搭一条带输出端编码器的关节链」的完整路径： 固件、IK、URDF、RViz、STEP 装配体都在，而且把安全做成了显式命令** （CLEAR / ZERO / POWER ON / ARM / DISARM / POWER OFF，加关节空间 PD 的力矩上限和看门狗）。 输出端编码器这件事尤其值钱 —— 只有电机端编码器的自制关节，减速齿隙和形变是看不见的， 做力控 / 落地检测时会被这段未知量直接拖死。
  • 个人怎么切进去：① 先只做一个关节：一颗 5010 + 一块 FOC 驱动板 + 一颗 AS5047P， 把「电机端 vs 输出端」的角度差扫出来，这张图本身就是能发出去的结果； ② 再照 STEP 打印连杆串成三关节，跑仓库里的 Python IK 轨迹，用 RViz 看 JointState； ③ 想更进一步：它的 1 kHz 外环 + CAN 是现成的底座，把上层换成本机上跑的策略即可。
  • 成本估算（未实测，按国内电商常见价推）：5010 云台电机 3× ≈ ¥300–450、FOC 驱动板 3× ≈ ¥300–600、 STM32H723 核心板 ≈ ¥100–180、STM32G030 + AS5047P 3× ≈ ¥150、CAN 收发器 / 线材 / 电源 ≈ ¥200、 打印件 ≈ ¥100 —— 整条链大致 ¥1200–2200，单关节起步约 ¥300–500，在预算内。
  • 坑：① README 里 YouTube 是 TODO，演示只有 B 站那一条，下手前先看完； ② 驱动板型号 README 没写死（只说「CAN FOC 驱动器」），选板要自己确认协议和 1 Mbps 波特率； ③ 5010 是航模云台电机，持续力矩很小，拿它当腿只能做轻质验证平台，别指望承重； ④ 安全命令齐全不等于安全 —— 1 kHz 外环 + 力矩上限第一次上电务必先 DISARM 状态空跑一遍。

是什么。 一台还没造出来的开源人形：1.40 m、购入质量 33 kg（成品估 45 kg）、30 个自由度 （腿 6+6、臂 7+7、腰 2、颈 2），结构全部 3D 打印（PA-CF / PPA-CF，Bambu Lab H2C，0.4 喷嘴）， 全身 RobStride 准直驱，Jetson AGX Thor 做算力，5 路 CAN @ 1 Mbps，运动学参考 Unitree G1。 作者的原话是「还在设计阶段，没造出来，现在放出来就是为了一起造」。 仓库里 BOM（xlsx，每行有供应商、链接、质量、备注）、电气方案、可打印 STL、URDF、Isaac Lab 仿真、 设计笔记，以及一份给 AI 接手用的 AGENTS.md，全在。

为什么现在值得做。 开源人形有两类：一类是权重和策略开源、本体买不到；另一类是本体图纸开源、但只给你一个完工的 zip， 你看不到任何设计决策过程。primo 是罕见的第三类 —— 它把尚未定稿的分歧也写出来了。 比如脚踝：两个电机装在小腿里、两根推杆、偏置万向节，pitch 是两者之和、roll 是两者之差； 再比如髋偏航电机，CAD 里装的是 RS06、BOM 里写的是 RS03，作者明说「下腿单之前由仿真决定」。 这种「还没决定、等人来算」的口子，就是个人能真正插进去的地方 —— 不需要你有这台机器人， 你只需要在 Isaac Lab 里用他的 URDF 把这个选型问题跑出一个答案。

2️⃣ j1s4nn/wmdrift —— 给自回归视频世界模型补一套「说得出数字」的失效诊断，纯 CPU 能跑

  • 是什么：喂一段 rollout 视频 + 模型当时被 condition 的相机轨迹，它量四件事： 相机漂移、时序抖动、记忆衰减、画质衰退，输出 report.md + metrics.csv + per_frame.csv + 四张 PNG。 仅推理，CPU 可跑，只有 LPIPS 和可选的 CLIP 对齐会用 GPU。
  • 它从哪来（这点最值得看）：作者在读 minWM， 发现那个项目的 debug skill 只用文字描述长程失效（相机偏离指令路径、帧抖、忘掉去过的地方、画质衰减）， issue #11 讨论长程训练、#18 讨论相机平移尺度歧义， 但没有一处把这些失效量成可跨 run 对比的数字。于是他自己写了那个「我想要的工具」。 —— 这和本期国内那条 microduck 诊断是同一种打法：上游把问题描述清楚了但没量化，个人补上那把尺。
  • 怎么上手：仓库自带四段合成视频（scripts/make_fixtures.py 渲的，带真值位姿）， python -m wmdrift analyze tests/fixtures/synthetic_pan.mp4 --pose "w*30" --output reports/pan 一条命令就有报告，不需要你先有一个世界模型。另有 batch 和 compare 两个子命令做跨 run 对比。
  • 个人切入点：① 拿本期专题二那条 lingbot 的输出视频喂进去，量一下「加速前后画质是不是真的无损」 —— 它自己报的是 PSNR/SSIM/LPIPS，wmdrift 量的是另一组维度（漂移 / 抖动 / 记忆），两边能互相打靶； ② 把它做成 minWM 的 CI 检查项提上去。
  • 坑：① 作者的测试环境是 Windows + torch 2.14(cu126) + opencv 4.11，Linux 没测； ② 四个指标都是相对指标，跨模型比要固定同一条相机轨迹，否则数字没有可比性； ③ 合成视频只有四段，真实 rollout 上的指标分布是未知的，别拿 fixture 上的阈值当通用门限。

1️⃣ 🌍 mattz1337/gridfinity-designer —— 把「东西怎么拿得出来」设计进凹槽里，而不是事后补一个指甲槽

  • 是什么：一个 Codex skill，配一台外接的 FreeCAD MCP server， 从照片 / 实测尺寸 / 已有 CAD 出发，生成合身的 Gridfinity 收纳件。 流程是：确定朝向与形状 → 把实测值、估算值、原型假设三类数字严格分开 → 设计取出方式 → 出带尺寸的排布图供确认 → 实现 → 产出 FreeCAD 原生文件、STEP/STL、预览图和一份诚实的校核报告。
  • 它真正新的地方：把「取出性」当成一等设计目标。多数 text-to-CAD 的收纳件做出来是个精确的坑， 东西塞进去就抠不出来。这个 skill 把取出方式列进设计变量：手指凹槽、露出高度、可拆插件、 press-to-lift（按住后端、笔的带帽端翘起来）—— 仓库里那段真打印的演示 GIF/视频就是这个机构， 用户自己录的 1×3 收纳件。它还照顾了 Gridfinity 的底脚、堆叠唇、高度约定和局部地板厚度。
  • 个人怎么切进去：① 没有 FreeCAD MCP 也能用 —— skill 会退化成「只出测量、规格和图纸， 并明确报告没有生成 CAD」，先用这一档验证它的测量引导问得对不对； ② 接上 FreeCAD MCP 跑一个你桌上真有的东西（笔、卡尺、电烙铁头），打出来试配； ③ 迁移到具身场景：把「取出性」换成「装配可达性」—— 灵巧手指节的固定座、腕部相机支架， 同样是「装得进去还要拆得出来」的问题，这套把实测 / 估算 / 假设分开记的做法可以直接搬。
  • 成本（含 API token 费，这条链路的主要开销）：FreeCAD 和 MCP server 本身不花钱， 花钱的是 agent 的来回。一个件的完整会话（测量引导 + 方案 + CAD 往返 + 校核报告） 估算 15–40 轮工具调用：用 Opus 级模型大致 $1–4 / 件，用便宜档模型大致 $0.2–0.6 / 件， 打印耗材几毛到几块。反复试配才是成本大头 —— 所以它专门做了「不改被测尺寸的前提下减料出首版试配件」， 这一条是实打实省钱的。（此为估算，作者没公布 token 统计。）
  • 坑：① README 自己写明：不安装 FreeCAD、不自带 MCP server、不保证照片能算出物理合身； ② 它假设 Codex 的本地 skill 支持，用别的 harness 要自己搬 skills/gridfinity-designer/SKILL.md； ③ MCP 实现差异大，skill 是发现可用工具而不是假定 schema —— 换 server 要重验一遍工具覆盖； ④ 远端 MCP server 还需要一个可达的输出落盘位置。

📌 专题分析

  1. 这周这条链路上真正变的，是「证据」开始比「生成」值钱了。 gridfinity-designer 的核心卖点不是它能建模， 是它把实测值、估算值、原型假设三类数字分开记，并输出一份会承认自己没验证什么的报告。 连着看上期的 DATUM（错误尺寸保留上一版）、09-15 的 cadloop（结论稳健性分区）， 三期三个项目不约而同在做同一件事：给 agent 生成的几何配一条可追溯的来源链。 text-to-CAD 的竞争点已经从「能不能出 STEP」移到「出的这个 STEP 凭什么信」。
  2. 「可取出性」是 DfAM 里第一个被 agent 真正接住的软约束。 壁厚、悬垂角、最小特征这类硬规则早就能查， 但「东西塞进去能不能拿出来」以前只能靠人看。把它变成设计变量（凹槽 / 露出 / 插件 / press-to-lift） 并且有一段真打印视频作证，是这周唯一一个从「几何合法」走到「人能用」的例子。 具身侧完全同构的问题是装配可达性，还没人做。
  3. 回流那一段仍然是整条链最薄的。 这周能找到的「打印中状态」方案（bambu-monitor）本身不含任何 agent 成分， 它只是恰好提供了 agent 需要的东西。也就是说：建模侧一周好几个新项目，执行回流侧要靠拿非 agent 工具来拼。 这个缺口对个人是机会 —— 把 Moonraker/拓竹的状态流封成一个 MCP server，是当前这条链上最缺、也最好做的那块。
  4. 成本结构提醒：这条链的开销依然不在硬件，在 token。本期两条一个 $0.2–4/件、一个 $0， 差别就在「几何计算有没有交给确定性工具」。凡是让模型直接吐坐标的方案，成本和错误率会一起涨。

1️⃣ 🇨🇳 BUAA-CI-LAB/EmbodiInfer —— 北航做的「具身版 vLLM」，π0.5 一次前向从 74.33 ms 压到 38.89 ms

是什么。 一个同时服务推理和 RL rollout 的具身模型执行引擎。操作策略、世界-动作模型、循环式导航策略 走同一套 Python 接口，引擎负责批处理、会话状态、多卡分发，各模型只写自己的 adapter（加载 / 预处理 / 解码）。 配套还有一个 EmbodiRun：配一个模型、一个算力节点、一个机器人或仿真器， 整条闭环从一个文件里跑起来。两个仓库都是 2026-09-20 才推的。

为什么对「连续决策」关键。 它做的四件事恰好对应连续流的四个痛点： CUDA graph 重放 prefix 和 decode 路径（省内核启动）、 跨环境批处理（多个环境的观测攒一批、或者随环境推进滚动聚合）、 循环会话把导航策略的隐状态跟着观测走（显式 commit / reset / cancel）、 同一个引擎直接出 log-prob 供 RL refit。第三条尤其少见 —— 大多数推理框架假设每次请求无状态， 而连续感知的导航策略恰恰是有状态的。

1 rMuscle: Robotic Muscle Memory for Efficient VLA Model Inference
https://arxiv.org/abs/2609.19104		 抓住「同一工位重复执行」这件事：Context Cache 复用视觉 token 输出省计算、Action Cache 复用神经元激活模式省权重访存，4090 和 Jetson Thor 上 1.29–1.42× 提速且真机成功率不变（折算到 A4000 ≈ 同样倍率，但绝对延迟 ×2–2.5） ❌ 未见公开代码
2 VLA-ULAP: Interleaving Cloud VLA Calls with Ultra-Lightweight Local Action Prediction at the Edge
https://arxiv.org/abs/2609.18663		 云端大 VLA 和一个 7.4 M 参数本地预测器交替出手：Orin Nano 上 19.9 ms / 0.183 J，对比 GR00T 在 A6000 上 284.3 ms / 50.55 J；砍掉 48.8–76.7% 的云端调用还保住 95.0–97.5% 成功率，真机是 SO-101 ❌ 未见公开代码
3 Agile-WAM: An Agile Tactile World Action Model for Contact-Rich Robot Control
https://arxiv.org/abs/2609.20761		 传感器侧：视觉和触觉时间尺度本就不同（相邻视觉帧高度相似、触觉在接触瞬间突变），于是视觉 latent 监督放在更远的时间偏移、触觉只预测下一帧；五个真机任务成功率相对 +29.4%，推理延迟 11.9 ms ⚠️ 项目页标「Code coming soon」
4 ForceDelta-VLA: Distilling Force-Conditioned Action Corrections for Contact-Rich Manipulation
https://arxiv.org/abs/2609.18242		 传感器侧：把动作拆成「可复用参考动作 + 力驱动修正量」，用冻结教师的力条件 / 力无关两种模式配对蒸馏出修正目标；在两次参考动作更新之间就能响应接触变化，不用重生成整段动作块。九个任务 82.2% vs ForceVLA 54.4%，接触力峰值降约 26% ⚠️ 仅项目页仓库（无代码）
5 SkipVLA: Skipping VLA Steps with Classical Planning for Fast Robot Manipulation
https://arxiv.org/abs/2609.20648		 执行侧：自由空间交给经典运动规划器，只在抓 / 放这类接触密集的技能上查 VLA；复用冻结的视觉-语言骨干预测每段规划的目标位姿，不需要额外演示。三个 VLA × 13 个 LIBERO 任务 + 真机 6-DoF YAM 臂，最高 2.5× 更快且成功率持平 ❌ 未见公开代码
6 Technical Report: One-Step Drifting Action Heads for GR00T N1.7
https://arxiv.org/abs/2609.18108		 模型侧的负面结果，值得单独看：把 GR00T N1.7 的迭代扩散动作头换成一步 drifting 头，动作头前向 45.3 ms → 5.0 ms、骨干+头 70.0 → 30.6 ms，但成功率系统性下降（LIBERO-Spatial 64.0±4.0%、Goal 52.0±1.0%、Long 26.0±2.6%），三个种子方差都很小说明不是初始化问题。作者把它报成速度-成功率的权衡而非改进 ❌ drifting 头未开源；底座 GR00T N1.7 是开放的

📌 专题小结

  1. 这周的加速全部发生在「重复性」上，而不是「模型更小」上。 rMuscle 复用跨执行的内部状态、 EmbodiInfer 复用去噪步之间的中间结果和 CUDA graph、SkipVLA 复用经典规划器去跳过自由空间、 VLA-ULAP 复用一个 7.4 M 的本地头去跳过云端调用。四条路子不同，假设是同一个： 连续控制里绝大多数前向是在重复算已经算过的东西。这对个人是好消息 —— 这类优化不需要重训模型。
  2. 「一步生成」这条路本周被明确打了个问号。 One-Step Drifting 那份技术报告把速度提了 9 倍， 成功率却在 LIBERO-Long 掉到 26%，而且三个种子方差只有 2.6 个百分点。 它列的可疑因素里有一条特别值得记：同步的 LIBERO 评测根本不会走异步 overlap 那条路径 —— 也就是说，一步生成的收益要在异步执行下才可能兑现，用同步 benchmark 评它本身就低估了它。 凡是看到「一次前向省了多少毫秒」，先问评测是不是异步的。
  3. 触觉终于开始按自己的时间尺度进闭环了。 Agile-WAM 和 ForceDelta-VLA 是从两头逼近同一件事： 前者让触觉 latent 只预测下一帧、视觉 latent 预测更远（承认两种模态的采样节奏不同）， 后者让力修正在两次参考动作更新之间生效（承认动作块的时间粒度太粗）。 过去把触觉当成「多一路图像」塞进视觉编码器的做法，本周被这两篇同时绕开了。
  4. 一个不好的信号：本期六篇论文无一放出可跑代码。 对照本专题前两期（FlashVLA、StreamPI、edge-reflex、 Dexmal 三件套都是有仓库的），这周是纯论文周。所以主条目只能从工程仓库里选， 也是为什么两条都落在推理侧 —— 带硬数字又有代码的，这周只有推理侧那两个。
  5. 给本机的一条实操建议：EmbodiInfer 的 4090 数字折到 A4000 是 π0.5 ≈ 10–13 Hz、GR00T ≈ 13–16 Hz。 这个频率够做桌面操作，不够做动态任务。想再往上，本期给的两条现实路径是 量化（EmbodiInfer 自带 π0.5 / StreamVLN 的量化 benchmark）和 云边交替（VLA-ULAP 那套思路， 本地那颗 7.4 M 的头在 A4000 上是白送的算力）。 另外若要在执行侧补上连续目标流，ServoPy（MIT，PyPI 上直接装， NumPy 是唯一必需依赖，Panda 演示 100 Hz 伺服 / 500 Hz 物理，纯 CPU）是本周新出的现成件 —— 它把「新目标随时进来、下一个控制周期就用上」这件事做成了库。

📈 趋势观察

这周最值得记的一条：个人参与开源具身项目的姿势，正在从「造新东西」转向「给已有项目补一把尺」。 本期国内 top1（microduck 诊断）和国外第 2（wmdrift）是两个互不相干的人、在两个互不相干的项目上， 做了同一件事：上游把失效现象描述清楚了，但没有量化，于是个人写出那个缺失的测量工具。 microduck 那条更狠一步 —— 它量到最后发现上游自己的评估指标高估误差约三倍， 这解释了为什么 issue 报告人用七组对照实验也定位不到问题。 这种贡献不需要算力、不需要硬件、不需要你比 maintainer 聪明，只需要你真的把数字逐帧读一遍。 对只有一张 A4000 的个人来说，这是当前投入产出比最高的一类工作。

第二条：「诚实性披露」开始变成开源具身仓库的标配，而且是自发的。 本期 ACT-so101 在 README 顶部写「未接真机、成功率一律 NOT_MEASURED，离线动作误差不等于任务成功率」； microduck 那条主动标注自己修复的适用范围（只覆盖「被命令前进却原地踏步」，不含原地转身）； wmdrift 写明合成 fixture 上的阈值不能当通用门限；One-Step Drifting 把自己报成权衡而非改进； gridfinity-designer 把实测 / 估算 / 假设三类数字分列。 五个项目、三个国家、互不相识。对个人的直接影响是：现在往 README 里写一句「我没验证什么」， 比多贴一张 GIF 更能让人认真看你的仓库。
