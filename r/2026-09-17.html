🇨🇳 国内

★ TOP 1（深度）· vla_pi0 —— 把 π₀ 装到自己那台臂上，从遥操作采集一直写到真机部署，中间的坑一个没省

是什么

joykraft/vla_pi0（51 ★，2026-09-11 建，中文 + 英文双 README）是一份端到端的单臂 VLA 工程文档 + 可运行代码包： 基于 OpenPI（π₀）和 LeRobot，覆盖「主从臂遥操作采集 → LeRobot 数据集 → 字段适配与归一化统计 → π₀ LoRA 微调 → WebSocket 策略服务 → 真机闭环执行」整条链路，用的是 Episode1 单臂（恩培那套主从臂）。

仓里带一段 1 分 40 秒的原速实机视频（docs/media/demo.mp4），演示抽屉开关和红色方块抓放， 中间有人为干扰（反复把抽屉关上、把方块挪走），不是挑好的那一遍剪出来的。

为什么现在值得做

过去半年 VLA 的开源程度已经足够了：π₀ 基础权重在 gs://openpi-assets/checkpoints/pi0_base 公开， LeRobot 的采集/数据格式是事实标准，SmolVLA / π₀.₅ 的微调脚本到处都是。 真正拦住个人的不是模型，是那一堆「不会有人写在论文里」的对齐问题： 你用 lerobot.record 采出来的数据字段叫 observation.images.fixed， 而 openpi 的 LeRobotLiberoDataConfig 要的是 observation/image； 你采集时用角度、训练时用弧度，模型照样收敛，只是上机就抽； 你的动作已经是增量了，配置里又对前 6 维做了一次相对动作转换，于是差分了两遍。

这个仓最大的价值就是把这些逐条写出来了，而且写法是「当前配置是这样、你要改成那样、为什么」。 这是我在这个日报里见过的把 VLA 真机部署讲得最具体的中文文档之一。

坑

  1. 显存：默认 batch_size=32，A4000 16G 跑不动 π₀ LoRA。 作者的 weight_loader 路径写的是 /root/autodl-tmp/pi0_base/params——这是 AutoDL 的路径，说明作者自己也是租卡跑的。 实测口径我没有，但 π₀ LoRA 在 24G 卡上通常要把 batch 压到 4–8。 按 20000 步、租一张 4090 算，¥2–3/小时 × 10–20 小时 ≈ ¥50–200 一次。
  2. 微调权重没有公开下载。 README 原话：「微调权重目前没有公开下载链接，未来是否发布及发布地址待确定」。 所以这个仓是流程可复现，结果不可直接复现——你必须自己采数据、自己训。 如果你的目标是「跑通一个 demo 就行」，先去看 LeRobot 官方的 SmolVLA 教程，成本低得多。
  3. 根目录没有 LICENSE 文件。 lerobot/ 和 openpi/ 两个子目录各自带上游的 LICENSE（Apache-2.0）， 但作者自己写的适配代码（enpei_scripts/、robots/enpei_follower/、teleoperators/enpei_leader/） 处于无明示许可状态。要拿去做任何公开的事，先去提个 issue 问许可。
  4. robots/enpei_follower/episode_server.py 不是控制服务，是 TCP 客户端。 README 明说了「配套控制程序需要另行准备」，默认连 localhost:12345。 没有这台臂的配套控制程序，第 5 步是走不通的——别以为 clone 下来就能驱动任意机械臂。
  5. 两个端必须用独立 Python 环境：训练端 Python 3.11 + jax[cuda12]==0.5.3 + torch>=2.7， 机器人端 Python 3.10 + torch==2.6.0。装一起必挂。
  6. --fps=30 是控制目标频率，不代表模型推理能到 30 Hz。客户端把图缩到 224×224、开独立线程请求动作块， 真实推理频率取决于你那张卡和网络。

3 · sixdof-arm —— 自己画的臂不知道 DH 参数怎么办：写脚本从 STL 网格里把六根关节轴求出来

  • 是什么：315nailong/sixdof-arm（2 ★，09-08 建，09-11 推）。C++17 + Eigen，不依赖 ROS，不需要真机。 README 的开场白值得原样引用：「我在 SolidWorks 里画了台六轴臂，画完发现一个问题：我不知道它的运动学参数。 量产的 UR5 可以抄官方文档，我这台不行，参数只存在于我自己的装配图里。」

  • 它做了什么：Python 脚本读 STL，从网格里求出 6 根关节轴，转成标准 DH 参数； 然后补上解析逆解、笛卡尔直线插补，最后用 C++ 算出的关节角驱动 STL 模型做动画。 仓里 models/stl/ 直接放着那台臂的七个零件 STL（底座、大臂、小臂、法兰…），有 LICENSE，有 tests/。

  • 为什么值得看：它给了四个自校验数字，这在个人项目里很少见——

    检查 结果
    从 CAD 反推的 DH 与手工测量的偏差 0.014 mm
    200 组随机位姿正逆解往返误差 ~1e-16 m
    笛卡尔直线插补的到位偏差 1.2e-16 m
    C++ 与 Python 两套实现的末端位置偏差 8.5e-7 mm

    最后一项作者自己解释了动机：「C++ 和 Python 各写了一遍 DH，不校一下不放心。两边参数要是漂了，动画照样能画出来，看不出问题。」 这句话是整个仓最有价值的一句——它描述的正是仿真类项目最常见的静默失败。

  • 怎么切进去：cmake -S . -B build && cmake --build build -j && ctest --test-dir build， 只要 C++17 + CMake ≥3.16 + Eigen3（libeigen3-dev）。十分钟能跑完，零成本，零硬件。 include/robot/ 是纯头文件，整个拷走就能用在别的项目里。 真要做贡献：仓里只有 arm6.hpp（作者那台）和 ur5.hpp（参考）， 加一套 SO-101 或 Piper 的 DH 参数并跑通那 200 组往返测试，是个一天量级、结果客观可验的 PR。

  • 坑：解析逆解只对特定构型成立（球腕/三轴交于一点这类），换一台臂不一定有闭式解； README 没写这台臂的构型假设，套用前先自己确认。Python 脚本还额外要 NumPy + matplotlib。

🌍 国外

★ TOP 1（深度）· real2sim-droid —— 一条真机录像进去，一个 MuJoCo 数字孪生出来，全自动，一张卡三分钟

是什么

Pro2004-a11/real2sim-droid（MIT，09-14 建）。输入是一条 DROID 数据集的真机 episode （Franka + Robotiq 2F-85，三台标定过的 ZED 相机），输出是一个 MuJoCo 场景： 同一条轨迹、同样的三台相机视角重放，物体位置由 SAM2 掩码 + 深度反推， 夹爪是物理仿真的抓取（不是把物体焊在手上），每帧带掩码 / 米制深度 / 6-DoF 位姿 / 接触力标注。 全程无人在环。

为什么现在值得做

Real2Sim 这个方向以前是「有大规模真机采集能力的组才玩得起」的东西。 今年变了三件事：DROID 的原始 episode 可以按需单条 HTTPS 下载（约 110 MB）， KarlP/droid 放出了改进后的标定 JSON，SAM2.1 和 Depth-Anything-V2 都是 Apache-2.0 的小模型。 结果就是：一条真机数据 + 一张消费级卡 + 三分钟 = 一个可以做反事实实验的数字孪生。

这对个人特别有用的地方在于——你可以拿它给 VLA 策略做评测环境， 而不必自己有臂。作者在 README 里点名了这个用途：「a policy-evaluation loop through the real cameras」。

这个仓真正难得的地方不是它能跑，是它把每个数字都量了，而且量的方式是「在没有拟合的那个维度上打分」：

IRIS 7dfa2da3+2023-05-11（把马克笔从碗里拿出） GuptaLab 553d1bd5+2023-05-19（方块叠方块）
FK 门（DROID 末端位姿 vs MuJoCo FK） 1e-5 mm 1e-5 mm
机器人掩码 IoU，外部相机 2（中位数） 0.92 0.76
物理抓取：夹持成功 / 放置误差 闭合步的 100% · 2.4 cm 100% · 0.8 cm
反事实（物体挪 5 cm，轨迹不变） 夹住 0% · 24 cm 夹住 2% · 5.9 cm
跨视角物体摆放（ext1 拟合，ext2 重检测） 中位 4.0 cm n/a（方块在 ext2 里太小）

注意那一行反事实：物体挪 5 cm、轨迹照旧，抓取成功率掉到 0%。 这不是 bug，这是仿真器在正确地报告「这条轨迹确实依赖物体在原位」—— 一个会把反事实也抓住的孪生体，说明它根本没在物理上做手脚。 一个项目敢把「我在这个条件下失败」印在 README 的表格里，可信度比十张对齐得很好的叠图都高。

第 3 步是本期国外最值得抢的活。 作者自己只跑了两条 episode（README 的「Limitations」第一条就是 「Two episodes so far」）。DROID 里符合条件的 episode 有的是，把这个管线的统计特性做出来， 基本等同于替这个项目写了评测章节，而且纯下载 + 纯计算，零硬件、零 API 费。

显存与本机可行性：管线里最重的是 SAM2.1-hiera-small 和 Depth-Anything-V2-Small，都是小模型； MuJoCo 渲染走 EGL。A4000 16G 跑得动，只是比 4070 Ti 慢一些。作者标的 3 分钟是 4070 Ti 的数。

坑（作者自己列了一节 "Traps we hit"，这里挑最要命的几条）

  1. 运动学覆写的手臂在 MuJoCo 的接触求解器里是隐形的——物体永远不会被拿起来。 手臂必须是动态的（重力补偿 + 4 倍增益跟踪，能把录制轨迹跟到 1.25° 以内）。 这一条是所有做 real2sim 的人都会踩的。
  2. 2F-85 的指垫 body 比指垫 geom 靠后 19 mm，且闭合时指垫沿接近方向还走约 1 cm。 抓取点要从远端指垫 geom 在记录的闭合开度下读，不能读 body。
  3. 一个指垫先碰到自由物体会把它弹飞，第二个指垫还没到。要把物体按住到两侧都接触为止。
  4. DROID 的时间戳是 epoch 毫秒，帧 i 对应步 i，相机比机器人状态读数早约 54 ms——渲染要按相机的时间来。
  5. SAM2 的自动掩码在 CUDA 上每次跑结果会飘，会静默改变重建出来的场景。仓里按图缓存掩码来压住这个。
  6. MuJoCo 相机的 principal_pixel = [w/2 − cx, h/2 − cy]（x 的符号不是直觉那个）；纹理必须 PNG； 视觉 geom 必须 density=0，否则会额外加质量。
  7. ext1 那路的机器人 IoU 只有 0.31，作者明说这是度量假象——机器人在画面边缘，SAM2 只分出了小臂。 别拿这个数去比较。
  8. 代理物体只有盒/柱/胶囊（碗有个空心特例），布料被当成刚性平板；只有容器和被抓物体与机器人碰撞。
  9. ZED SDK 没用上，深度是 SGBM + Depth-Anything-V2 融合，区域性偏差有几厘米，只用了相对高度。 .svo 的 zed 后端写了但没测过。

它凭什么比一般的 FreeCAD MCP 强

关键在于它不让模型直接吐坐标。看这几个工具的设计：

工具 做的事
classify_faces STEP → 参数化的第一步：判定每个面到底是什么（平面/圆柱/圆锥/球/自由曲面）。BSpline 面会被采样后拟合，所以「假自由曲面」能被还原成圆锥并给出轴、顶点、半角
section_profile 在某个高度切截面，直接输出草图可用的 2D 线/弧/圆（先在 3D 里把孔、沉头、倒角填掉，只留外轮廓）
build_features 在 Body 上一次一个特征地堆 草图 + Pad/Pocket/Groove/Revolution/Fillet/Chamfer，每步 recompute + 校验；profile.section 直接描原始截面，坐标不经过 LLM；参数进 Spreadsheet
compare_shapes 体积/面积/包围盒差 + 模糊差集碎片及其包围盒——告诉你重建错在哪儿
suggest_sketch_fixes 约束修复提案：接近/开口端点合并、缺失的水平/竖直/相等、删冗余或冲突约束、给剩余自由度补尺寸。每条都在副本上试过，附带效果（DoF、状态）和置信度，什么都不自动改
check_printability 给定材料/喷嘴/热床配置，查薄壁、悬垂与桥接（支撑面积）、小孔与水平孔、超出热床、首层接触 → 打分 + 问题清单 + 修复候选，paint=True 直接按结果给面上色
apply_print_fixes 把 DfAM 改件做成 PartDesign 特征：象脚倒角、竖直孔补偿、水平孔泪滴化、薄面加厚、悬垂下 45° 填充、超尺寸拆件
setup_analysis / run_analysis 材料 + 固定面 + 载荷 + Gmsh 二阶网格 + CalculiX，一次调用；跑完给最大 von Mises 应力及位置、最大位移、安全系数、结论，并把应力云图画在 3D 视图里

一句话：它把「模型负责说要什么、引擎负责保证怎么做对」这条原则，落到了 FreeCAD 的 API 层。

  3. GitHub 自动生成的 "Source code (zip)" 不含编译后的运行程序，直接把仓库加成远程插件源也不会自动下载运行程序。 普通用户必须用 Release ZIP。
  4. 当前版本不生成物理螺旋螺纹（攻丝孔用底孔 + 原生装饰螺纹），也不完整解释任意 GD&T。
  5. OCR 数字必须结合原图判断，作者原话。未声明单位时按 mm。关键尺寸缺失或冲突时会要求澄清。
  6. 本机开发验证用的是 SolidWorks 2025，其他版本要自己验。
  7. 「几何创建、重建和测量成功，不能自动证明与任意工程图等价」——这句是作者自己写的， 请把它当成使用这类工具的通用免责条款。
  8. 云端 AI 会话怎么处理你的图纸和提示，取决于客户端——作者明确拒绝把这个项目描述成完全离线。 涉密图纸别往里丢。

📌 专题分析：这周这条链路上真正变了的东西（4 点）

1. 「逆向」这一格，一周之内被两边同时补上了，而且补法完全不同。

过去这个专题写的项目，输入几乎都是「一句话」或「一张参考图」——从零生成。 这一周出现的两条都是逆向：cadxray 是 STEP/STL → 参数化特征树，Auto-SolidWorks 是 二维工程图 → 参数化模型。 这个转向是有道理的：从零生成的东西你不敢用在会承力的地方，而逆向的终点是可验证的—— cadxray 的 compare_shapes 能给出「体积差 0.0 mm³」，Auto-SolidWorks 的尺寸能逐条对回图纸标注。 一个能被证伪的产出，比一个好看的产出有用得多。

值得一并记住的是 cadxray 那条硬数据：44 面的夹爪钳口，只用四个工具重建到 0.0004% 体积差， 8 个 BSpline 过渡面被识别成圆锥（残差 6.6e-5）。 这说明「厂商 STEP 里那些看起来是自由曲面的东西，大部分其实是规则面」—— 对做开源机械臂改件的人来说，这意味着你下载的那个电机座 STEP，很可能是可以被完整参数化的。

2. 「模型不吐坐标」正在变成这条链路的共识写法。

cadxray 的 build_features 里那句 profile.section 直接描原始截面、坐标不经过 LLM， 和 Auto-SolidWorks 的「计划直接传 typed draft / IR，不通过任意 shell 或脚本接口操作 CAD」， 说的是同一件事：让模型产出意图和约束，让引擎产出几何。 这和本专题 09-15 写过的 cadjson（选择器不按索引、一个零件一个 JSON）、 09-13 写过的 ModelRift openscad-skill（render/inspect/revise 回路）是同一条演化线。

对个人的直接含义：评估一个 text-to-CAD 项目时，先看它让模型写什么。 写坐标的，token 成本随零件规模线性涨，且跨轮次必漂； 写意图 + 稳定 ID 的，才有可能做到第十轮编辑还找得到第一轮那个孔。 KJDraw（KanJieTeam/kjdraw，Apache-2.0）把这条原则写成了一句标语—— 「The model decides what to draw. The engine decides how to draw it correctly.」——虽然它做的是 2D DXF。

3. 「和具身智能的接口」这一段，本周只有一个 2 星的东西，但它的形状是对的。

按覆盖面轮换，本期本该有一条 URDF/SRDF/SDF 自动生成。找遍了，这周新建的只有 enesbirlik/claude-code-robotics（MIT，09-15 建，2 ★）够得上标准，所以没给它独立条目，放在这里说：

它是个 Claude Code 插件，五个技能（ROS 2 工作区 / URDF-Xacro 构建器 / micro-ROS 桥 / Nav2-MoveIt2 配置 / ROS 2 生态包速查）， 加上两个真的会执行的 hook：verify_urdf.sh 跑 xacro 和 check_urdf， colcon_build_check.sh 跑限定范围的 colcon build，都是 PostToolUse 触发—— 模型一写完 URDF 就立刻知道它是不是畸形的。 另外带一个只读的 ROS 2 MCP 服务器（ros2_node_list / ros2_topic_echo / gz_topic_echo 等六个工具）， 没有 publish、没有 set_parameter、不能改生命周期状态。

它针对的问题 README 说得很准：通用 LLM 写机器人代码时会编出看起来合理但错误的 URDF 惯性张量、 发明不存在的 rclpy QoS 默认值、靠猜参数名去「修」Nav2 代价地图。 skills/urdf-xacro-builder/SKILL.md 里直接给了闭式惯性张量公式和宏。

这就是本期最便宜的一个动手位：装上它，拿你手上任意一个开源臂的 URDF （SO-101、Piper、OpenArm 都行），让它跑一遍一致性检查，把 check_urdf 报出来的问题提回上游仓库。 半天，零成本。它和 cadxray 合起来其实就是那条完整闭环的两端—— cadxray 负责「件对不对、打不打得出来」，claude-code-robotics 负责「装上去之后模型描述对不对」， 中间那一段（CAD 装配体 → URDF 关节树自动导出）这周依然是空的， 最近一次有像样东西是 09-12 的 robotics-design-skill-suite。

4. 「跑一个件多少钱」，八期了，还是没有任何一个项目自己报过。

本专题从 09-10 开始每期都要求把 API token 费算进去。到今天写了十几个项目， 只有 09-16 的 3Dpriting-detect-agent（全本地 Qwen2.5-3B，token 费 0）和 09-14 的 flex-fab-agent（求解在 OR-Tools 里，不花 token）能给出确定的数字， 而它们给得出来的原因都是「压根没调云端模型」。 所有真正用大模型做几何推理的项目，成本都是我在这里估的。

这件事的实际后果是：你没法比较两个 text-to-CAD 方案哪个更便宜， 而这条链路上便宜和贵能差一个量级（见上面 cadxray 的 $1–3 和 Auto-SolidWorks 纯文字的 $0.05–0.2）。 所以本期把这个列为第一号缺口：给任意一个这类项目加一段「本次运行累计输入/输出 token + 估算金额」的输出， 是几十行代码的事，而且几乎必被合。
