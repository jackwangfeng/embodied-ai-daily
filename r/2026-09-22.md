## 🇨🇳 国内

### 1️⃣ 【深度】FBddcz/embodied-jev「行知」—— 把具身决策实验搬进浏览器，零 GPU 零 API Key 就能跑第一轮

**是什么。**
[embodied-jev](https://github.com/FBddcz/embodied-jev)（中文名「行知」）是一个 MuJoCo + Franka Panda 的
**具身决策工作台**：本机起一个服务，浏览器里选任务、选模型、点「运行实验」，看着机械臂把方块搬进托盘。
2026-09-20 建仓，**两天 162 ★**，MIT。

三个任务：搬运入盘 / 方块堆叠 / 越障搬运。抓取靠双侧夹爪真实接触判定，成功与否由**独立的物理条件**判，
不是模型自己说了算。四种控制模式：

| 模式 | 模型看到什么 | 模型输出什么 |
|---|---|---|
| 预设技能 | 结构化状态或 RGB-D 检测坐标 + 可用技能表 | 阶段与技能选择 |
| 逐步 XYZ | 状态 / RGB-D 坐标，或已启用相机的原始 RGB | 一个 XYZ／夹爪短步候选 |
| 分层 XYZ | 状态、接触事实、近期动作 | 先出子目标，再分别选 X／Y／Z／夹爪方向 |
| **规则基线** | 同模式的可用观测 | **由程序选动作，零模型调用** |

**为什么现在值得做。**
这条线上大多数「能跑的东西」都卡在装 Isaac Sim、配 CUDA、申请权重。行知把门槛压到了
**Python 3.11 + Node 22.12 + 一次 `npm run build`**：默认规则基线，**模型调用数 0、花费 0**，
先把「观察 → 决策 → 执行 → 反馈」这个闭环在自己电脑上看一遍，再决定要不要接模型。

它对「实验诚实性」的处理值得单独说，这是同类项目最容易糊弄的地方：

- **未接通的模型不生成模拟成绩**，未知费用不会显示成 0 美元；
- 普通 Chat API 只返回动作选择，界面**不会把模型自报的「信心」当成真实概率**（只有原生返回候选概率的接口才显示）；
- 对比实验按**仿真时间**对齐回放，README 明说「实际耗时保留模型等待，不能拿回放速度当推理速度」；
- 候选生成、几何计算和安全检查属于控制程序，**不计作模型学到的能力**。

作者自己放出的一组真实结果也没修饰：官方 Jev 的分层 XYZ 两局搬运**均达到终态**，
分别 **89 / 88 步、178 / 176 次真实请求、约 72 / 80 秒**；但**两局下放时都失抓**，
方块落进托盘后完成撤离，所以「还不能称为稳定精确放置」。这个口径比「成功率 100%」有用得多。

**个人怎么切进去（分步 / 带成本和时间）。**

| 步 | 做什么 | 时间 | 花费 |
|---|---|---|---|
| 0 | `git clone` → venv → `pip install -e .` → `npm ci && npm run build` → `embodied-jev serve --port 8090`，浏览器开 `127.0.0.1:8090`，保持「规则基线」跑三个任务各一遍 | 30–60 分钟 | **0** |
| 1 | 接**本地 MiniCPM5-2B**：`pip install -e '.[minicpm]'`、`EMBODIED_MINICPM=1`、`embodied-jev warmup`。首次下 **约 5 GB** 权重，CUDA 下走 FP16。A4000 基线被占 4.4G，剩 ~11.6G，2B 的 FP16 权重约 4–5 GB，**装得下**；缓存全了可以 `HF_HUB_OFFLINE=1` 离线跑 | 半天（含下载） | 0（电费） |
| 2 | 接自己的云端 API（OpenAI 兼容 / Claude 原生），开「模型对比」，统一任务 + 种子 + 动作预算，跑 2–3 路 | 1–2 小时 | 见下方成本 |
| 3 | **交付**：导出实验 JSON，把「同一任务同一种子下，本地 2B 小模型 vs 云端大模型」的步数 / 请求数 / 耗时 / 失败模式写成一篇对照。这是目前公开数据里**最缺的一格** —— README 自己也写「Jev / Claude 的同设置对照还待完成」 | 1–2 天 | 同上 |
| 4（可选） | 提 PR。缺口很明显：Windows 路径只提供了命令、**CI 只验过 macOS / Linux**；没有导入历史实验文件的入口（服务重启轨迹就没了）；任务只有三个 | 数天 | 0 |

**云端调用成本怎么估。** 拿作者实测的 **178 次请求 / 局**当基数。逐步 XYZ 模式每次请求是「当前状态 +
可用动作 + 简短历史」，量不大，按每次 1.5–3k 输入 / 100–200 输出 token 估，一局约
**270–530k 输入 + 18–36k 输出**。按当前公开价目：

| 模型 | 输入 $/M | 输出 $/M | 一局(178 次)约 |
|---|---:|---:|---:|
| Claude Sonnet 5 | 3 | 15 | **$1.1–2.1**（约 ¥8–15） |
| Claude Opus 5 | 5 | 25 | **$1.8–3.4**（约 ¥13–25） |
| Claude Haiku 4.5 | 1 | 5 | **$0.4–0.7**（约 ¥3–5） |

**做一组三任务 × 三模型 × 三种子的完整对照，量级在 ¥100–300**，这是可以自己掏的。
本地 MiniCPM5-2B 那一路是 **0**，所以合理的姿势是：**本地模型跑多种子拿方差，云端模型只跑少数几局做上限对照。**

**坑与风险。**

- **项目太新。** 两天 162 ★，接口一定会变。要么钉 commit，要么做好每周同步的准备。
- **Windows 未经 CI 验证。** README 给了 PowerShell 命令但明说「当前已验证的环境为 macOS 与 Linux CI」。
- **官方 Jev 是邀请制。** 要先到 TypeSafe 官网排 waitlist，拿到邀请才能建 Key。**做对照实验不要把它排进关键路径**，
  用 OpenAI 兼容 / Claude 原生那两个入口即可。
- **图像输入的边界要看清。** 原始图像目前只走支持图像的 Chat / Claude 逐步模式；**Jev 只接收文本**，
  它读的是本地检测器给出的 RGB-D 坐标，不是相机图。跨模型对比时这一条必须写进方法部分，否则不公平。
- **别拿回放速度当推理速度**（作者已经在 README 里提前堵了这个口子，但导出数据时容易忘）。
- Key 存在系统钥匙串里，系统存储不可用时页面会退化成「仅本次会话」——**不会改存明文**，这点做得对，但注意别在共享机器上留 Key。

### 2️⃣ robot-hint/HINT —— 给长程操作装一个「先决定信哪只相机、再锁定意图」的路由器（浙大等，Apache-2.0）

- **是什么**：[HINT](https://github.com/robot-hint/HINT)（[arXiv:2609.02653](https://arxiv.org/abs/2609.02653)，
  [项目页](https://robot-hint.github.io/)）是长程操作的 agentic 框架。核心是一个 **pattern router**：
  它决定**该信哪只相机**、以及**什么时候更新语义**；在这些切换点上，task manager + grounder 解析出当前子任务和目标，
  tracking 在两次更新之间**维持住这个承诺**。追踪到的意图再通过**视觉高亮 + attention prior** 注入动作策略 ——
  **不给基础模型加任何可训练参数**。
- **为什么值得做**：长程任务的失败往往不是动作不行，而是「中途把目标搞丢了」。HINT 把这件事拆成可单独替换的模块
  （`src/perception/` 是 task manager / grounding / tracking，`src/intent/` 是高亮与 attention prior），
  每一块都能单独换掉做消融 —— 对个人来说这是难得的**可局部动手**的结构。
- **个人怎么切进去**：**先别碰真机，也先别训 π₀.₅。** 仓库有 `src/dataset_export/`，
  能对已有 LeRobot 数据集**离线**导出高亮视频和 attention map。README 明确建议
  「先跑一个 episode 检查高亮效果，再做完整导出」——这是一条零硬件、单卡就能走完的验证路径。
  看懂高亮对不对，再决定要不要投训练。
- **坑**：依赖 GroundingDINO + SAM2 + Qwen3-VL + π₀.₅(OpenPI) 四套权重，显存压力主要在这里；
  一个 conda env 同时装了 PyTorch 和 JAX，但 **README 明说「不要在同一个 Python 进程里加载两个模型」**；
  YAML 里**必须填绝对路径**，HINT 不展开 `$HOME` / `$CKPT_ROOT`。
- **相关**：[OpenPI](https://github.com/Physical-Intelligence/openpi) ｜ [LeRobot](https://github.com/huggingface/lerobot)

## 🌍 国外

### 1️⃣ 【深度】Pro2004-a11/real2sim-droid —— 一条 DROID 真机 episode 进去，一个带真值标注的 MuJoCo 数字孪生出来，全自动

**是什么。**
[real2sim-droid](https://github.com/Pro2004-a11/real2sim-droid)（MIT，Python 3.12 / MuJoCo 3.13 / PyTorch 2.6）
吃一条 DROID 数据集里的真机 episode（Franka + Robotiq 2F-85，三台标定过的 ZED），
吐出一个 MuJoCo 场景：**同一条轨迹、同样的相机位姿**重放一遍，物体位置由 depth + SAM2 自动摆放，
抓取是**物理仿真出来的**（不是脚本吸附），逐帧输出 mask / 米制深度 / 6-DoF 位姿 / 接触力。
**No human in the loop。**

**为什么现在值得做。**
Real2Sim 这件事，绝大多数公开实现要么半自动（人工对齐物体），要么只交一个「看着挺像」的叠加图。
这个仓库的分量全在**它把每一句话都量化成了和真实录像对比的数字**：

| 门 | IRIS `7dfa2da3+2023-05-11`（把记号笔从碗里拿出来） | GuptaLab `553d1bd5+2023-05-19`（方块叠方块） |
|---|---|---|
| FK 门（DROID 末端位姿 vs MuJoCo FK） | **1e-5 mm** | **1e-5 mm** |
| 机器人 mask IoU（外部相机 2，中位） | **0.92** | **0.76** |
| 物理抓取：持住比例 / 释放误差 | **100%** 的闭合步 · 2.4 cm | **100%** · 0.8 cm |
| 反事实（物体挪 5 cm、轨迹不变） | 持住 **0%** · 24 cm | 持住 **2%** · 5.9 cm |
| 跨视角物体摆放（ext1 拟合、ext2 重检测） | 中位 **4.0 cm** | n/a（方块在 ext2 里太小） |

最后那行反事实是整个仓库最该被抄走的设计：**它证明了这个数字孪生不是把抓取写死了。**
物体挪 5 cm、轨迹照旧 → 抓不住。任何号称「复现了真机」的仿真，都应该被这么问一次。

**个人怎么切进去（分步 / 带成本和时间）。**

| 步 | 做什么 | 时间 | 花费 |
|---|---|---|---|
| 0 | `pip install torch --index-url .../cu124` → `pip install -e .`（拉 mujoco、menagerie、transformers、opencv） | 30 分钟 | 0 |
| 1 | `python scripts/fetch_droid.py --calib` 拉改进过的标定 JSON（HF `KarlP/droid`，**约 330 MB**）；再 `--episode <id>` 拉单条 episode（**约 110 MB，走 HTTPS，不需要 gsutil**） | 20 分钟 | 0 |
| 2 | `python -m real2sim all --episode <id>`。作者实测 **4070 Ti 上约 3 分钟**；**A4000 折算约 6–8 分钟**。产物落在 `runs/<episode>/`：`ingest/`（帧、K、cam→base）、`depth/`、`gate/`、`objects/`、`sim/`（rgb、label map、`*_depth.npy`、含位姿/四元数/接触力的 `state.npz`）、`compare/`（并排 MP4 + `metrics.json`） | 10 分钟 | 0 |
| 3 | `python -m real2sim counterfactual --episode <id>` 复现那条反事实。**这一步是理解这个仓库的关键，别跳** | 10 分钟 | 0 |
| 4 | **交付路线 A（最短）**：换一条你自己挑的 DROID episode 跑一遍，把 mask IoU / 抓取持住率 / 反事实三条数字发进 issue。作者只验过两条 episode，**第三条数据点就是新信息** | 半天 | 0 |
| 5 | **交付路线 B（更有价值）**：把产出的逐帧真值（mask / 米制深度 / 6-DoF 位姿 / 接触力）当作**免费的标注数据**，喂给你正在训的感知模块。这是把「别人的真机数据」变成「你的带标注仿真数据」的桥 | 数天 | 0 |

**显存**：SAM 2.1-hiera-**small** + Depth-Anything-V2-**Small**，都是小号，A4000 16G（基线占 4.4G）够用。

**坑与风险。**

- **只验过两条 episode。** 方块叠方块那条的 mask IoU 只有 **0.76**（vs 0.92），跨视角摆放在那条上**直接 n/a**
  （方块在第二个外部相机里太小）—— 小物体是已知短板，别指望它在精细装配类 episode 上同样好。
- **跨视角中位误差 4.0 cm** 不小。做需要厘米级绝对位置的下游任务时，这是误差下限。
- **`fetch_droid.py --calib` 要 330 MB**，`--episode` 每条约 110 MB，先看硬盘。
- 钉死 cu124 的 PyTorch + MuJoCo 3.13，和你已有的环境大概率冲突，**开独立 venv**。
- 反事实那两个数字（持住 0% / 2%）是**特性不是 bug**：它说明这不是一个通用抓取模拟器，
  只是「这一条轨迹在这一个场景下的物理复刻」。别拿它当抓取策略的训练场。

### 2️⃣ RyanXXYC/Pounce —— 离合式 VR 遥操作 + 一套能替代原厂 FD.exe 的 Feetech STS 舵机工具（硬件 / 遥操作套件，MIT）

- **是什么**：[Pounce](https://github.com/RyanXXYC/Pounce) 是个 Windows 桌面程序（Python + tkinter），
  用 Oculus Rift S 的 Touch 手柄通过 SteamVR 直接遥操作 [xLeRobot](https://github.com/Vector-Wangel/XLeRobot)
  的双臂、四轮底盘和相机云台。数据通路写得很清楚：

  ```
  手 → 头显相机(位置) + 手柄 IMU(姿态) → SteamVR → 程序 60 Hz 读位姿
     → 漂移门 → 离合 delta → 房间系→臂系旋转 → One Euro 滤波 → IK
     → 两条 USB-serial(1,000,000 bps) 上 20 Hz 关节指令 → STS3215
  ```
- **为什么值得做**：两件事。一是**离合式控制**（握住 grip 手跟着动、松开臂冻结、再握从原地续上，像把鼠标提起来放下）——
  这意味着**臂永远不会跳**，是遥操作采数据最怕的失败模式。二是那套舵机页（Debug / Program / OneKey / PWM）
  **讲的是纯 Feetech SCS/STS 总线协议**，作者明说「适用于任何 STS 舵机装置，不止 xLeRobot」——
  也就是说，哪怕你不玩 VR，只要手里有 STS3215（SO-101 / SO-100 / xLeRobot 全家都是），
  这就是一套**开源的中位校准与编程工具，可以替掉原厂 FD.exe**。
- **个人怎么切进去**：**283 个单元测试不需要任何硬件** —— 协议、运动学、滤波器、绑定模型、SteamVR 数据文件
  都是纯代码且被覆盖。先 `python -m pytest` 跑一遍读懂闭式 IK 和 One Euro 的实现，
  再决定要不要买硬件。xLeRobot 整机 **$660**（约 ¥4700），**刚好卡在预算线内**，但 Rift S 得另算。
- **坑**：**只有 Windows**（Python 3.9+，作者在 3.9.13 上开发）。仓库里那份 `teleop_config.json`
  是**作者自己那台的标定值**（舵机 ID、轮组、增益、运动学符号与零位、操作者坐标系）——
  README 明说「用它当参考，但在信任 EE 模式之前必须在自己的机器上跑 Wheel-ID / Servo-Cal / Cal-Wizard 三个向导」。
  别直接拿来用。

### 🇨🇳 yuexinyang526-coder/TacBench-Lite —— 一台笔记本上跑完的视触觉闭环基准，用「冻结触觉」证明了策略要的是动态反馈

**是什么。** [TacBench-Lite](https://github.com/yuexinyang526-coder/TacBench-Lite) 是一条
**纯 CPU** 的「仿真环境 → 多模态数据 → 多模态模型 → 闭环评测」最小闭环：
MuJoCo 物理 + **自研的轻量视触觉渲染器**（射线几何穿透 + 力致弹性体压缩 + 三色 LED 光度立体 + 标记点阵）、
3 自由度笛卡尔龙门 + 40 mm 方形视触觉垫、四个接触密集型任务、**658k 参数**的 TacLite 策略。
代码 MIT，数据集 CC-BY-4.0（344 MB / 800 episode），**50 个 checkpoint** 走 Release 附件。

作者的硬件现实写在 README 里：RTX 3050 Laptop（4 GB）+ 16 GB 内存 + i5-11400H，
Isaac Sim 系（含 TacEx、Tabero 官方栈）跑不动，**所以选了纯 CPU MuJoCo 并自己写渲染器**。

**可量化的口子。** 动作是 `[dx, dy, dz, f_des]`，由底层**混合力/位置控制器以 50 Hz** 执行，
**单步 8.3 ms**；渲染器自检：16 mm 方孔平移 0/3/6/10/14 mm 下，**孔心恢复误差 ≤ 0.6 mm 且单调**；
力 → 形变 0.57→10.8 N 对应 0.14→2.71 mm；剪切 → 标记位移 0→1.04 N 对应 0.22→0.37 mm。
评测 = 每任务 30 episode × 4 任务 = **150 episode/格**，**每个 seed 重新采一整套数据**（5 个独立数据集），
配对精确 McNemar + Holm–Bonferroni 校正。

**为什么值得做（这才是这条专题要的东西）。** 6.2 节那张传感器失效表是整个仓库的重点：

| 条件 | press | align_hole | slide_ridge |
|---|---|---|---|
| 正常 | 85.3% | **56.7%** | 46.0% |
| 触觉置零 | 57.3% | **0.0%** | 36.7% |
| **触觉冻结**（冻在首次接触帧） | 75.3% | **0.0%** | 36.7% |
| 触觉加噪（σ=25/255） | 72.0% | 40.7% | 48.0% |
| 替换语言指令 | **8.0%** | 28.7% | 38.0% |

**「触觉冻结」和「触觉置零」一样把 align_hole 打到 0%。**
也就是说：给策略一个**恒定的、正确的**触觉画面（它确实在接触），和干脆不给，**结果完全一样**。
策略要的不是「有没有接触」这一个 bit，**是这一路信号在持续变化**。
这是我在这个专题里见过最干净的一次「连续流不可替代」的证据 —— 而且它跑在纯 CPU 上。
（口径也写得很严：冻结发生在**法向力首次 > 0.3 N 的那一帧**，此前照常送实时帧；早期版本在 episode 第一帧就冻结，
那时垫子还没接触，该口径已废弃。这种自我纠正在个人项目里很少见。）

另外两条同样有迁移价值：**去触觉后 align_hole 56.7% → 1.3%**（校正后 `p = 5.6e-24`，两路视觉撑不起 1.5 mm 容差）；
**粗触觉编码（6×6 token）下 align_hole 只剩 2.7%** —— 表征的空间分辨率必须和任务容差同量级。

**个人怎么切进去。** ① `pip install -r requirements.txt`（174 个包，含 torch 2.5.1+**cpu** 和 mujoco 3.13）；
② **约 1 分钟的最小验证**：`python -m sim.validate_tactile`（渲染器自检）+ `python -m sim.eval_expert`
（脚本专家上界 100/100/96/100%）；③ 从 Release 拉 344 MB 数据 + 127 MB 权重，`python -m model.degrade`
复现那张失效表；④ **交付**：把「冻结 vs 置零 vs 加噪」这套协议搬到**你自己的传感器模态上**
（力矩、事件相机、关节编码器都行）—— 这是一套可以直接复用的「这一路信号到底是不是必须连续」的测法。

**坑（作者自己列的负面结果，非常硬）。** 6.3 节：渲染器对真实 GelSight Mini 的外部效度是**负面的**。
100/100 帧-几何精确配对下，**本渲染器 vs 真实 NCC = +0.27**，而「真实 vs 另一个数字的渲染」这个随机下限是 **+0.29** ——
**匹配值不高于随机下限**。渲染器给出正确的接触轮廓，但不携带可区分数字的内部结构。
光度域差距：亮度 ×0.51，逐通道对比度比约 [1.2, 3.5, 1.6]（真实传感器绿通道几乎是平的，std 9.1；
渲染器三通道都放了几乎相同的结构，std ≈ 33）。**所以：这是一个做消融和协议设计的台子，不是一个 sim-to-real 的台子。**
另外一键脚本是 PowerShell（`run_all.ps1` / `ablation.ps1`），Linux 上要自己拆成 shell。
还有一条诚实得少见：分类迁移实验（纯渲染训练 → 真实测试）**作者故意不报数字**，
因为两个域的触点分布差一个量级，渲染训练 13.3% 与真实训练 1.7% 都落在噪声带内，此时报数字是误导。

### 🌍 Vigilant-CRS/Inference-Governor-QoS —— 不是算得更快，是**不算已经过期的那一帧**

**是什么。** [Inference-Governor-QoS](https://github.com/Vigilant-CRS/Inference-Governor-QoS) 是一个 Rust 写的
**推理 QoS 调度器**，坐在 NVIDIA Triton（或 TF Lite）前面，**在请求到达 GPU 之前**做六个决定：

| | 决定 | 为什么重要 |
|---|---|---|
| 🗑️ | **丢掉已被取代的工作** —— 同一路相机来了新帧就替掉还在排队的旧帧 | 旧帧的结果机器人反正会扔掉，算它等于抢新帧的 GPU 时间 |
| ⏱️ | **拒绝一定会迟到的工作** —— 算完就已经过期的，干脆不启动 | 迟到的答案不是「慢」，是「错」 |
| 🛡️ | **压住后台长任务** —— 受保护的流马上要来，长任务就不开工 | 这是唯一一处它**故意让 GPU 空着**，也正是相机保持新鲜的原因 |
| 🎚️ | **切到还塞得下的小模型变体** —— 压力下宁可精度略低但准时 | |
| ✂️ | **把长任务切块续跑** —— 声明 `cooperative:` 的生成式模型按实际空出的时间切片，块与块之间让出槽位，状态走 prompt 传递 | 内部实测：不可守承诺的拒绝 **221 → 0**，受保护相机 **795 → 891 / 910 帧**，总算力不变 |
| 🎯 | **兑现一个能写下来的承诺** —— contract 可带 `objective:`，同时约定占比和最长容忍间隔 | 「98% 新鲜，且绝不出现整整一秒空白」这种话运维能讲、调度器能查 |

它说的是 **Open Inference Protocol**（和 Triton 同一个 gRPC 接口），**客户端只改一个东西：连接地址。**

**可量化的口子（作者自己给的口径很克制，值得抄）。**
RTX 3070 Laptop (8 GB)、Triton 2.70、真实模型（RF-DETR @ 512 px、ResNet pose、depth，外加一个 95 ms 不可中断块），
**对手是调过的 Triton**（同模型、同 instance group、同共享内存数据通路、开了带优先级的 rate limiter）：

| 流 | Triton（调过） | Vigilant | 未覆盖周期 |
|---|---:|---:|---:|
| detector (RF-DETR) | 84–85% | **99%** | **少 20–22×** |
| pose | 91% | **99%** | **少 10–12×** |
| depth | 97–98% | 90–100% | **无增益 —— 作者明说「不算作胜利」** |

六轮、两个驱动版本各三轮。对上 Triton 的**最强配置**（全局受限共享资源）时 detector 是 12.9–15.1×，
作者**给区间不给最好看的那个数**，并注明那次比较是 09-10 的 gap 计账修正之前测的、之后没重跑。
还有**诚实的另一半**：同一轮里后台语言模型覆盖率是 **0%** —— 95 ms 不可中断块塞不进 33 ms 周期，有没有调度器都塞不进，
区别只是「调度器决定了谁输，并且说出来」。开了 cooperative 切块后：detector 98% → 91%，语言模型 **2 代 → 40 代**。

**换算到本机。** 它测的是 3070 Laptop（8 GB）。A4000 算力更高但**基线已被别的进程占 ~4.4G**，
而这个工具**要解决的恰恰就是「多个东西抢一张卡」**—— 本机就是它的目标场景。
延迟数字按 ×1.5～2 折算到 A4000 的多任务负载上看即可（它不是模型推理，是调度开销，绝对值很小）。

**为什么这条值得单独列。** 前三期这个专题写的全是「让一次前向更快」（Triton kernel、CUDA graph、投机解码、流式解码）。
这条是**正交的另一个维度**：一帧 33 ms 进来一次，检测器要 15 ms，本来塞得下 —— 直到一个语言模型在同一张卡上开了个 95 ms 的活。
**更快的 GPU 只会更快地算过期的帧。** 这句话（"A faster GPU computes stale frames faster"）是整个仓库的论点，
也是「流式感知 → 连续决策」里一直被忽略的一环：**连续性不只是模型的事，是排队的事。**

**个人怎么切进去。**
① 先不装，读 README 里那张 ASCII 时序图（F1..F5 四帧被 95 ms 块挤掉的过程），三分钟就懂了；
② `vig autotune --endpoint 127.0.0.1:8001 -c vig.yaml -o qualification` —— 它会在你的机器上量你的模型、
拿你的 contract 试配置、**只保留背靠背重跑还站得住的那些**，并且**在你的负载根本不需要调度器时直说**；
③ **交付**：在本机（A4000 + 那 4.4G 的占用）上跑一遍 autotune，把「一个 VLA 推理 + 一路相机检测」
这种真实具身负载下的覆盖率数字发出来 —— 作者测的是通用感知负载，**具身场景的数据点是空的**。

## 📈 趋势观察

**这一期最清楚的一条线：可信度正在从「跑得多快」转向「哪些数字不算数」。**

把本期九个条目的自述放在一起看，一个模式很刺眼 —— **它们都在主动划掉自己的一部分成绩**：

- embodied-jev：「未接通的模型不生成模拟成绩」「不能拿回放速度当推理速度」「两局下放都失抓，还不能称为稳定精确放置」
- real2sim-droid：反事实实验**故意**证明自己的抓取不泛化；方块那条 IoU 只有 0.76 且跨视角 n/a，照写
- TacBench-Lite：渲染器对真实 GelSight 的匹配 **NCC 0.27 < 随机下限 0.29**，整节标题就叫「负面结果」；
  分类迁移**故意不报数字**，因为都落在噪声带里
- Inference-Governor：depth 流「无增益 —— 不算作胜利」；后台语言模型 0% 覆盖「诚实的另一半」；
  对手最强配置那组数字标注「修正之后没重跑」
- MicroDuck-BoBoRedesign：三个目录写在 README 里但仓库里还没有，作者直接标 "in active development"
- Prompt2Print：五档状态 `PASS / WARN / FAIL / UNKNOWN / NOT_RUN`，**"nothing is ever simulated as a pass"**

这不是巧合。**当「跑通一个 demo」变得足够容易之后，区分度就从「有没有结果」转移到了「这个结果的边界在哪」。**
对个人参与者来说这是个好消息：*你最容易做出的贡献，不是再训一个模型，而是给别人的项目补上一个它自己没量过的维度。*
本期四条「个人怎么切进去」的交付路线（embodied-jev 的本地 vs 云端对照、real2sim-droid 的第三条 episode、
TacBench-Lite 的冻结协议迁移、Inference-Governor 的具身负载数据点）**全都是这种形状**。

**第二条线，关于「连续」的定义在变宽。**
这个专题开到第四期，前三期的答案都是「让模型算得更快 / 让架构吃得下流」。
这期两条把边界推开了：TacBench-Lite 证明了**连续性是信号的属性**（冻结的正确触觉 = 没有触觉），
Inference-Governor 证明了**连续性是排队的属性**（更快的 GPU 只会更快地算过期的帧）。
再加上论文清单里事件相机那两篇（逐事件处理、不做时间累积），
「流式感知 → 连续决策」这件事的完整形状大概是四层：**传感器怎么采 → 怎么排队 → 怎么算 → 怎么和执行重叠。**
前三期只碰了后两层。

**第三条，一个反复出现的现实：这条链上最好的工程往往挂 0 星。**
本期 Inference-Governor 0 ★、Prompt2Print 1 ★、patent-3d-demo 1 ★、Pounce 1 ★、TacBench-Lite 1 ★，
而 embodied-jev 两天 162 ★。星数衡量的是「有多少人能一眼看懂它解决了什么」，不是工程质量。
**用 `gh search repos --created ">=<日期>"` 按时间捞、而不是按星数捞**，这条检索习惯这几期一直在兑现价值。
