🇨🇳 国内

★ TOP 1（深度）· RoboGesture —— 让人形一边说话一边比手势，54 类动作的部署权重直接给了

是什么。

银河通用（Galaxy General）+ 清华（Li Yi、He Wang 组）的 ECCV 2026 工作，9 月 5 日建仓、9 月 11 日仍在推。 MIT 许可。它解决的是一个被 VLA 热潮盖住、但做人机交互一定会撞上的问题： 人形机器人说话的时候，身体该怎么动。

技术路径一句话：把一段 WAV 直接映射成 30 FPS 的 41 维 qpos 序列，中间不经过转写文本。

  • 音频用 Mimi（Kyutai 的音频 tokenizer，CC-BY-4.0）编码；
  • 一个音频条件的动作生成器输出 41 关节轨迹，外挂一个 54 类语义头，让动作和话里的语义对齐， 而不是只跟着韵律抖；
  • 可选地接一条对话链路：英文 ASR → Qwen3-4B-Instruct + LoRA（rank 8 / alpha 32）产生带动作标签的回复 → TTS → 手势播放。

它明确不是「实时流式」：每句话的音频和动作是整句生成、整句做碰撞过滤、然后同步播放的。 README 里自己写清楚了这一点，没有含糊过去。

为什么现在值得做。

  1. 这是本周唯一一个「顶会 + 代码 + 真权重」三样齐全的国内具身工作。 同期开源的 X-WBC（CoRL 2026，跨本体人形全身控制）和 CAP（CoRL 2026，复旦 + TARS，感知退化下的人形行走） 都只有项目页和一串未勾选的 checkbox。RoboGesture 的 checkpoints/ 里躺着实打实的 motion/model.pt 和 qwen_lora/adapter_model.safetensors，还附了 SHA-256。
  2. 入门那一步被降到了「不用下任何模型」。 仓里带了 15 对 sample_XX.wav + sample_XX.npz （音频 + 动作），robogesture render 就能把它们合成 960×720 的 H.264/AAC MP4。 这意味着你可以先花 20 分钟确认「这东西到底长什么样」，再决定要不要投入。
  3. 手势这条线几乎没人做，而它是「机器人像个人」的最短路径。 本系列做到第十期， 翻过的国内仓绝大多数在抓取、导航、行走上打转。语音 → 语义对齐的上半身动作，是一个空得多的口子。

个人怎么分步切进去（带成本和时间）。

先把硬现实说清楚：官方测试环境是 Linux x86-64 + Python 3.10 + RTX 4090（24 GB）+ CUDA 12.1。 本机 A4000 16 G 的情况分三段，我按「先做哪个」排序。

第一步 —— 只渲染（30 分钟，0 元，16 G 绰绰有余，大概率连 GPU 都不太用得上）。

git clone https://github.com/GalaxyGeneralRobotics/RoboGesture.git
cd RoboGesture
# Ubuntu 上先补系统包
sudo apt-get install git git-lfs python3.10-venv libportaudio2 libegl1 libgl1 libglib2.0-0
bash scripts/setup.sh          # 建 .venv/，装 PyTorch 2.5.1+cu121 和钉住版本的 Unitree SDK

.venv/bin/robogesture render examples/sample_01.npz --output outputs/sample_01.mp4

注意 render 这一步不需要任何 checkpoint —— NPZ 里已经是动作，渲染器自动找同名的 WAV 配上。 15 个样本全渲一遍，你就有了这个模型能力边界的第一手印象。

第二步 —— WAV → 动作（半天，0 元，16 G 应该够）。

git lfs install --local && git lfs pull && git lfs fsck
.venv/bin/python scripts/download_models.py --only mimi

.venv/bin/robogesture infer examples/sample_06.wav --output outputs/generated.npz
.venv/bin/robogesture render outputs/generated.npz --output outputs/generated.mp4

然后把 examples/sample_06.wav 换成你自己录的一段中文。论文和 LoRA 都是英文对话链路， 中文语音喂进纯音频的动作生成器会发生什么，仓里没有任何数据 —— 这是一个半天就能做完、 而且现在没人做过的实验。把结果贴回 issue 就是有效贡献。

第三步 —— 完整对话链路（1–2 天，几十元量级，16 G 是未知数）。

.venv/bin/python scripts/download_models.py        # 再拉 Qwen3-4B-Instruct-2507
.venv/bin/python scripts/check_install.py --require-cuda
.venv/bin/robogesture stream                        # 不连设备，只看入口

Qwen3-4B bf16 约 8 GB，加上 Mimi 和动作模型，16 G 理论上装得下但没人验证过。 另外这条链路要你自己的火山引擎 ASR / TTS 凭据（docs/robot.md 里写明了）， 这是唯一一处真金白银的花费，按调用量计，试几十句是几元到几十元的量级。

坑与风险。

  1. checkpoints/ 里的两个文件在 GitHub 网页上看是 134 字节和 133 字节 —— 那是 Git LFS 指针。 直接 git clone 然后加载会报一个和权重无关的怪错。必须 git lfs install --local && git lfs pull。 这是本条最容易浪费一小时的地方。
  2. 这不是论文的复现包。 README 原文：「Full training workflows, preprocessing and private datasets are not included; this is not a full reproduction package for the paper's experiments.」 训练数据是私有的，你能拿到的是部署版的 54 类推理变体，外加两个用合成张量跑的训练核心示例。 想复现论文数字的，趁早死心；想拿它做交互 demo 的，够用。
  3. 真机那一端的门槛在钱不在码。 官方验证平台是 Unitree G1 + BrainCo Revo2 灵巧手， 这套东西远超本系列「≤ 约 5000 元」的线。但第一步和第二步完全不需要机器人， MuJoCo 里的固定基座场景（腿角全零）就能看动作。
  4. 离线渲染带平滑和碰撞过滤，不等于真机可以直接播。 README 自己标了 「suitable for inspecting motion, not a replacement for a live robot preflight」。

3 · Vision_Sync_Dexterous_Hand —— 一个摄像头把手指弯曲映射到灵巧手，默认不动、先 dry-run

一句话：MediaPipe 21 点 → 六维归一化关节命令 → USB-RS485 驱动 BrainCo Revo2， MIT，32 个文件，22 项单测，默认以 dry_run 安全模式启动。

值得写的不是「视觉遥操作」这件事（这个已经烂大街了），而是它把安全当成了默认行为：

  • 默认不使能，要显式开；
  • 张手 / 握拳双姿态标定，自动兼容正向和反向特征；
  • 滤波是四层叠的：关键点 EMA → 滚动中值 → One Euro 低通 → 死区 → 关节速度限制；
  • 丢手超时自动暂停并保持最后姿态（不是归零，不是继续跟最后一帧抖）；
  • README 第一段就是警告：「首次运行务必 dry_run……测试时保留物理断电手段。」

后端是分离的三个：DryRunBackend / Rs485Backend（走 bc-stark-sdk）/ 实验性的 DdsBackend （Unitree DDS，接 brainco_hand_service）。换一只别的灵巧手，只要写一个新 backend。

个人怎么切进去：Windows 或 Linux，Python 3.9–3.12，一个普通 USB 摄像头。 python -m venv .venv && pip install -r requirements.txt，跑 scripts/teleop_mediapipe.py， 浏览器里打开中文 WebUI 看骨架预览和手动滑块。整个过程零硬件、零成本、半小时。

坑：真机需要 BrainCo Revo2（不便宜）+ USB-RS485 转换器 + bc-stark-sdk， 而 README 自己说「如果当前平台没有可用的 PyPI 包，请从……」—— 也就是 SDK 的平台覆盖有缺口。 另外 Revo2 的关节顺序 [thumb, thumb_aux, index, middle, ring, pinky] 是硬编码的假设， 换手要一起改映射层。仓建于 8 月 31 日，建完当天推完就再没动过，1 star。

顺带一提：这条和上面的 TOP 1 撞在同一只手上 —— RoboGesture 的官方验证平台也是 G1 + BrainCo Revo2。 本周国内两条独立的线索指向同一款灵巧手，这件事本身值得注意（趋势观察第 2 点）。

→ 出处 https://github.com/wsdd2/Vision_Sync_Dexterous_Hand

🌍 国外

★ TOP 1（深度）· mjbatch —— 4096 个 MuJoCo 仿真，纯 CPU 并行，Go1 在五年前的 M1 笔记本上一分钟学会走路

是什么。

Kevin Zakka（MuJoCo Menagerie、mjctrl 的作者）9 月 10 日开的新仓，四天 400 star，Apache-2.0， PyPI 上已有包。一句话：一个把成千上万个 MuJoCo 仿真塞进 CPU 线程池并行跑的 Python 库。

三个特性，每一个都对应一类以前很别扭的写法：

  • C++ 线程池执行，全程释放 GIL —— 不是 multiprocessing，没有进程间拷贝；
  • bind 给 MjData 字段做批量活视图 —— batch.bind("qpos") 拿到的是一个 (num_sims, nq) 的 numpy 数组，原地更新，你的控制器一次算完 4096 个；
  • expand 给 MjModel 字段做逐仿真参数化 —— 每个仿真可以有自己的摩擦、自己的几何、自己的齿轮比， 配 set_const 重算派生常量。这是域随机化和硬件协同设计的关键。

核心用法短到可以整段抄：

import mujoco, numpy as np
from mjbatch import Batch

model = mujoco.MjModel.from_xml_path("scene.xml")
batch = Batch(model, num_sims=4096)              # 线程数默认吃满所有逻辑核
qpos, ctrl = batch.bind("qpos"), batch.bind("ctrl")
batch.expand("geom_friction")[:, :, 0] = np.random.uniform(0.4, 1.2, (4096, 1))
for _ in range(1000):
    ctrl[:] = policy(qpos)                        # 你的控制器，4096 个一起算
    batch.step()                                  # 并行推进，qpos 原地更新

为什么现在值得做。

  1. 它把「做具身 RL / MPC 需要一张好显卡」这个前提拆掉了。 README 原话：Go1 的 RL 控制器 在一台五年前的 M1 笔记本上不到一分钟学会走路。本系列的读者里， 卡在「买不起 / 租不到 GPU」这一步的人，比卡在算法上的多得多。
  2. 它带的六个示例本身就是六份可抄的模板，而且覆盖面是刻意铺开的：
    示例 做什么 方法
    hello.py 4096 个单摆，1000 步一次调用跑完 最小骨架
    cartpole_swingup.py 双杆小车摆起 iLQR
    cartpole_mpc.py 小车摆起控制器 predictive sampling
    g1_flip.py G1 人形跟踪参考后空翻 滚动时域 iLQR
    go1_joystick.py Go1 四足跟随摇杆 PPO，1024 个并行环境
    arm_throw.py 同时优化机械臂的比例、齿轮和控制 CEM 协同设计
    rizon_inertia.py 拟合 Rizon 臂的惯性参数 阻尼 Gauss–Newton
  3. arm_throw.py 这一类东西以前几乎没有平民实现。 「本体形状和控制策略一起优化」 在论文里很常见，在开源代码里很少见，因为它要求你能便宜地同时仿真一堆不同的机器人—— 而这正好是 expand 干的事。对个人来说这是一条真正新开的路： 你可以在打印之前，先让 CEM 告诉你连杆该多长。

个人怎么分步切进去（带成本和时间）。

第一步 —— 装上、跑 hello（15 分钟，0 元，任何一台电脑）。

pip install mjbatch
# 或者跟着仓库走
git clone https://github.com/kevinzakka/mjbatch && cd mjbatch
uv run examples/hello.py        # 4096 个单摆，打印 sim-steps/s 和线程数

hello.py 会直接打印你这台机器的吞吐。先记下这个数，它是你后面所有决策的基准。

第二步 —— 摸自己机器的天花板（半天，0 元）。

uv run python benchmarks/scaling.py unitree_g1 --threads 1,8,24

这个脚本会用单个 mjData 在纯 Python 循环里步进作基线，再逐线程数报吞吐。 它还接受 Menagerie 的模型名直接加载。跑一遍 G1、Go1 和你自己的 XML，你就知道 「我这台机器能撑多少个并行环境」——这是本系列一直缺的一份数据。

第三步 —— 复跑 Go1 PPO 并改一个东西（1–2 天，0 元）。

uv sync --group examples
uv run examples/go1_joystick.py --headless

go1_joystick.py 的常量全摊在文件开头，改起来毫无心理负担： NUM_ENVS, HORIZON, ITERS, EPISODE = 1024, 24, 600, 500， FRICTION = (0.4, 1.0)，COMMAND_RANGE = [1.5, 0.8, 1.2]（前进 m/s、横移 m/s、偏航 rad/s）， 奖励项是一个字典 REWARD = dict(track=1.0, turn=0.5, gait=2.0, pose=0.5, orient=-5.0, ...)。 把 gait=2.0 调到 0 看它会不会变成拖着走，这种一行改动的消融，在这套代码里成本接近于零。

第四步（可选，最有意思的那条）—— 拿 arm_throw.py 改成你自己的臂。 把 CEM 的设计变量从示例的比例 / 齿轮换成你打算打印的连杆长度，跑出来的结果拿去建模。 这条和本期专题那条「改件 → 打印 → 上机」是同一条链路的上游。

坑与风险。

  1. 它是 CPU 并行，不是 GPU 并行。 吞吐量级和 MJX / Isaac 不是一回事。 它的价值是在没有好显卡的机器上把门槛拉到零，而不是在有 A100 的机器上更快。 拿它去和 MJX 比绝对吞吐会得出错误结论。
  2. bind 返回的是活视图，不是快照。 qpos = batch.bind("qpos") 之后 batch.step()， qpos 的内容就地变了。想留历史必须自己 .copy()。这是最容易写出静默 bug 的地方。
  3. expand 改了 MjModel 字段之后，派生常量要用 set_const 重算， 否则你改的摩擦 / 惯量可能不生效，而且不报错。
  4. 部分示例要开窗口（window.py），无头机器上记得加 --headless； 有些示例还需要 uv sync --group examples 才有依赖。
  5. 仓库四天大，API 还会动。 现在写的代码，两周后可能要改。 这不是不做的理由，但别把它塞进你不想维护的东西里。

2 · DogLegs —— 给四足的每条腿多贴一个 IMU，状态估计就换了一个量级；数据集和 C++ 程序都放出来了

一句话：波恩大学 + 武汉大学的 IROS 2025 工作，用机身 IMU + 四个腿载 IMU + 关节编码器 估计机身位姿、速度和 IMU 误差。独立的 C++17 程序，ROS 只用来录包，不用来跑。

项 内容
跑起来 cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j，然后 ./build/DogLegs config/parking_lots.yaml
数据 五个野外序列全部公开（Google Drive）：parking_lots / grass / asphalt_road / construction_site / offroad
输入格式 未压缩 ROS1 v2 包，六个话题：一个机身 IMU + 四个腿 IMU（fl/fr/rl/rr）+ robot_sensor（29 个值：时间戳 + 12 关节位置 + 12 关节速度 + 4 个足端力）
配置粒度 YAML 里连 IMU 噪声（arw 1.2 deg/√hr、vrw 6 m/s/√hr、gbstd 20 deg/hr）、每条腿的杆臂（[0, ±0.03, 0.048]）和安装角都摊开了
基线 同作者另开一个 leg-odometry 仓做对照（只有机身 IMU + 编码器，不加腿载 IMU）

为什么把它放进「硬件 / 软硬兼有」：它的核心命题是一个硬件决策 —— 「多花几十块钱在每条腿上贴一个 IMU 值不值」。而且它把「不值 / 值」的对照实现成了两个独立仓库。 消费级 6 轴 IMU 模块（ICM-42688 一类）单个几十元量级，四个加起来比一个舵机还便宜。

个人怎么切进去（三档）： ① 零硬件：下数据集，编译，跑五个序列，python3 utils/plot.py output/parking_lots 画轨迹， 和 leg-odometry 的结果并排比 —— 半天，0 元，就能自己回答「腿载 IMU 到底带来多少」。 ② 有四足：按 YAML 里的杆臂和安装角字段，在自己的狗上贴四个 IMU，录一段包灌进去。 ③ 改 YAML 做消融：if_estimate_leverarm 现在是 false，打开它看杆臂在线估计收不收敛； 或者故意把 fl_imu_mountingangle 拧 5°，看估计器的鲁棒边界在哪 —— 这类实验作者没做，是空的。

坑：① 数据集在 Google Drive，国内要自己解决网络； ② 必须是未压缩的 ROS1 v2 包，你自己录的包多半是压缩的或者 ROS2 的，得先转； ③ 论文是 IROS 2025，仓是 2026 年 9 月才建的 —— 这不是本周的新研究，是本周才变成可跑的代码。 本系列的标准是「个人现在能不能动手」，按这条它合格；但别把它当最新成果引用。

3 · Palmimo DevKit —— 给 AI agent 装身体的六足桌面机器人，SDK 是 Apache-2.0，机器要 $3,980

先把不好的消息放前面：这台机器 ¥598,000 日元（不含税），约 $3,980，折人民币约 2.8 万 —— 远超本系列「硬件 ≤ 约 5000 元」的线。作为「买来玩」的推荐，它不合格。

放进来是因为它的软件那一半是免费的、开源的、而且可以完全脱离硬件运行， 并且那一半恰好是本系列一直在找的一种东西：一个把 LLM tool call 变成机器人动作的干净参考实现。

架构是一条直线，而且每一段都可以单独拆下来：

Palmimo.forward() → step() → MotionEngine 计算 → {servo_name: tick} → ServoDriver → 硬件
                                                              （或 dry-run 模式下只算不发）
  • MotionEngine 是纯的：步态 + 逆运动学，不碰任何 I/O。这意味着你可以直接把它拿去驱动你自己的六足。
  • palmimo_sdk.mcp 把同一套工具通过 MCP 暴露给 Claude Code / OpenClaw / 任何 MCP 客户端。
  • palmimo_sdk.agent 把 LLM tool call 翻成动作（walk / wave / look / set a face / speak / capture a frame）， 背后的模型是可换的。
  • 18 个内置动作：行走转向（forward / strafe_left|right / rotate_left|right / creep，反相三脚步态）、 手势（wave / bow / clap…）、姿势（stretch / dance / pushup…）。
  • 每一个动作都能在没有硬件的情况下算完（dry-run 优先是设计原则，不是附加功能）。

硬件规格（官网 Specs & pricing 栏，2026-09-14 抓取）：400×300×300 mm / 约 2 kg； 21 轴（腿 3×6 = 18 + 颈 3）；执行器 DYNAMIXEL XC330-M288-T × 21（5 V）； 主控 Raspberry Pi 5 / 16 GB 板载 + 舵机接口板（USB↔串口，1 Mbps）； 2.8 吋圆形触摸屏 480×480（RP2350）；500 万像素 USB 摄像头；ReSpeaker 麦克风阵列 + 3 W 立体声。

个人怎么切进去（不买机器的那条路）： pip 装 SDK（仓库标 pre-release），全程 dry-run 跑一遍 18 个动作，把 MCP server 接到你自己的 agent 上， 看着日志里的 {servo_name: tick} 流出来。然后拿 MotionEngine 去驱动一台便宜得多的六足 （18 个 MG996R 级舵机 + ESP32 的方案，整机一千元以内）。这才是这个仓对个人的真实价值。

坑：① 价格如上，且是「Early Builders / Early Partners」早期价、不含税、按台报价给企业； ② 仓库标 status: pre-release，API 会动； ③ 语音那部分（piper-plus TTS + GTCRN 降噪）是可选依赖，装起来比核心麻烦； ④ 官网主语言是日语，/en 是英文版。

🇨🇳 国内 · flex-fab-agent —— 把「打印执行」这一段往上抬到排产：CP-SAT 求最优排单，agent 只负责对话和审批

是什么。

面向 3D 打印柔性制造的排产智能体，MIT，Docker 一键起。它管的不是「怎么切一个件」， 而是**「十台机器、一堆订单、来了急单、坏了一台，接下来先打哪个」**。 这是本专题第 2 段（打印执行）里一直没被碰过的一层。

能力 怎么做的
数学规划排产 OR-Tools CP-SAT，九大约束（C1–C9），求全局最优排单，不是启发式
对话式智能体 LangGraph 编排 18 种工具：查订单 / 设备 / 库存 / 客户 / 合同，跑排产，审批版本
事件驱动模拟 订单到达 → 前道 → 打印 → 完成，随机注入设备故障和插单
全链路自动化 自动排产调度器 + FIFO 审批 + 幂等防重复（同一订单只被打印一次）
评估 三层评估（工具 / 轨迹 / 语义）+ RAGAS 回归 + 61 个自动化测试文件

为什么这一层重要。 本专题写到第五期，「一句话 → 一个件」这条路已经被走了很多遍。 但只要你不止打一个件 —— 打一批、给别人打、或者做「改件 → 打印 → 上机」的多轮迭代 —— 你撞上的下一堵墙就是排产，而不是建模。这是第一个正面处理这堵墙的开源仓。 而且它把「幂等」和「审批」写进了核心，说明作者被重复打印坑过。

个人怎么切进去（带成本和时间）。

第一步（1 小时，0 元） —— 不碰 LLM 先把架子跑起来：

git clone https://github.com/sjs1919/flex-fab-agent && cd flex-fab-agent
docker compose build && docker compose up -d     # http://localhost:8000
python run_all_tests.py                          # 全量单测，mock LLM，零成本

README 明写 run_all_tests.py 用 mock LLM，零成本，smoke_test.py --skip-llm 也不花钱。 先把这两个跑绿，再决定要不要充值。

第二步（半天，几元） —— 填 .env，接真模型。.env.example 里主备双供应商： PRIMARY_PROVIDER=DeepSeek（deepseek-chat），备用火山方舟。 把 FLEX_FAB_AGENT_DATA_SOURCE 先设成 csv 可以跳过 MySQL。

第三步（1–2 天，0 元） —— 最有价值的改造：把 C1–C9 那九条约束换成你自己打印机的约束 （喷嘴口径、料盘容量、换料时间、夜间不可值守时段）。CP-SAT 那一层是通用的， 约束建模才是你的场景知识。这一步不花 API 费，因为求解器不是模型。

API token 成本（跑一个件大概多少钱）。

这条链路和上面那条是两种成本结构，值得对照着记：

  • 求解不花钱。 CP-SAT 是本地 OR-Tools，排一次产的模型调用次数是 0。
  • 花钱的是对话和审批。 一次「帮我把这批单排一下并给出理由」的往返，量级是 几千到两万 input token + 一千量级 output。按 DeepSeek 公开价目表的量级， 单次在人民币一毛以内；一天几十次对话是几元的量级。
  • 真正的开销在评估。 python -m flex_fab_agent.eval.runner 是三层评估 + RAGAS，用真实 LLM， 一轮下来调用数高一两个量级 —— 这是唯一一处可能让你意外的账单，跑之前先看清楚配置。

⚠️ 以上是量级估算，不是实测账单，具体按 DeepSeek 官方价目表 自行核算（输入是否命中缓存会差好几倍）。

专题分析：这一周这条链路上真正变了什么

1. 「让模型生成几何」和「让模型生成搜索脚本」的成本差了一个数量级，而后者这周第一次有了完整样本。

本专题前几期的成本结构基本都是：一个件 = N 次 mesh 生成 / CAD 代码生成 + M 次几何门重试， token 费按次累加，失败重试直接翻倍。wrist-mount 这条把结构整个翻过来了： 模型只用来（a）从数据手册里提三条约束、（b）写一个 1° 步进的扫描脚本， 剩下 17 个角度的几何计算和 MuJoCo 测量全是确定性代码在跑，一次模型调用都不发。 结果是几毛钱做完一件带完整验证证据的改件。 这条经验可以直接搬到建模段：凡是「在一个参数区间里找最优」的问题， 让模型写搜索脚本，别让模型当搜索器。

2. 「可打印性检查」正在被「可安装性检查」取代 —— 后者才是具身场景真正卡人的地方。

前几期的几何门（idea-to-print 的 19 项 DfAM、SimpleCADforDSH 的单体 / 水密 / 0.2 mm 包络） 回答的都是「这个件能不能打出来」。wrist-mount 关心的三件事 —— 相机到夹爪的保守间隙 ≥ 9 mm、光学参考点到 TCP ≥ 70 mm、螺丝旋入深度 ≤ 4.0 mm —— 没有一条是打印约束，全是装到机器人上之后才会发作的约束。 而且它们的来源是厂家数据手册的具体页码，不是常识。 这提示了自动建模 agent 的下一个明确缺口：一个能从器件手册里抽出装配约束的工具。 目前没人做。

3. 「一句话造一个件」已经饱和，「造一批件」还是空的。

本周专题的两条，一条是把单件做到极致（wrist-mount 的 1° 扫描 + 12 张实物照 + 4 份 CSV）， 一条是直接跳过单件去管批量（flex-fab-agent 的 CP-SAT 排产）。中间那一段 —— 同一个 agent 连续迭代同一个件的 v1→v2→v3，并且记住上一版为什么失败 —— 两边都没做。agentic-additive（Vibe Print MCP） 喊的就是这件事（SQLite 打印历史 + 缺陷检测 + 推荐引擎），但它自己的 ONE_RUN_RESULT.md 里切片那一步标的是 MOCK（没装真切片器），闭环并未真的闭上。 这是整条链路上现在最空的一格。

4. 建模段本周最大的那个仓，值钱的是它顺手做的 URDF 导出。

Procedura（SpatiaOS，210 star，MIT，8 月 27 日） 把文本变成可编辑的参数化程序（命名零件 + 带类型的配合关系），而不是三角面片汤 —— 这是又一个 text-to-CAD。但它有一个别人没有的开关：--motion 把关节运动导出成 OpenUSD / URDF。 也就是说这条建模线自己长出了通往具身的接口。 本期不把它列为专题条目（建模段这四期已经写了四条），但这个能力值得单独记一笔。 顺带它 README 里那个坑非常值钱：OpenSCAD 如果不是 Manifold 后端，会静默退回 CGAL， 一个 hull() 从 1.77 秒变成 1774 秒 —— 看起来像卡死，实际是在算。 装 OpenSCAD 时务必 openscad --backend 确认，发行版打包的 2021.01 版本是没有的。

趋势观察

1. 「开源 = 有代码」这个假设，这周第三次被打破，而且是在同一个会议上。

本周三个 CoRL / ECCV 级别的国内外人形工作同时开仓： X-WBC（CoRL 2026，跨本体全身控制，九个仿真本体 + 四个真机）、 CAP（CoRL 2026，复旦 + TARS + 哈工大，感知退化下的 G1 行走）、 RoboGesture（ECCV 2026）。 前两个的 Release status 全是未勾选的 checkbox，main 分支明说是 placeholder； 只有第三个放了真权重。上一期我写过生数 Motus2 和北大 SEED-UMI 的同一问题 —— 这已经不是偶发，是本季度的常态。

对个人的操作建议很具体：看到 arXiv 别动，先 git clone 然后 ls。 再具体一点：checkpoints/ 目录里文件大小是三位数字节的，那是 Git LFS 指针，不是权重 （RoboGesture 就是这样，但它 git lfs pull 是真的能拉下来 —— 另外两个拉下来也是空的）。

2. 国内的灵巧手这周意外地收敛到了同一款：BrainCo Revo2。

TOP 1 的 RoboGesture，官方验证平台是 Unitree G1 + BrainCo Revo2； 第 3 条的 Vision_Sync_Dexterous_Hand，整个包就是围着 Revo2 的 RS485 协议写的 （外加一条走 Unitree DDS brainco_hand_service 的路）。两个作者、两个完全无关的项目、同一只手。 这和上半年「大家都在接 π0」是同一种现象的硬件版：一个平台一旦被够多的上层工作默认， 它就变成了事实标准，学它的接口比学具体项目更划算。 如果你打算在国内做灵巧手相关的事，Revo2 的 SDK（bc-stark-sdk）值得先摸一遍。

3. 硬件侧连续第二周是「配件周」，而且这次连数据都对上了。

上一期我提出「开源本体多到一定程度后，给现有本体做增量比再造一台更有产出效率」。 这周的证据更足：我用十几个硬件向查询词扫 09-01 之后创建的新仓，star > 0 的整机项目依然是个位数， 而增量类的有一串 —— reBot 的 D405 支架（本期专题）、 Unitree Z1 的双轴打印腕（4× XL330，FreeCAD + STEP + STL）、 Microduck 的 FreeCAD 整机装配 + Excel BOM（70 个零件、39 个 BOM 项）、 Microduck 的国产复刻询价库（四方案对比 + 实价询价 + 打板规格、1548 个文件）、 DogLegs 的腿载 IMU 阵列（本期国外第 2）。 注意后两个都自己标了上游模型是 CC BY-NC-SA，衍生件禁商用 —— 这是复刻圈现在最大的法务暗礁， lingzolabs 甚至明写「本项目不满足 OSHWA/OSI 对开源硬件的通常定义」。这种诚实值得表扬，也值得你抄进自己的仓。

4. 「不要显卡」这件事，这周被两个方向同时证明了。

一个是 mjbatch（本期国外 TOP 1）：4096 个 MuJoCo 仿真跑在 CPU 上， Go1 在五年前的 M1 上一分钟学会走。另一个是 microduck-arena： MuJoCo 编译成 WASM，9 个 ONNX 策略在浏览器里 50 Hz 跑 3v3 机器人足球，零后端、零安装 （https://microduck-arena.com/ 打开就能看）。 方向不同，指向同一件事：具身仿真的算力门槛正在从「有没有 GPU」下沉到「有没有电脑」。 本系列一直把「单卡 A4000 能不能跑」当筛选线，这周开始这条线在很多任务上已经不是约束了。

5. 一个反例，提醒这个榜单的筛选标准还是有用的。 本周还翻到两个看起来对口但过不了线的： FMG 灵巧手 README 承诺 1_hardware/CAD_files/ 和 BOM.csv，实际目录里只有两个 markdown，CAD 和 BOM 都不存在； qqqqya/handled 开源了一整套「已量产夹爪」的 STM32G474 工程 （9261 个文件，带 micro-ROS、固件加密和 SN 工具），但整个仓没有 README，也没有 LICENSE。 后者其实很可惜 —— 内容量摆在那，补一份 README 就是一个很有价值的仓，这是个明摆着的贡献机会。
