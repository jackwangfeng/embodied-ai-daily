## 🇨🇳 国内

### ★ TOP 1（深度）· vla_pi0 —— 把 π₀ 装到自己那台臂上，从遥操作采集一直写到真机部署，中间的坑一个没省

**是什么**

`joykraft/vla_pi0`（51 ★，2026-09-11 建，中文 + 英文双 README）是一份**端到端的单臂 VLA 工程文档 + 可运行代码包**：
基于 OpenPI（π₀）和 LeRobot，覆盖「主从臂遥操作采集 → LeRobot 数据集 → 字段适配与归一化统计 →
π₀ LoRA 微调 → WebSocket 策略服务 → 真机闭环执行」整条链路，用的是 Episode1 单臂（恩培那套主从臂）。

仓里带一段 **1 分 40 秒的原速实机视频**（`docs/media/demo.mp4`），演示抽屉开关和红色方块抓放，
**中间有人为干扰**（反复把抽屉关上、把方块挪走），不是挑好的那一遍剪出来的。

**为什么现在值得做**

过去半年 VLA 的开源程度已经足够了：π₀ 基础权重在 `gs://openpi-assets/checkpoints/pi0_base` 公开，
LeRobot 的采集/数据格式是事实标准，SmolVLA / π₀.₅ 的微调脚本到处都是。
**真正拦住个人的不是模型，是那一堆「不会有人写在论文里」的对齐问题**：
你用 `lerobot.record` 采出来的数据字段叫 `observation.images.fixed`，
而 openpi 的 `LeRobotLiberoDataConfig` 要的是 `observation/image`；
你采集时用角度、训练时用弧度，模型照样收敛，只是上机就抽；
你的动作已经是增量了，配置里又对前 6 维做了一次相对动作转换，于是差分了两遍。

**这个仓最大的价值就是把这些逐条写出来了**，而且写法是「当前配置是这样、你要改成那样、为什么」。
这是我在这个日报里见过的把 VLA 真机部署讲得最具体的中文文档之一。

**个人怎么分步切进去**

这条路分两段，**第一段完全不需要机械臂**：

| 阶段 | 做什么 | 需要什么 | 时间 | 钱 |
|---|---|---|---|---|
| 0 | 把 `docs/media/demo.mp4` 看完，确认这台臂的形态和你的目标接近 | 浏览器 | 10 分钟 | 0 |
| 1 | 只装训练端：`cd openpi_episode1_student && GIT_LFS_SKIP_SMUDGE=1 uv sync`，跑 `uv run python -c "import jax; print(jax.devices())"` 确认看到 GPU | Linux + CUDA 12 驱动，Python 3.11 | 半天 | 0 |
| 2 | **拿别人的公开 LeRobot 数据集**（HF 上 SO-101 的一堆）走一遍「字段适配 → `compute_norm_stats.py`」，验证你能把任意 LeRobot 数据喂进 openpi | A4000 16G 够（这一步只读数据） | 1 天 | 0 |
| 3 | LoRA 微调。**这一步 16G 不够**，见下面「坑」 | 云上 4090/A100 | 1–2 天挂机 | ¥50–200 |
| 4 | `serve_policy.py --port 6006` 起策略服务，用 `openpi_client_test.py` 在没有真机的情况下打一发假观测，确认服务能返回 50×7 的动作块 | 任意机器 | 2 小时 | 0 |
| 5 | 真机闭环（只有这一步要臂） | Episode1 或任何能凑出「6 关节 + 夹爪 + 两路相机」的臂 | 数天 | 看你有什么 |

**第 2 步是我最推荐的切入点**：整条链路里最容易出错、也最没人写的就是字段映射，
而它**零硬件、零 GPU 成本**，产出是一份「我把 X 数据集接进 openpi 的 RepackTransform 写法」——
这东西发出去大概率有人用。

具体要改的地方仓里写明了：`openpi_episode1_student/src/openpi/training/config.py` 里那个
`enpei_robot_demo_drawer_low_mem_finetune`，`RepackTransform` 改成：

```python
{
    "observation/image": "observation.images.fixed",
    "observation/wrist_image": "observation.images.handeye",
    "observation/state": "observation.state",
    "actions": "action",
    "prompt": "prompt",
}
```

同时在 `dataclasses.replace(...)` 里设 `action_sequence_keys=("action",)`。
**改之前先看你数据集的 `meta/info.json` 里的 `features`，别照抄。**

**坑**

1. **显存：默认 `batch_size=32`，A4000 16G 跑不动 π₀ LoRA。** 作者的 `weight_loader` 路径写的是
   `/root/autodl-tmp/pi0_base/params`——这是 AutoDL 的路径，说明作者自己也是租卡跑的。
   实测口径我没有，但 π₀ LoRA 在 24G 卡上通常要把 batch 压到 4–8。
   **按 20000 步、租一张 4090 算，¥2–3/小时 × 10–20 小时 ≈ ¥50–200 一次。**
2. **微调权重没有公开下载。** README 原话：「微调权重目前没有公开下载链接，未来是否发布及发布地址待确定」。
   所以这个仓是**流程可复现，结果不可直接复现**——你必须自己采数据、自己训。
   如果你的目标是「跑通一个 demo 就行」，先去看 LeRobot 官方的 SmolVLA 教程，成本低得多。
3. **根目录没有 LICENSE 文件。** `lerobot/` 和 `openpi/` 两个子目录各自带上游的 LICENSE（Apache-2.0），
   但作者自己写的适配代码（`enpei_scripts/`、`robots/enpei_follower/`、`teleoperators/enpei_leader/`）
   处于无明示许可状态。**要拿去做任何公开的事，先去提个 issue 问许可。**
4. **`robots/enpei_follower/episode_server.py` 不是控制服务，是 TCP 客户端。**
   README 明说了「配套控制程序需要另行准备」，默认连 `localhost:12345`。
   没有这台臂的配套控制程序，第 5 步是走不通的——**别以为 clone 下来就能驱动任意机械臂**。
5. **两个端必须用独立 Python 环境**：训练端 Python 3.11 + `jax[cuda12]==0.5.3` + `torch>=2.7`，
   机器人端 Python 3.10 + `torch==2.6.0`。装一起必挂。
6. `--fps=30` 是控制目标频率，**不代表模型推理能到 30 Hz**。客户端把图缩到 224×224、开独立线程请求动作块，
   真实推理频率取决于你那张卡和网络。

### 3 · sixdof-arm —— 自己画的臂不知道 DH 参数怎么办：写脚本从 STL 网格里把六根关节轴求出来

- **是什么**：`315nailong/sixdof-arm`（2 ★，09-08 建，09-11 推）。C++17 + Eigen，**不依赖 ROS，不需要真机**。
  README 的开场白值得原样引用：「我在 SolidWorks 里画了台六轴臂，画完发现一个问题：我不知道它的运动学参数。
  量产的 UR5 可以抄官方文档，我这台不行，参数只存在于我自己的装配图里。」
- **它做了什么**：Python 脚本读 STL，从网格里求出 6 根关节轴，转成标准 DH 参数；
  然后补上解析逆解、笛卡尔直线插补，最后用 C++ 算出的关节角驱动 STL 模型做动画。
  仓里 `models/stl/` 直接放着那台臂的七个零件 STL（底座、大臂、小臂、法兰…），有 LICENSE，有 `tests/`。
- **为什么值得看**：它给了**四个自校验数字**，这在个人项目里很少见——

  | 检查 | 结果 |
  |---|---|
  | 从 CAD 反推的 DH 与手工测量的偏差 | 0.014 mm |
  | 200 组随机位姿正逆解往返误差 | ~1e-16 m |
  | 笛卡尔直线插补的到位偏差 | 1.2e-16 m |
  | C++ 与 Python 两套实现的末端位置偏差 | 8.5e-7 mm |

  最后一项作者自己解释了动机：「C++ 和 Python 各写了一遍 DH，不校一下不放心。两边参数要是漂了，动画照样能画出来，看不出问题。」
  **这句话是整个仓最有价值的一句**——它描述的正是仿真类项目最常见的静默失败。
- **怎么切进去**：`cmake -S . -B build && cmake --build build -j && ctest --test-dir build`，
  只要 C++17 + CMake ≥3.16 + Eigen3（`libeigen3-dev`）。**十分钟能跑完，零成本，零硬件。**
  `include/robot/` 是纯头文件，整个拷走就能用在别的项目里。
  真要做贡献：仓里只有 `arm6.hpp`（作者那台）和 `ur5.hpp`（参考），
  **加一套 SO-101 或 Piper 的 DH 参数并跑通那 200 组往返测试，是个一天量级、结果客观可验的 PR。**
- **坑**：解析逆解只对特定构型成立（球腕/三轴交于一点这类），换一台臂不一定有闭式解；
  README 没写这台臂的构型假设，套用前先自己确认。Python 脚本还额外要 NumPy + matplotlib。

→ **原始出处**：<https://github.com/315nailong/sixdof-arm>

## 🌍 国外

### ★ TOP 1（深度）· real2sim-droid —— 一条真机录像进去，一个 MuJoCo 数字孪生出来，全自动，一张卡三分钟

**是什么**

`Pro2004-a11/real2sim-droid`（MIT，09-14 建）。输入是**一条 DROID 数据集的真机 episode**
（Franka + Robotiq 2F-85，三台标定过的 ZED 相机），输出是一个 MuJoCo 场景：
**同一条轨迹、同样的三台相机视角**重放，物体位置由 SAM2 掩码 + 深度反推，
夹爪是**物理仿真的抓取**（不是把物体焊在手上），每帧带掩码 / 米制深度 / 6-DoF 位姿 / 接触力标注。
**全程无人在环。**

**为什么现在值得做**

Real2Sim 这个方向以前是「有大规模真机采集能力的组才玩得起」的东西。
今年变了三件事：DROID 的原始 episode 可以按需单条 HTTPS 下载（约 110 MB），
KarlP/droid 放出了改进后的标定 JSON，SAM2.1 和 Depth-Anything-V2 都是 Apache-2.0 的小模型。
**结果就是：一条真机数据 + 一张消费级卡 + 三分钟 = 一个可以做反事实实验的数字孪生。**

这对个人特别有用的地方在于——**你可以拿它给 VLA 策略做评测环境**，
而不必自己有臂。作者在 README 里点名了这个用途：「a policy-evaluation loop through the real cameras」。

**这个仓真正难得的地方不是它能跑，是它把每个数字都量了**，而且量的方式是「在没有拟合的那个维度上打分」：

| | IRIS `7dfa2da3+2023-05-11`（把马克笔从碗里拿出） | GuptaLab `553d1bd5+2023-05-19`（方块叠方块） |
|---|---|---|
| FK 门（DROID 末端位姿 vs MuJoCo FK） | 1e-5 mm | 1e-5 mm |
| 机器人掩码 IoU，外部相机 2（中位数） | **0.92** | **0.76** |
| 物理抓取：夹持成功 / 放置误差 | **闭合步的 100%** · 2.4 cm | **100%** · 0.8 cm |
| **反事实**（物体挪 5 cm，轨迹不变） | 夹住 0% · 24 cm | 夹住 2% · 5.9 cm |
| 跨视角物体摆放（ext1 拟合，ext2 重检测） | 中位 4.0 cm | n/a（方块在 ext2 里太小） |

**注意那一行反事实**：物体挪 5 cm、轨迹照旧，抓取成功率掉到 0%。
这不是 bug，**这是仿真器在正确地报告「这条轨迹确实依赖物体在原位」**——
一个会把反事实也抓住的孪生体，说明它根本没在物理上做手脚。
一个项目敢把「我在这个条件下失败」印在 README 的表格里，可信度比十张对齐得很好的叠图都高。

**个人怎么分步切进去**

```bash
git clone https://github.com/Pro2004-a11/real2sim-droid.git && cd real2sim-droid
python -m venv .venv && . .venv/bin/activate
pip install torch --index-url https://download.pytorch.org/whl/cu124   # 先装 CUDA 版
pip install -e .

export REAL2SIM_DATA=./data
python scripts/fetch_droid.py --calib     # 改进标定 JSON，约 330 MB
python scripts/fetch_droid.py --episode IRIS+7dfa2da3+2023-05-11-14h-12m-38s   # 单条 episode，约 110 MB，走 HTTPS 不用 gsutil

export MUJOCO_GL=egl                      # Linux 无头必须
python -m real2sim all --episode IRIS+7dfa2da3+2023-05-11-14h-12m-38s          # 作者实测 4070 Ti 约 3 分钟
python -m real2sim counterfactual --episode IRIS+7dfa2da3+2023-05-11-14h-12m-38s
python -m real2sim showcase --episode IRIS+7dfa2da3+2023-05-11-14h-12m-38s
```

| 阶段 | 做什么 | 时间 | 成本 |
|---|---|---|---|
| 1 | 复现作者那两条 episode，对比 `compare/metrics.json` 里的数字和 README 表格 | 半天（含 ~450 MB 下载） | 0 元 |
| 2 | 用 `python scripts/fetch_droid.py --list-candidates` 列出**两台外部相机都有真值标定且有立体视频**的 episode，挑 10 条批量跑 | 1 天 | 0 元 |
| 3 | **把「跨视角物体摆放误差」的分布在这 10 条上统计出来**，报中位数 / 90 分位 / 失败原因分类 | 1 天 | 0 元 |
| 4 | 接一个策略进去：起一个 π₀ / SmolVLA 服务，用孪生体的三路相机做闭环评测 | 数天 | 0–少量 |

**第 3 步是本期国外最值得抢的活。** 作者自己只跑了两条 episode（README 的「Limitations」第一条就是
「Two episodes so far」）。DROID 里符合条件的 episode 有的是，**把这个管线的统计特性做出来，
基本等同于替这个项目写了评测章节**，而且纯下载 + 纯计算，零硬件、零 API 费。

**显存与本机可行性**：管线里最重的是 SAM2.1-hiera-small 和 Depth-Anything-V2-Small，都是小模型；
MuJoCo 渲染走 EGL。**A4000 16G 跑得动**，只是比 4070 Ti 慢一些。作者标的 3 分钟是 4070 Ti 的数。

**坑（作者自己列了一节 "Traps we hit"，这里挑最要命的几条）**

1. **运动学覆写的手臂在 MuJoCo 的接触求解器里是隐形的**——物体永远不会被拿起来。
   手臂必须是动态的（重力补偿 + 4 倍增益跟踪，能把录制轨迹跟到 1.25° 以内）。
   这一条是所有做 real2sim 的人都会踩的。
2. **2F-85 的指垫 body 比指垫 geom 靠后 19 mm**，且闭合时指垫沿接近方向还走约 1 cm。
   抓取点要从**远端指垫 geom 在记录的闭合开度下**读，不能读 body。
3. **一个指垫先碰到自由物体会把它弹飞**，第二个指垫还没到。要把物体按住到两侧都接触为止。
4. **DROID 的时间戳是 epoch 毫秒**，帧 *i* 对应步 *i*，**相机比机器人状态读数早约 54 ms**——渲染要按相机的时间来。
5. **SAM2 的自动掩码在 CUDA 上每次跑结果会飘**，会静默改变重建出来的场景。仓里按图缓存掩码来压住这个。
6. MuJoCo 相机的 `principal_pixel = [w/2 − cx, h/2 − cy]`（x 的符号不是直觉那个）；纹理必须 PNG；
   视觉 geom 必须 `density=0`，否则会额外加质量。
7. **ext1 那路的机器人 IoU 只有 0.31，作者明说这是度量假象**——机器人在画面边缘，SAM2 只分出了小臂。
   别拿这个数去比较。
8. 代理物体只有盒/柱/胶囊（碗有个空心特例），**布料被当成刚性平板**；只有容器和被抓物体与机器人碰撞。
9. ZED SDK 没用上，深度是 SGBM + Depth-Anything-V2 融合，**区域性偏差有几厘米，只用了相对高度**。
   `.svo` 的 `zed` 后端写了但**没测过**。

DROID（CC BY 4.0）、KarlP/droid 标定、MuJoCo Menagerie 的 Panda（Apache-2.0）和 2F-85（BSD-2）、
SAM 2.1 与 Depth Anything V2（Apache-2.0）、Poly Haven 纹理（CC0）。

### 2 · StationeryBench —— 五个「桌上文具」双臂任务，写成了可安装的包，**不用真机也能先跑通整条评测流水线**

- **是什么**：`robocurve/stationerybench`（MIT，4 ★，09-10 建）。五个双臂操作任务：
  **拔马克笔帽 / 从盒里取橡皮并合盖 / 从一摞便利贴里抽出中间那本 / 把回形针倒进举起的碗 / 两臂之间用纸杯传递直尺**。
  每个任务一套固定摆放、20 次重复、二值成功判定。
  建在 [Inspect Robots](https://github.com/robocurve/inspect-robots) 上。组织的自我介绍是
  「We measure and report frontier robotics capabilities to the public.」
- **为什么它比大多数 benchmark 更适合个人**：**它把「没有机器人」当成一等公民**。
  装完就注册五个任务、一个 `stationery` embodiment 和三个 mock policy，
  其中 `stationery_scripted` 读特权状态、必定成功——**它不测模型能力，它测的是你的评测流水线通不通**。

  ```bash
  uv pip install "stationerybench @ git+https://github.com/robocurve/stationerybench"
  inspect-robots list tasks
  inspect-robots run --task stationerybench/uncap_marker --policy stationery_scripted \
      --embodiment stationery --epochs 2
  ```

  这三行在任何一台笔记本上都能跑完，**零硬件、零 GPU、零 API 费**。
- **任务文档的质量是这个仓真正的资产**：每个任务都有**摆放照片、清单、逐字指令、分阶段评分细则、
  以及人类演示的 MP4**（`docs/assets/*-human.mp4`）。物体规格精确到「黑色 Sharpie 细头油性笔，带帽」
  「约 30×22×7 cm 的布面翻盖书型盒」「三块 3×3 英寸收缩膜包装的便利贴方砖」「约 15 cm 的轻质陶瓷碗」。
  **这意味着你可以用几十块钱的文具，在自己桌上把这套场景 1:1 复现出来。**
- **怎么切进去**：
  ① 半小时——跑通 mock，确认 `inspect-robots view logs/` 能看到那份 JSON（20 个 epoch 写在同一个文件里）；
  ② 一天——按任务文档买齐五套文具，拍自己的摆放照片，**对照官方照片写一份「复现偏差记录」**；
  ③ 有臂的话——接你自己的 embodiment adapter（仓里 `src/stationerybench/embodiment.py` 是模板），
  官方给的是 YAM 双臂的适配（`inspect-robots-yam 0.36`）。
- **坑**：
  1. **`stationery_noop` 和 `stationery_random` 无人值守跑必须加 `--no-prompt`**，
     否则每个非确定性 epoch 结束后终端会停下来等你输入判定。mock 永远不会自己报失败终止。
  2. **`partial` 算失败。** 官方报告里是从录像打 0–4 分阶段分，这个包只记操作员的二值判定，
     评分细则保留但不记数字阶段，**和论文的 CSV/断点续跑流程不等价**——README 专门有一节
     "Differences from the published report" 说这事。
  3. 默认 120 s 时限对应报告里的 VLA 条件（10 Hz × 1200 步）；**agent 条件是 90 s**，要复现得加 `-T max_seconds=90`。
  4. 真机跑的时候手臂**会带力矩保持 home 位姿**等你摆物体。README 反复提醒：等手臂停稳再伸手，急停放在手边。
  5. 仓库本身的 CI 门很硬（覆盖率 100%、mypy strict、Ruff D1 要求公开接口都有契约 docstring），
     **提 PR 前先本地跑那条 `uv sync --locked ...` 长命令**，不然过不了。

### 3 · humanoid-companion —— 本地跑的语言模型当脑子，PPO 策略当腿，**没有 GPU 也能看它走**

- **是什么**：`YauhenBichel/humanoid-companion`（Apache-2.0，09-11 建）。
  一台会说话的小人形：用强化学习策略**走路**，说话时**挥手、点头、跳舞**，
  有一张带口型同步的**脸**，用你自己跑的语言模型（Ollama / llama.cpp / vLLM / 任何 OpenAI 兼容 API）当大脑。
  身体目前是 MuJoCo 里的 ROBOTIS OP3，**但跑的就是真机会跑的那个控制回路**，目标是把同一份代码放到一台真的 50 cm 机器人上。
- **为什么值得看（而且和市面上的「LLM 控制机器人」demo 不一样）**：
  **它把「不信任模型输出」写进了架构**。README 里那张表原话：
  语言模型只能**请求**走路，走路规划器才决定走不走；模型的回答按 JSON schema 解析、校验、
  **夹到训练时的指令范围和限速内**；停止词根本不送进模型；**任何解析失败一律等于「站着不动」**。
  手势是叠加在行走策略上的头/臂偏移，**腿留给策略保平衡，而且每个手势都单独测过稳定性才被允许**
  （`docs/gesture-stability.md`）。
  这套「不可信输出 → 确定性闸门 → 安全降级」的结构，就是本日报反复说的那件事的一个干净样本。
- **算力门槛极低**：走路策略是 MuJoCo Playground（MJX）里 PPO 训出来、**导出成纯 NumPy** 的
  （`policies/op3_walk.npz`，300 KB，与 Brax 对齐到 1e-5）。50 Hz 控制回路带安全停：
  倾角、关节限位、看门狗超时、急停。**跑它不需要 GPU**（macOS / Linux，Python 3.12 + uv）。
- **怎么切进去**：
  ```bash
  git clone https://github.com/YauhenBichel/humanoid-companion && cd humanoid-companion
  uv sync --frozen
  uv run humanoid-sim --vx 0.5 --seconds 10 --record walk.mp4    # 只看它走，不用大模型
  ollama pull llama3.1:8b && export HUMANOID_LLM_MODEL=llama3.1:8b
  uv run humanoid-talk --open                                     # 脸和身体并排出现在浏览器里
  ```
  **半小时能看到东西。** 想深入就去改 `train.py`（Brax PPO，CPU 或 GPU 都行，
  环境里已经带了推挤、动作延迟、编码器偏置、域随机化）。
- **坑**：
  1. **身体是仿真的**，README 自己写明了「Today its body is a simulated ROBOTIS OP3」。
     想上真机你得自己有一台 OP3 或等价的 20 自由度小人形——**这部分不在 5000 元预算内**。
     所以本条按**软件**算。
  2. 语音要另外起服务（Kokoro 的 `ghcr.io/remsky/kokoro-fastapi-cpu`，走 OpenAI speech API）；
     不起也能用，只是变成字幕 + 动作。
  3. 演示视频里那段白俄罗斯语告别用的是作者自己的 [belarusian-tts](https://github.com/YauhenBichel/belarusian-tts)，
     换语言要自己找声音。
  4. 本地 8B 模型输出 JSON 的稳定性是这套东西的实际瓶颈——**解析失败的降级是「站着不动」，
     所以模型不行的时候表现就是「它不动了」，不是报错**。调试时先看解析日志。

### 🌍 国外 · cadxray —— 把 FreeCAD 变成 agent 能「看进去」的东西：36 个工具，从诊断红草图一直到 FEM 和打印取向

**是什么**

`WaveSimm/cadxray`（MIT，09-10 建，09-13 推）。一个 **MCP 服务器 + FreeCAD 插件**的组合：
插件跑在 FreeCAD 里（`freecad/cadxray`），桥接跑在 AI 工具那边（标准 MCP stdio），
两者**只通过 `127.0.0.1:9877` 通信，不对外**。支持 FreeCAD 1.0.x / 1.1.x（在 1.1.3 上验证过），
Windows / macOS / Linux 都行。任何支持 MCP 的客户端都能接：Claude Code、Claude Desktop、Cursor、VS Code、
Windsurf、Codex CLI、Gemini CLI。

装它就两行：

```bash
uvx --from git+https://github.com/WaveSimm/cadxray#subdirectory=bridge cadxray install
claude mcp add --scope user cadxray -- uvx --from git+https://github.com/WaveSimm/cadxray#subdirectory=bridge cadxray
```

第一行把插件装进 FreeCAD 的 Mod 目录，第二行注册。**重启 FreeCAD 后报告视图里会打印
`[CAD X-ray] 서버 시작 http://127.0.0.1:9877 (툴 36개)`**（README 是韩语的，英文版在 `README.en.md`）。
装不上跑 `cadxray doctor`，会逐项告诉你插件装没装、FreeCAD 服务连不连得上、版本对不对。

**它凭什么比一般的 FreeCAD MCP 强**

关键在于**它不让模型直接吐坐标**。看这几个工具的设计：

| 工具 | 做的事 |
|---|---|
| `classify_faces` | **STEP → 参数化的第一步**：判定每个面到底是什么（平面/圆柱/圆锥/球/自由曲面）。**BSpline 面会被采样后拟合**，所以「假自由曲面」能被还原成圆锥并给出轴、顶点、半角 |
| `section_profile` | 在某个高度切截面，直接输出**草图可用的 2D 线/弧/圆**（先在 3D 里把孔、沉头、倒角填掉，只留外轮廓） |
| `build_features` | 在 Body 上一次一个特征地堆 草图 + Pad/Pocket/Groove/Revolution/Fillet/Chamfer，**每步 recompute + 校验**；`profile.section` 直接描原始截面，**坐标不经过 LLM**；参数进 Spreadsheet |
| `compare_shapes` | 体积/面积/包围盒差 + 模糊差集碎片及其包围盒——**告诉你重建错在哪儿** |
| `suggest_sketch_fixes` | 约束修复提案：接近/开口端点合并、缺失的水平/竖直/相等、删冗余或冲突约束、给剩余自由度补尺寸。**每条都在副本上试过，附带效果（DoF、状态）和置信度，什么都不自动改** |
| `check_printability` | 给定材料/喷嘴/热床配置，查薄壁、悬垂与桥接（支撑面积）、小孔与水平孔、超出热床、首层接触 → 打分 + 问题清单 + 修复候选，`paint=True` 直接按结果给面上色 |
| `apply_print_fixes` | **把 DfAM 改件做成 PartDesign 特征**：象脚倒角、竖直孔补偿、水平孔泪滴化、薄面加厚、悬垂下 45° 填充、超尺寸拆件 |
| `setup_analysis` / `run_analysis` | 材料 + 固定面 + 载荷 + Gmsh 二阶网格 + CalculiX，一次调用；跑完给最大 von Mises 应力及位置、最大位移、**安全系数**、结论，并把应力云图画在 3D 视图里 |

**一句话：它把「模型负责说要什么、引擎负责保证怎么做对」这条原则，落到了 FreeCAD 的 API 层。**

**测过什么（README 的 "What it has been tested on" 一节）**

- 287 个 handler 测试无头跑：`freecadcmd tests/in_freecad/test_handlers.py`，4 秒
- 一个 80 零件的厂商装配体（3149 个面）：带沉头和倒角的孔、螺纹提示、零干涉、按钢密度 8.5 kg
- **STEP → 参数化重建**：一个支架做到 **0.0 mm³ 体积差**；一个 44 面夹爪钳口（BSpline 过渡、燕尾槽、倒角唇）做到 **0.0004%**。
  先手写一遍，再**只用那四个工具**重做一遍：12 个特征、每个草图全约束、`compare_shapes` 判定 *identical*。
  8 个 BSpline 过渡面被识别成圆锥（轴、顶点、59.63° 半角，残差 6.6e-5）
- **整个装配体参数化重建**：80 零件里的 20 种零件全部重建（15 个完全一致、4 个吻合、1 个因自由曲面圆角差 0.14%），
  再用 `align_shapes` 放置 80 次，零干涉，**3.5 分钟**
- 一个 5758 面片的线轴导向件 STL 被重建到**每个网格顶点误差 0.03 mm 以内**，含 M44.5×2 外螺纹

**个人怎么切进去**

| 步 | 做什么 | 时间 | 花费 |
|---|---|---|---|
| 1 | 装好，跑官方 [10 个实操练习](https://wavesimm.github.io/cadxray/practice/01-plate-holes/) 的头两个 | 1 小时 | 几毛钱 token |
| 2 | 拿一个你从立创/GrabCAD 下的**厂商 STEP**，用 `classify_faces → section_profile → build_features → compare_shapes` 重建成参数化件 | 半天 | 见下 |
| 3 | 对同一个件跑 `check_printability` + `suggest_orientation` + `apply_print_fixes`，**把改前改后的支撑面积差记下来** | 2 小时 | 少量 |
| 4 | 跑 `setup_analysis`/`run_analysis` 拿安全系数，和 09-15 写过的 [cadloop](./2026-09-15.html)（Gmsh + FEniCSx）对同一个件互相印证 | 1 天 | 少量 |

**第 4 步是个真空位**：cadxray 用 CalculiX，cadloop 用 FEniCSx，**两条链路在同一个件上给出的安全系数差多少，
现在没人量过**。这是一天量级、纯软件、结论客观的活。

**成本：跑一个件大概多少钱**

这条链路的开销主要是 **API token，不是耗材**。按我对工具回合数的估算（**是估算，不是实测**）：

- 一个中等复杂度的零件（10–15 个特征）做「STEP → 参数化 → 可打印性 → 改件」，
  大约 **40–80 次工具往返**。每次回包硬上限 100 KB，但实际多数在几 KB。
- 按 Sonnet 档（约 $3/M 输入、$15/M 输出）粗算：输入累计 150k–400k tokens、输出 15k–30k tokens
  → **单件约 $1–3**（约 ¥7–22）。开了提示缓存能再省一截。
- 换 Opus 档大约是 5 倍。**建议：探索阶段用便宜模型跑工具循环，只在最后的判断题上换大模型。**
- `check_printability` / `estimate_print` / FEM 这几个是**纯本地计算，不花 token**——
  贵的永远是「让模型看懂几何然后决定下一步」那部分。

**坑**

1. **`through`（通孔判定）是启发式的**——开进一个凹槽的孔可能被读成通孔。
2. **厂商 STEP 里不含螺纹模型**，`thread_hint` 只按直径推断。
3. **STL/OBJ 网格没有面和实体**，孔/干涉类工具读不了。要走 M9 那条路：
   `import_mesh → analyze_mesh → section_profile → build_features → compare_shapes`。
   **绝对不要对 `makeShapeFromMesh` 出来的实体调 `compare_shapes`**（布尔运算 10 分钟起），要直接传网格。
4. **只在 FreeCAD 1.1.3 / Windows 上实跑验证过**。1.0.x 的代码路径是对着 1.0.2 源码核过的，**没有实跑**。
5. README 主体是韩语，英文在 `README.en.md`；`docs/api-notes.md` 里记了每条依赖的 FreeCAD API 事实和验证版本
   （比如 `solve()` 在两个值不同的尺寸约束下返回 `-4` 而不是 `-3`、失败求解后 `FullyConstrained` 会残留 `True`）——
   **这份笔记本身对任何写 FreeCAD 自动化的人都有用**。

### 🇨🇳 国内 · Auto SolidWorks —— 把一张工程图 PDF 丢进去，本机 SolidWorks 里长出参数化零件

**是什么**

`qdaia/Auto-SolidWorks`（代码 MIT，09-06 建，09-09 推，C#）。
**Windows + 本机 SolidWorks + 9 个 MCP 工具**的 Codex 插件：
用自然语言**或工程图**创建和修改参数化零件、装配体，保存原生模型和 STEP/STL。

工具流程是固定的：
`cad_get_capabilities → cad_read_drawing（有图时）→ cad_create_model_plan → cad_build_model → cad_inspect_model`。
装配、型材、连接诊断另有 `cad_build_assembly`、`cad_list_weldment_profiles`、`cad_executor_health`。
**计划直接传 typed draft / IR，不通过任意 shell 或脚本接口操作 CAD**——这一点和 cadxray 的
`execute_code`（在 FreeCAD 里跑任意 Python）是两种不同的安全取舍。

**测试案例摆在 README 第一屏**：一个 **PPL001M45.1-2 空心轴**，以多视图工程图为输入，
含阶梯轴段、侧面长窗口、键槽、环槽、端面孔组，**原始 PDF 图纸和三张模型视图都放出来了**。
而且作者紧跟一句：「本案例展示提供的图纸与模型效果；**截图不作为全部尺寸、公差和图纸等价性已通过验证的证明**。」
——这种自我设限在国内开源项目里不常见，加分。

**能力范围**（README 原表）：草图（矩形/圆/弧/多边形/槽/椭圆/样条 + 约束与驱动尺寸）、
零件（拉伸/切除/旋转/孔/圆角/倒角/抽壳/拔模/肋/放样/扫描）、阵列镜像布尔分割、
**钣金（基体与法兰、展开）/ 焊件（型材构件与裁剪）/ 曲面**、装配（插入、配合、干涉检查）、
图纸输入（本地图片与 PDF、**OCR 候选**、分区/旋转提示、尺寸绑定检查）、
输出 SLDPRT / SLDASM / STEP / STL / SLDDRW / PDF。
`cad_export_drawing` 还能从已保存零件导出**第一角法 A3 原生工程图 + PDF**，四视图、原生尺寸、参数表，
**最多支持 44 个源参数**。

**为什么它值得国内这一格**

国内制造业的存量资产是**二维工程图**，不是 STEP，更不是 Fusion 的参数化历史树。
本日报之前写过的 text-to-CAD 项目（[cadjson](./2026-09-15.html)、[SimpleCADforDSH](./2026-09-12.html)、
[idea-to-print](./2026-09-13.html)）全都是「从零生成」，
**Auto-SolidWorks 是第一条把「已有图纸 → 参数化模型」这条路做出可运行产物的**。
配合 cadxray 的「STEP → 参数化」，这一周等于两个方向都补上了入口。

**个人怎么切进去**

1. 装 .NET 9 Windows Desktop Runtime（x64）+ 支持插件的 Codex CLI，
   从 [Release 页](https://github.com/qdaia/Auto-SolidWorks/releases)下 `auto-solidworks-0.5.4-windows-x64.zip`，
   解压后 PowerShell 跑 `install.ps1`。**半小时。**
2. 先用文字试最简单的：「创建一个 80 × 50 × 10 mm 的矩形板，中心有一个直径 10 mm 的通孔，保存 SLDPRT 和 STEP」。
   **确认它真的起了 SolidWorks 并存出了文件。**
3. 再喂图。**推荐从自己画过、知道正确答案的零件图开始**，这样你能判断 OCR 读错了没有。
4. 产出建议：**把「同一张图，模型出来的尺寸 vs 图纸标注」逐条对一遍，做成一份误差表**。
   作者自己没做这件事（他明说了截图不构成等价性证明），**这是个现成的、结论客观的贡献位**。

**成本：跑一个件大概多少钱**

- **图纸输入这一步是视觉 token 大户**。一张 A3 工程图要看清尺寸标注，
  分辨率不能压太狠——按高分辨率单图约 2–4k 视觉 token 估，
  `cad_read_drawing` 可能要分区多看几次，一个零件在读图上就可能花 **10k–30k 输入 token**。
- 加上 plan / build / inspect 三轮的工具往返，一个中等复杂度零件我估在
  **输入 80k–250k tokens、输出 10k–25k tokens**，Sonnet 档 **约 $0.5–1.5（¥4–11）**。
- **纯文字驱动（不读图）会便宜一个量级**，大约 $0.05–0.2 一个件。
- **同样是估算，不是实测。** 作者没给 token 统计——**顺带说，「跑一个件到底花多少钱」这个数字，
  本专题写了七八期，还没有任何一个项目自己报过。**

**坑**

1. **最大的坑：SolidWorks 是商业软件，且必须本机安装并激活。**
   插件包不分发 SolidWorks 程序或 interop DLL，安装脚本是从你本机 SolidWorks 目录读 interop 组件的。
   **代码是 MIT，但这条链路整体不是零成本的**——没有 SolidWorks 许可的人，这条直接跳过，去看上面的 cadxray（FreeCAD 免费）。
2. **只支持 Windows。**
3. **GitHub 自动生成的 "Source code (zip)" 不含编译后的运行程序**，直接把仓库加成远程插件源也不会自动下载运行程序。
   **普通用户必须用 Release ZIP。**
4. **当前版本不生成物理螺旋螺纹**（攻丝孔用底孔 + 原生装饰螺纹），**也不完整解释任意 GD&T**。
5. **OCR 数字必须结合原图判断**，作者原话。未声明单位时按 mm。关键尺寸缺失或冲突时会要求澄清。
6. 本机开发验证用的是 **SolidWorks 2025**，其他版本要自己验。
7. **「几何创建、重建和测量成功，不能自动证明与任意工程图等价」**——这句是作者自己写的，
   请把它当成使用这类工具的通用免责条款。
8. 云端 AI 会话怎么处理你的图纸和提示，取决于客户端——**作者明确拒绝把这个项目描述成完全离线**。
   涉密图纸别往里丢。

→ **原始出处**：<https://github.com/qdaia/Auto-SolidWorks>
相关：[Release（0.5.4 Windows x64）](https://github.com/qdaia/Auto-SolidWorks/releases)

### 📌 专题分析：这周这条链路上真正变了的东西（4 点）

**1. 「逆向」这一格，一周之内被两边同时补上了，而且补法完全不同。**

过去这个专题写的项目，输入几乎都是「一句话」或「一张参考图」——**从零生成**。
这一周出现的两条都是**逆向**：cadxray 是 **STEP/STL → 参数化特征树**，Auto-SolidWorks 是 **二维工程图 → 参数化模型**。
这个转向是有道理的：从零生成的东西你不敢用在会承力的地方，而**逆向的终点是可验证的**——
cadxray 的 `compare_shapes` 能给出「体积差 0.0 mm³」，Auto-SolidWorks 的尺寸能逐条对回图纸标注。
**一个能被证伪的产出，比一个好看的产出有用得多。**

值得一并记住的是 cadxray 那条硬数据：**44 面的夹爪钳口，只用四个工具重建到 0.0004% 体积差，
8 个 BSpline 过渡面被识别成圆锥（残差 6.6e-5）**。
这说明「厂商 STEP 里那些看起来是自由曲面的东西，大部分其实是规则面」——
对做开源机械臂改件的人来说，这意味着**你下载的那个电机座 STEP，很可能是可以被完整参数化的**。

**2. 「模型不吐坐标」正在变成这条链路的共识写法。**

cadxray 的 `build_features` 里那句 `profile.section` 直接描原始截面、**坐标不经过 LLM**，
和 Auto-SolidWorks 的「计划直接传 typed draft / IR，不通过任意 shell 或脚本接口操作 CAD」，
说的是同一件事：**让模型产出意图和约束，让引擎产出几何。**
这和本专题 09-15 写过的 [cadjson](./2026-09-15.html)（选择器不按索引、一个零件一个 JSON）、
09-13 写过的 [ModelRift openscad-skill](./2026-09-13.html)（render/inspect/revise 回路）是同一条演化线。

对个人的直接含义：**评估一个 text-to-CAD 项目时，先看它让模型写什么。**
写坐标的，token 成本随零件规模线性涨，且跨轮次必漂；
写意图 + 稳定 ID 的，才有可能做到第十轮编辑还找得到第一轮那个孔。
KJDraw（`KanJieTeam/kjdraw`，Apache-2.0）把这条原则写成了一句标语——
「The model decides what to draw. The engine decides how to draw it correctly.」——虽然它做的是 2D DXF。

**3. 「和具身智能的接口」这一段，本周只有一个 2 星的东西，但它的形状是对的。**

按覆盖面轮换，本期本该有一条 URDF/SRDF/SDF 自动生成。**找遍了，这周新建的只有
`enesbirlik/claude-code-robotics`（MIT，09-15 建，2 ★）够得上标准**，所以没给它独立条目，放在这里说：

它是个 Claude Code 插件，五个技能（ROS 2 工作区 / **URDF-Xacro 构建器** / micro-ROS 桥 / Nav2-MoveIt2 配置 / ROS 2 生态包速查），
**加上两个真的会执行的 hook**：`verify_urdf.sh` 跑 `xacro` 和 `check_urdf`，
`colcon_build_check.sh` 跑限定范围的 `colcon build`，都是 `PostToolUse` 触发——
**模型一写完 URDF 就立刻知道它是不是畸形的**。
另外带一个**只读**的 ROS 2 MCP 服务器（`ros2_node_list` / `ros2_topic_echo` / `gz_topic_echo` 等六个工具），
**没有 publish、没有 set_parameter、不能改生命周期状态**。

它针对的问题 README 说得很准：通用 LLM 写机器人代码时会**编出看起来合理但错误的 URDF 惯性张量**、
发明不存在的 `rclpy` QoS 默认值、靠猜参数名去「修」Nav2 代价地图。
`skills/urdf-xacro-builder/SKILL.md` 里直接给了闭式惯性张量公式和宏。

**这就是本期最便宜的一个动手位**：装上它，拿你手上任意一个开源臂的 URDF
（SO-101、Piper、OpenArm 都行），让它跑一遍一致性检查，**把 `check_urdf` 报出来的问题提回上游仓库**。
半天，零成本。它和 cadxray 合起来其实就是那条完整闭环的两端——
**cadxray 负责「件对不对、打不打得出来」，claude-code-robotics 负责「装上去之后模型描述对不对」**，
中间那一段（CAD 装配体 → URDF 关节树自动导出）**这周依然是空的**，
最近一次有像样东西是 09-12 的 [robotics-design-skill-suite](./2026-09-12.html)。

**4. 「跑一个件多少钱」，八期了，还是没有任何一个项目自己报过。**

本专题从 09-10 开始每期都要求把 API token 费算进去。到今天写了十几个项目，
**只有 09-16 的 [3Dpriting-detect-agent](./2026-09-16.html)（全本地 Qwen2.5-3B，token 费 0）和
09-14 的 [flex-fab-agent](./2026-09-14.html)（求解在 OR-Tools 里，不花 token）能给出确定的数字，
而它们给得出来的原因都是「压根没调云端模型」。**
所有真正用大模型做几何推理的项目，成本都是我在这里估的。

这件事的实际后果是：**你没法比较两个 text-to-CAD 方案哪个更便宜**，
而这条链路上便宜和贵能差一个量级（见上面 cadxray 的 $1–3 和 Auto-SolidWorks 纯文字的 $0.05–0.2）。
**所以本期把这个列为第一号缺口**：给任意一个这类项目加一段「本次运行累计输入/输出 token + 估算金额」的输出，
是几十行代码的事，而且**几乎必被合**。

## 📈 趋势观察

**1. 本周开源硬件是真的荒，而且荒得有结构。**

我这期按 `created:>=2026-09-08` 扫了 40 多个查询词（机械臂、灵巧手、四足、遥操作、外骨骼、
BOM、STEP/STL、CERN-OHL、topic:open-source-hardware…），**新建的、带真实 CAD/BOM、够得上「个人能照着做出来」的本体项目，
一只手数得过来，而且其中大半是 microduck 的衍生**：
`laotawayer/microduck`、`7757/fanduck`、`fanhao375/microduck-replica-cad`（37 ★）、
`microai-lab/microduck-studio`、`joeynyc/awesome-microduck`(116 ★)、`srayuth089/microduck-docker`…

这不是坏事，但要看清它是什么：**一个便宜、有官方 MJCF、有预训练策略、能一个人装完的平台，
会把整个社区的硬件精力吸过去**。代价是别的形态（桌面臂、灵巧手、轮足）这周几乎没有新供给。
**对个人的操作含义**：如果你想做硬件且想让别人用上，**现在做 microduck 的配件/改件，
比从零设计一个新本体的曝光率高一个量级**；反过来，如果你想做的是别的形态，
这一周的空窗恰恰说明**竞争者也少**。

**2. 「零真机也能跑完整闭环」这一类，本周同时出现了两个强样本。**

real2sim-droid（一条公开 episode → 可做反事实的 MuJoCo 孪生）和 StationeryBench（装完就有 mock policy，
三行命令跑通整条评测流水线）看起来毫不相干，但它们解的是同一个问题：
**把「需要机器人」这个门槛，从流程的第 1 步推到第 N 步。**

这和 09-16 的 [RLE-Bench](./2026-09-16.html)（九任务族里 task07/08/09 纯 CPU）、
09-15 的 [LLMs Robot Arena](./2026-09-15.html)（浏览器擂台）是同一个方向。
**趋势判断：2026 下半年「具身智能个人可参与性」的增量，主要来自评测和仿真侧，不是硬件侧。**
硬件降本已经到了平台期（一只鸭子几千块、一只手两百块，见 09-15 的 [Easyhand](./2026-09-15.html)），
而「不用买硬件就能产出可验证结果」的工具链还在快速变好。

**3. 不可信输出 → 确定性闸门 → 安全降级，正在从「好设计」变成「默认结构」。**

本期六条主线里有三条是同一个骨架：
humanoid-companion（LLM 只能**请求**走路，规划器决定，解析失败 = 站着不动）、
claude-code-robotics（hook 真的跑 `check_urdf`、MCP 只读不能 publish）、
cadxray（`suggest_sketch_fixes` 什么都不自动改，`apply_sketch_fixes` 要指定 id 且会 fingerprint 校验、变差就回滚）。

再往前数：09-16 的 [model-forge 七道门](./2026-09-16.html)、09-13 的
[idea-to-print 19 项 DfAM 几何门](./2026-09-13.html)、09-12 的
[SimpleCADforDSH 几何 QA 硬门](./2026-09-12.html)。
**如果你现在要做一个 agent × 物理世界的项目，"模型的输出必须先过一道能失败的确定性检查" 已经不是加分项，
是评审会默认问你的第一个问题。**

**4. 一个反向提醒：有名字、有星、有 arXiv，不代表你能跑。**

本期扫到两个很显眼但**最终没进榜**的项目，理由值得写下来：
- **`shengshu-ai/Motus2`**（38 ★，生数科技，arXiv 2608.30237）——自进化通用世界模型，做灵巧操作。
  README 里开源路线图**七项全是未勾选**，更新写的是「我们计划在 2026 年 9 月内逐步发布代码和检查点」。
  **今天还什么都没有。** 不满足「技术可达成」。
- **`Tengbo-Yu/SEED-UMI`**（9 ★，CoRL26，北大通研院 + Delta Intelligence）——人和机器人**戴同一副外骨骼**采数据，
  20 自由度，思路非常漂亮（把运动重定向变成成对的跨本体监督）。但仓里只有**项目页前端 + 论文 PDF**，
  **没有代码，没有 CAD**。不满足「产出可预期」。

这两个都值得**加星观望**，但本周别指望动手。

## 🔧 不是比赛、但确实缺人做的口子（半天到一周量级）

1. **给 real2sim-droid 跑 10 条 episode，把跨视角物体摆放误差的分布统计出来。**
   作者只跑了两条（README 的 Limitations 第一条）。纯下载 + 纯计算，零硬件零 API 费。一天。（国外 TOP 1）
2. **在 A4000 16G 上把 real2sim-droid 的 `all` 跑一遍，报墙钟时间和显存峰值。**
   作者只给了 4070 Ti 的 3 分钟。两小时。（国外 TOP 1）
3. **把「一条 LeRobot 公开数据集 → openpi RepackTransform」的写法整理成一篇可复制的说明。**
   vla_pi0 把坑列全了但只覆盖它自己那台臂，**零硬件、零 GPU 成本**。一天。（国内 TOP 1）
4. **给 vla_pi0 提 issue 问根目录许可。** 子目录有上游 Apache-2.0，作者自写的适配代码无明示许可。十分钟。（国内 TOP 1）
5. **给 laotawayer/microduck 转存一份 SolidWorks 低版本文件。** README 里作者点名求这个，转完在 issue 注明版本和验证结果。半小时。（国内第 2）
6. **补 microduck ROADMAP 里那两个空框之一**：标准件精确数量核对，或打印材料/层高/填充/支撑建议。半小时到两小时。（国内第 2）
7. **给 sixdof-arm 加一套 SO-101 或 Piper 的 DH 参数，并跑通那 200 组正逆解往返测试。**
   结果客观可验，一天，纯 C++。（国内第 3）
8. **按 StationeryBench 的任务文档买齐五套文具复现摆放，写一份「复现偏差记录」。**
   官方给了摆放照片、物体规格和人类演示视频，**几十块钱**。一天。（国外第 2）
9. **量一下同一个件在 cadxray（CalculiX）和 cadloop（FEniCSx）上的安全系数差多少。**
   两条 FEA 链路在同一个件上的一致性，**现在没人量过**。一天，纯软件。（专题 · 国外）
10. **给任意一个 text-to-CAD 项目加一段「本次运行累计 token + 估算金额」的输出。**
    几十行代码，几乎必被合，而且**这是本专题写了八期都还没人做的第一号缺口**。半天。（专题分析第 4 点）
11. **装上 claude-code-robotics，拿一个开源臂的 URDF 跑一遍一致性检查，把 `check_urdf` 报的问题提回上游。**
    半天，零成本。（专题分析第 3 点）
12. **给 Auto-SolidWorks 做一份「模型尺寸 vs 图纸标注」的逐条误差表。**
    作者明说截图不构成等价性证明——这个位置是空的。一天（需要 Windows + SolidWorks）。（专题 · 国内）
