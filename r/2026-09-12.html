★ TOP 1（深度）· PocketVLA —— 3M 参数的 VLA，从数据生成到 GRPO 全流程在自己机器上跑一遍

是什么

PocketVLA（9 月 10 日建仓，Apache-2.0）是一个刻意做小的 VLA 教学/实验仓： 参数量 3.02M，结构却是标准的那一套 —— 视觉编码器把 vision token 线性投影进语言模型的 embedding 空间， 和文本 token、本体感知 token、可学习的 action-query token 拼在一起过共享 LM 主干， 动作头只读 action-query token 在 LM 输出里的隐状态，经 MLP + tanh 解出动作。 也就是说视觉、语言、本体感知全部经由融合主干影响动作，这条通路和 π0 / SmolVLA 那一类是同构的，只是每一层都缩到了玩具尺寸。

任务是一个纯 NumPy 写的 2D 环境：一条 2 连杆平面机械臂，俯视 64×64 观测， 场景里红/绿/蓝三个球 + 一个筐，位置每回合随机，指令形如 put the blue ball into the bin。 三个球外观只差颜色，所以模型必须真的把指令里的颜色词接到图像上；抓到之后还得再从图像里找到筐。 动作是 (Δq1, Δq2, grip)，关节增量限幅 ±0.15 rad，末端离球心 < 0.09 且闭合夹爪即吸附，每回合最多 90 步。

仓库给了端到端五段：数据生成 → SFT 行为克隆 → GRPO 强化学习 → 闭环评测 → OOD 泛化评测， bash scripts/run_all.sh 一条命令串完。数据由一个成功率 100% 的特权专家（闭式 IK + 双速比例控制 + 夹爪状态机）在线生成， train 7000 回合 / 184,364 样本，val 3000 回合，test 500 场景，GRPO 3000 场景，OOD 300 场景，也可以直接从 HF 下。 已训好的两个 checkpoint 也放出来了：SFT 闭环成功率 74.2%，SFT + GRPO 80.2%。

为什么现在值得做

因为它把 VLA 里最容易被跳过的那一环变成了一个十分钟就能重跑的对照实验。

仓库里最有价值的一张表不是成功率，是消融：模型有两个轻量辅助读出头（从融合后的 vision token 出发， 用 Conv + 注意力加权 8×8 网格中心，分别回归球和筐的世界坐标），它们不在动作通路上， 只提供深监督辅助损失，use_aux_heads: false 一键关掉。关掉之后——

闭环成功率 74.2% → 6.0%（−68.2 个点），抓对球率 79.0% → 19.0%。

一个「不在动作通路上」的辅助损失，撤掉就让模型从能用变成完全不能用。 这个现象在大 VLA 上人人都在讨论（空间定位到底是被动作监督学出来的，还是必须显式喂）， 但在 7B 模型上跑一次消融要几百卡时，在这里是改一行 YAML 加十分钟。 这是本期唯一一条你能在一个下午内亲手验证一个真实 VLA 结论的项目。

另一半价值是它的诚实：作者把失败归因统计、分颜色成功率、专家 vs VLA 的世界坐标轨迹对比图都写进了评测脚本， 还单独给了 OOD（没见过的干扰物）那一栏，而不是只报一个漂亮数字。

个人怎么分步切进去（带成本和时间）

前提：本机单卡即可，仿真器是纯 NumPy、CPU 就能跑。下面的时间是我按规模估的，不是实测—— 作者 README 写的是「普通 GPU 即可训练，10 分钟内跑完全流程」，我没有逐段计时去核。

  1. 第 0 步 · 跑通（约 30 分钟，0 元）

    conda create -n pocketvla python=3.10 -y && conda activate pocketvla
pip install -r requirements.txt
bash scripts/run_all.sh

    拿到 outputs_sft_3m/eval/ 里的 GIF 和失败归因图。先确认你复现出的 SFT 成功率落在 74% 附近， 偏太多说明环境或随机种子有问题，别带着这个往下走。

  2. 第 1 步 · 重跑那个消融（约 30 分钟，0 元） configs/sft_3m.yaml 里 use_aux_heads: false，重训重评。 你要拿到的不是「确实掉了」，而是掉在哪一步——看失败归因统计里是「抓错球」涨了， 还是「抓对了但放不进筐」涨了。作者报的是抓对球率 79%→19%，说明崩在定位而不是控制。

  3. 第 2 步 · 做一个作者没做的对照（半天到一天，0 元） 现成的开关还有一个：balanced_losses: false（夹爪按「持球状态 × 标签」4 组逆频率加权、 球偏移回归按归一化距离 4 桶加权）。作者只说了它是为了防止远距离视觉定位被拖垮， 没有给关掉之后的数字。这是一个一天内能交出来的、有人会用的结果 —— 直接 PR 一张表进去。

  4. 第 3 步 · 换个东西进去（1–2 周，0 元） 把动作头从 tanh 直接回归换成 flow-matching / diffusion head，其余不动。 这是主流 VLA 之间最大的一个结构分歧点，在这个仓里是唯一变量可控的对照。 再狠一点：把辅助头从「显式回归坐标」改成「不给坐标、只加一个对比损失」，看能救回多少那 68 个点。

坑与风险

  • 别把这里的结论直接外推到真机 VLA。 观测是 64×64 的合成俯视图，没有光照、没有纹理、没有遮挡、没有相机噪声； 「辅助头是救命的」这个结论在真实图像上大概率仍然成立但幅度不会是 68 个点。它是用来练手和建立直觉的，不是 benchmark。
  • 数据由一个 100% 成功的特权专家生成，示教里只加了 σ=0.002 rad 的微小噪声 —— 示教分布极窄，所以 GRPO 那一段涨的 6 个点（74.2 → 80.2）有多少是真的 RL、有多少是在补数据覆盖的洞，仓库没有拆开。想认真做 RL 的话这是第一个要查的地方。
  • 仓库 9 月 10 日才建，18 star，只有一次 push。issue 区基本是空的，遇到问题多半得自己看代码。 好消息是代码量小、模块边界清楚（pvla/sim/ pvla/model/ pvla/expert/ pvla/train.py），能读完。
  • HF 上的 checkpoint 要 trust_remote_code=True 且必须先 import pvla.model 注册自定义类，从仓库根目录跑。

🌍 国外

★ TOP 1（深度）· teleop-walking-benchmark —— 把 29 个开源 G1 行走策略放进同一个接口、同一张考卷

是什么

rhoyn/teleop-walking-benchmark（9 月 1 日建仓，MIT，9 月 11 日还在更新）。 把网上能找到的开源 Unitree G1 行走策略全部移植到同一个 C++ 接口背后， 在同一个任务上用两个物理引擎打分，然后把表贴出来。

任务定得很死，这是它值钱的地方：60 秒、12 个航点、50 Hz 控制、2 ms 物理步长。 起手有一个吊架把所有策略摆成同一个站姿保持 3 秒再松开。每段路上砸一拳 —— 随机关节、随机方向、0.08 秒、最高 600 N。评分看的是恢复，不是跟踪误差。 策略只拥有 15 个腿部和腰部关节；14 个手臂关节由 harness 做随机游走，永不静止，也不许借去平衡。 这一条把「靠甩手保持平衡」这种在 demo 视频里看不出来、在排行榜上很占便宜的做法直接堵死了。

工程上真正的关键：每个策略和每个物理引擎都在同一个 CUDA 接口后面，所以整批策略是在 GPU 上批量跑的， 而不是「每个策略每个 run id 起一个进程」。两个引擎都在 GPU 上步进 —— PhysX 原生， MuJoCo 走 MuJoCo Warp。 MuJoCo Warp 没有 C API，作者的做法是 make capture 把一个 substep 录成 CUDA graph， 运行时由 C++ 直接重放，全程不碰 Python。

结果表里 A 档（两引擎平均完成率 ≥ 60%）11 个策略各跑 5120 个 run id，B 档跑 512 个， Results 一节记的总量是 144,384 次 run（README 开头另有一处写 471,424，两个数字对不上，以 Results 表为准）。

为什么现在值得做

因为这是我见过第一份把「同一个 checkpoint 在不同姿态命令下」和「同一支血统的两代策略」都显式标出来的机器人策略横评。

作者在表下面写了三段注解，每一段都是别的排行榜会偷偷抹掉的东西：

  • gr00t_wbc 是 HOMIE v2，不是独立策略家族 —— 作者在 GEAR 做的 homie 后继， 「所以 gr00t_wbc 和 homie 是同一血统而非两个条目」，并附上了 InternRobotics/OpenHomie#23 里 @Elgce 的确认。
  • gr00t_wbc 和 decoupled_wbc 各出现四行，是同一个 checkpoint 在四个躯干高度/俯仰命令下的结果， 每行拥有同样的 15 个关节、接同样的命令，所以每行都参与排名。
  • 两行带删除线的 *_with_arms 是不排名的，因为那是把 29 个关节全给了策略 —— 换了考卷就不进榜。

还有一条负面结果值得单独拎出来：mimic_lite 自己不带 planner，harness 只好用 sonic 的 planner 从同样的速度命令生成参考动作喂给它 —— 这类「论文里有、放出来的权重缺一半」的情况被写进了表注，而不是被沉默处理。

个人怎么分步切进去（带成本和时间）

前提：一张 NVIDIA 卡（本机 A4000 16G 够用）、CUDA、TensorRT。策略推理只占一次 run 的 不到 3%，瓶颈全在物理。

  1. 第 0 步 · 复现一行（1–2 小时，0 元，最大风险在装环境）
    ./download_weights.sh && ./export_onnx.sh && make && make capture
./run.sh --policy gr00t_wbc_h074_p000 --engine physx --runids 0-255
./build/table        # 渲染结果表
    先只跑 PhysX（不需要 MuJoCo Warp 的 capture），拿到 256 个 run 的数字，和表里 A 档的量级对上再往下。
  2. 第 1 步 · 打开 MuJoCo 那一路（半天） make capture MJWARP_NWORLD=256，然后 --engine mujoco。 注意 capture 会把舰队规模固定死，改模型或改 --runs 都要重录，否则跑不起来。
  3. 第 2 步 · 把你自己的策略塞进去（2–5 天） 这是这个仓最实际的用法：接口是统一的 C++ + TensorRT plan，你只要导出一个符合观测约定的 ONNX。 跑完你拿到的不是「我的策略能走」，而是在 39 行里排第几，以及在哪个引擎上掉得更多。
  4. 第 3 步 · 攻击这个 benchmark 本身（1–2 周，最有价值） 表里 MuJoCo 和 PhysX 的完成率对不齐（比如 sonic 是 36% vs 15%，openwbt 是 0% vs 6%）。 两个引擎之间的分歧本身就是一个可发表的观察 —— 找出是接触模型、摩擦还是求解器造成的， 这比再刷一个策略上去有用得多，而且不需要任何硬件。

坑与风险

  • 仓库描述还写着 “Thirteen … policies”，正文已经是 29 个、结果表 39 行。 描述没跟着更新，别拿它当事实引用。
  • make capture 不跑就起不了 MuJoCo 引擎，而且报错不一定直说。这是新人第一个会撞的墙。
  • 需要 TensorRT。A4000 能跑，但 TensorRT 版本和 ONNX opset 的兼容矩阵是这类项目的经典时间黑洞，预留半天。
  • 这是一个人维护的 6 star 仓库。方法论比软件成熟度靠谱，别把它当成有 SLA 的基础设施。
  • 打分是恢复导向的，和你在论文里看到的跟踪误差排名不可比 —— 别拿这里的名次去反驳别人的跟踪指标。

🌍 国外 · robotics-design-skill-suite —— 把 CAD → URDF / SDF / SRDF → ROS 2 / Gazebo 做成一串带「物理合理性门」的 agent skill

是什么

holdonyb/robotics-design-skill-suite（8-4 建仓，MIT，中英双 README）。 一套给 Codex 用的机器人设计 skill 套件，分三层：

层 skill
系统路由 robotics-design
机械产物 cad、step-parts、dxf、cad-viewer
机器人描述 urdf、sdf、srdf
软件与仿真 ros2-engineering-skills、ros2-sim

仓库本身是一个薄的、可审计的分发层 —— 第三方 skill 不是复制进来的， 而是记在 manifest.json 里的完整 pin 住的 commit，安装时才拉。安装器拒绝覆盖已存在的 skill 目录。

用法就是一句话：

$robotics-design Design an indoor mobile manipulator from requirements through CAD, URDF, SDF, ROS 2, simulation, and validation.

也可以只叫某一个产物的 owner：

$urdf Review this robot description for frame, axis, limit, inertia, and consumer-load errors.
$sdf Build a Gazebo Harmonic world and identify every validation gate that was not run.

真正值得看的是 v0.3.0 加的那个「物理合理性门」：在进入仿真或训练之前， 它要求一份机器可读的设计契约（design-contract.json），把带显式单位的量绑到证据上、 把部件绑到左右驱动和每个关节的职责上、把每个插件输入闭合到一个期望的物理量纲上， 校验产物哈希，然后跑：

python skills/robotics-design/scripts/validate_design_contract.py path/to/design-contract.json --report evidence.json

输出是确定性诊断 + 带符号的裕度：传动系统、电池/续航、静稳定性、机械臂重力与刹车保持、 零部件质量闭合、保守稳态绕组热负载、以及声明的执行器接口配合。退出码 0 才算过。

为什么这段链路现在重要

因为「agent 画了个件」和「agent 交出一台能进仿真的机器人」之间隔的正是这一段， 而这一段过去只有两种做法：手写 URDF，或者让模型直接吐 XML 然后人肉 debug。

URDF 有几个出了名的坑 —— 它不定义关节顺序（只是一堆 link 和 joint）， 惯量张量随便填也能加载，limit 写错了在 Gazebo 里要跑起来才发现。 这套 skill 的思路不是「让模型更会写 URDF」，而是先逼出一份可校验的设计契约，再让每个产物对契约负责， 并且把「哪些校验门没跑」当成一等输出（$sdf 那条命令字面上就是这么写的）。 这和 09-11 专题里 design-os 那个「拒绝含糊通过」的生产门是同一个方向 —— 这一周这条链路上的共同变化，就是门开始比生成更重要。

个人怎么切进去

  1. git clone → python scripts/install.py --dry-run 看它要往 ~/.codex/skills 放什么，再真装（需要 Git + Python 3.11+）。
  2. 拿你手上任何一台现成机器人的 URDF（比如本期国外第 3 条那台四足，或者 09-10 推的北京人形 Sprite）， 跑 $urdf Review ...，看它挑出几个真问题、几个误报。这是评估这套东西值不值得用的最快方法，半小时。
  3. 认真一点：为你自己的设计写一份 design-contract.json，跑 validate_design_contract.py， 看电池续航和静稳定性那两个裕度是正是负。这一步会强迫你把平时拍脑袋的数写成带单位的量。
  4. 能出产出的口子：这套 skill 只覆盖到 Gazebo，没有 MuJoCo / MJCF 那一路。 补一个 mjcf skill（或者在 urdf skill 里加 URDF→MJCF 的一致性门）是一个一周量级、明显有人要的贡献。

成本（把 API token 算进去）

这条链路的钱花在模型调用，不在硬件。按典型一次「从需求到 URDF + SDF + 一次校验」的会话估：

  • skill 定义 + 参考文档进上下文：约 20k–60k input token（这套 skill 带 reference/ 和 docs/，比单文件 skill 重）
  • 生成 + 两三轮修正：约 8k–20k output token
  • 校验脚本本身是确定性 Python，0 token —— 这是这套设计省钱的关键：把判断从模型手里拿走了

一个件/一台机器人的一次完整往返，大致落在 ¥1–5 人民币的量级（按当前主流前沿模型每百万 token 的公开定价换算， 这是量级估算不是实测账单，具体数字随你用哪个模型差好几倍，跑之前自己按用量表核一次）。 真正会把钱烧掉的是让模型反复猜几何；用了确定性门之后，失败会在几十行诊断里被挡下来，而不是又生成一遍。

坑

  • 0 star，最后一次 push 是 8 月 24 日。 想法好，但没有社区验证，当参考实现看，别当依赖。
  • 它是 Codex skill 格式（~/.codex/skills）。装到 Claude Code 上要自己转一遍 skill 格式，不是即插即用。
  • manifest.json 里 pin 的是第三方 commit —— 好处是可复现，坏处是上游修了 bug 你也拿不到，得自己动 manifest。
  • 校验门给的是保守稳态热负载和裕度，不是瞬态。堵转、冲击这些真正烧舵机的工况它不管。

🇨🇳 国内 · SimpleCADforDSH —— text → build123d → STEP，几何 QA 是硬门，模型跑在本地 dsh 上

是什么

jianboer/SimpleCADforDSH（9-8 建仓，MIT，9-11 更新）。 DeepSeek Harness（dsh）的树外插件 —— 走官方插件契约（host tools + client slot + skill），不 fork 也不打 patch 改 dsh 源码。

流程是四步，每一步一个工具：

prompt ─▶ text-to-cad skill
          ├─ simplecadfordsh_brief   锁死 overall_size_mm / special_features
          ├─ simplecadfordsh_gen     写 build123d Python → 导出 STEP + GLB，返回 facts + qa
          ├─ [同窗 CAD 面板打开]      QA 问题、参数栏、面检查器、模型树、着色 3D 视图
          └─ simplecadfordsh_export  STL / GLB（3MF 计划中）

三个点和上周的同类项目不一样：

  1. 出的是 code-CAD，不是 mesh。 每个件都是一个 gen_step() 的 build123d 脚本， 总体尺寸写在顶层 PARAMS 字典里、函数体里全部引用 PARAMS[...] —— 这是它能在面板里改尺寸再生成的前提。
  2. 几何 QA 是内置的硬检查，不是让模型自己说「看起来没问题」：single_body（单实体）、 watertight（水密）、overall_dimension（0.2 mm 容差），每项给 pass/fail 判定。
  3. 相似度只是 advisory。 CAD 与参考图的轮廓 IoU + 基于 QA/相似度/brief 意图的规则建议， 明确标成「参考」而不是门 —— 分清哪些指标能当门、哪些只能当提示，这个区分本身就是进步。

和 09-11 那条的关系：上期国内推的 weisofns/dsh-print3d 是同一个宿主（dsh）上的打印执行段， 这一条是建模段。两条拼起来，DeepSeek Harness 上现在有了一条「文本 → 参数化 CAD → 打印」的完整本地链路。 这不是巧合 —— dsh 的插件契约把「工具是确定性的、模型只负责编排」写进了接口， 所以这个生态里长出来的东西天然是「确定性工具 + 小模型」这个形态。

个人怎么切进去

  1. 环境比上周那条重一点：Node.js 22 + 一个装了 build123d（以及 numpy，图像特征还要 PIL/trimesh）的 Python 环境 + 配好 DeepSeek API key 的 dsh Web。
  2. 按 README 三步接进去：把包链到 $DSH_HOME/profiles/node_modules/simplecadfordsh、 把 SIMPLECADFORDSH_PYTHON 指到你的 conda 环境、在 dsh patch 文件里插一行。 仓库给了 scripts/start-dsh-web.ps1 自动做前两步（PowerShell 脚本，Linux 下要自己 export）。
  3. 第一个有用的产出：拿 09-11 提过的那批开源机械臂零件（法兰、相机支架、夹爪指尖）当题目， 跑 10 个件，统计 watertight 和 overall_dimension 各失败几次、第几轮收敛。 这个仓库现在没有任何成功率数据 —— 一张 10 行的表就是有人会引用的贡献。
  4. 再进一步：3MF 导出还在「计划中」。多色 / 多材料打印必须走 3MF，补这个导出是明确的一个口子。

成本（把 API token 算进去）

这一条的账比国外那条好算，因为跑在 DeepSeek 上：

  • 一次典型生成：brief + gen + QA 反馈重试 1–2 轮，约 15k–40k input token、3k–8k output token
  • build123d 执行、STEP/GLB 导出、三项几何 QA、轮廓 IoU —— 全部是本地确定性计算，0 token
  • 按 DeepSeek 官方定价 换算，一个件大致几分钱到两三毛人民币 （量级估算，命中缓存会更便宜；动手前按官方价目表自己核一次，价格会变）

对比一下这条链路今年的成本曲线：09-10 推的 清华 MAC 靠拆 agent + 确定性翻译器把 token 打到 1/116、成本 1/13； 09-11 推的 dsh-print3d 靠本地 8B 模型把 token 费打到 0；这一条介于中间 —— 用云端便宜模型 + 本地确定性 QA，几毛钱一个件，但不用自己养模型。

坑

  • 3 star、9 月 8 日建仓，3MF 还没做，报错路径基本没人踩过。
  • 安装要手工 patch dsh 的一行配置并做软链，不是 npm i 就完事 —— dsh 升级后大概率要重来一遍。
  • overall_dimension 的 0.2 mm 容差是针对总体包络的，不检查内部特征（孔位、壁厚、圆角）。 别把 QA 通过当成可打印：单实体 + 水密 + 包络对，和 DfAM 可打印性（悬垂、最小壁厚、支撑）是两回事，后者这个仓完全不管。
  • 轮廓 IoU 是从单一视角算的，对回转体基本没有分辨力，别拿它当验收指标。

专题分析：这一周这条链路上真正变了什么

  1. 门（gate）开始比生成器重要，而且门的形态在收敛。 robotics-design-skill-suite 的 validate_design_contract.py、SimpleCADforDSH 的三项几何 QA、 09-11 design-os 的 AGENT_OK/AGENT_FAIL、dsh-print3d 的 6 个确定性工具 —— 四个互不相识的项目，在两周里独立收敛到同一个结构：模型负责编排和生成，判定交给确定性代码， 并且「哪些门没跑」是一等输出。这比任何一个模型的 CAD 能力提升都更能改变这条链路的实际可用性。

  2. 第 3 段（和具身智能的接口）终于有人系统做了，切入点是「关节顺序」和「物理裕度」这两个老坑。 URDF 本身不定义关节顺序，下游每个工具按自己的规则排成向量 —— 这件事过去靠人盯，现在有了工具化的解法：robotics-design-skill-suite 在设计契约里把「部件↔左右驱动↔每关节职责」绑死； 本期国外第 3 条那台四足在 README 里直接写「用名字映射，不假设 DOF 顺序」； 还有一个纯浏览器的小工具 ImChong/Robot_Joint_Order_Check_Tool_Online（MIT）， 传一个 URDF 或 MJCF 就把它在 Isaac Gym / Isaac Sim / MuJoCo / Genesis / Newton / Gazebo / PyBullet / ros2_control 里的关节顺序并排打出来， 全部一致显绿、任何一个对不上标红，纯本地解析不上传。在线版在这。 这是本期最小的一个工具，也是最可能让你今天就省掉两小时的那个。

  3. 成本已经不是这条链路的瓶颈了 —— 现在的瓶颈是「模型不知道自己错在哪」。 三种省钱路线（拆 agent 走确定性翻译 / 本地小模型 / 云端便宜模型 + 本地 QA）都已经把一个件压到几毛钱以内。 token 费不再是决策变量。真正决定能不能用的是失败时的诊断质量 —— validate_design_contract.py 输出「确定性诊断 + 带符号的裕度」而不是「校验失败」，方向是对的。

  4. DfAM（可打印性）仍然是整条链路上最空的一格。 自动建模段在做几何 QA，打印执行段在做切片和机器控制，接口段在做 URDF/SDF —— 但「这个件打得出来吗」（悬垂角、最小壁厚、支撑可去除性、翘曲风险）几乎没有项目当成硬门在做。 SimpleCADforDSH 明确不管，design-os 的门在装配排版层。 如果你想在这条链路上做一件有辨识度的事，一个能被 agent 调用、输出确定性判定的 DfAM 检查器是当前最空的位置。 现成的抓手：MaxEllis/orcaslicer-mcp（46 star，AGPL-3.0，9-10 更新）里有个 check_profile_physics，把流量、温度、几何、冷却的数学跑一遍，返回 ok/warnings/blocked —— 那是切片参数层面的确定性门，把同样的形态做到几何层面就是缺的那一块。

趋势观察

一、这周最值得注意的不是某个模型，是「同一张考卷」这件事开始出现了。 teleop-walking-benchmark 把 29 个 G1 行走策略拉到同一个 C++ 接口、同一个任务、两个引擎上打分， 并且把「同血统的两代策略」「同 checkpoint 的不同姿态命令」「换了关节数所以不排名」全部显式标出来。 过去一年具身领域的横评基本是各家报各家的数，这份表第一次让「谁更抗打」变成一个可以争论的、有公开复现路径的问题。 配套的还有本期国内第 1 条的 PocketVLA —— 它把消融做成十分钟的事。 两者是同一件事的两端：让结论变得可以被便宜地检验。

二、开源硬件这周确实是空档，而且不是我没找到。 把 open hardware / robot gripper / dexterous hand / robot kit / exoskeleton / BLDC driver / SO-101 / hexapod / 开源硬件 / 舵机 / 双足机器人 / 四足机器人 这些词在 8 月 20 日之后建的仓里扫了一遍， 两位数 star 的新硬件仓只有 takto-one（09-09 已推） 和一批 Microduck 衍生仓。所以本期是软 4 / 硬 2，而不是凑一条充数。 上期（09-11）是 3/3，没有形成连续偏向。 顺带一提，Microduck 生态的扩散速度很不寻常：09-06 推它的时候是两三个仓， 现在中文复刻、Isaac Lab 环境、playground、docker 一键跑、awesome 列表、装机教程（714 star）全都出来了 —— 一台 ¥4000 级的双足机器人在两周内长出了完整的生态，这是这一年里开源硬件最快的一次冷启动。

三、「本体便宜」正在从「关节模组便宜」退回到「用航模舵机」。 本期国外第 3 条那台四足用的是 0.304 N·m 的普通舵机、整机 0.28 kg， Microduck 用 14 个 XL330，09-09 推的 HumbleArm 是 ¥200 级舵机臂。 这一批项目的共同点不是性能，是把机械源文件、URDF 和仿真验证流程一起给出来， 让人能从 CAD 读到控制代码。对个人来说，这比又一台更强的 ¥10 万本体有意义得多。

四、专题那条链路的结论：门比生成器重要，DfAM 是最空的一格。 见上文专题分析第 1、4 点。
