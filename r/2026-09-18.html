🇨🇳 国内

★ TOP 1（深度）· PocketVLA —— 3.02M 参数的 VLA，纯 NumPy 仿真，一张普通卡十分钟跑完「数据 → SFT → GRPO → 评测 → OOD」

是什么

一个从零实现的 0.003B（3.02M 参数）VLA，Apache-2.0，09-10 建仓，09-17 还在更新，30 ★。

结构和主流 VLA 同构：视觉编码器 + 语言模型主干 + 动作头，标准 VLM 早融合 （vision token 经线性投影进 LM embedding 空间，与文本 token、本体感知 token、 可学习 action-query token 拼接后过共享主干），完整兼容 HuggingFace AutoModel / AutoTokenizer。

下游任务 2D Grab：

要素 定义
场景 红 / 绿 / 蓝三个球 + 一个收纳筐，位置每回合随机
指令 自然语言，如 put the blue ball into the bin
观测 64×64×3 俯视图（含筐，不标记目标）+ 指令 token + 6 维本体感知 (q1, q2, ee_x, ee_y, 夹爪, 持球)
动作 (Δq1, Δq2, grip)，关节增量限幅 ±0.15 rad；grip > 0 闭合
抓取 闭合夹爪时末端距球心 < 0.09 即吸附（抓错要自己恢复）
成功 已松爪且球完整落在筐内；每回合最多 90 步

全链路都在仓里：collect（数据生成，闭式 IK + 双速比例控制 + 状态机专家，成功率 100%） → train（SFT，动作 MSE + 类平衡夹爪损失 + 辅助头深监督） → evaluate（500 场景固定测试集闭环，逐场景 GIF + 失败归因 + 分颜色成功率图） → grpo（组采样闭环 rollout + 优势加权回归 + KL 锚） → eval_ood（300 场景，含训练中从未出现过颜色的干扰物）。

两个 checkpoint 和五份数据（约 65 MB）都放在 HuggingFace 上。

为什么现在值得做

因为它把「消融」做成了个人十分钟能自己验的东西。

市面上"从零实现 VLA"的教程绝大多数停在 forward pass。PocketVLA 不但把 GRPO 强化学习和 OOD 评测也做完了，还给了可复现的对照数字：

变体 辅助损失 闭环成功率 抓对球率 平均落点距离 成功回合平均步数
SFT（带辅助头） 球偏移 + 筐偏移 74.2% 79.0% 0.251 30.8
SFT（无辅助头 noaux） — 6.0% 19.0% 0.876 46.4

关掉辅助头，成功率从 74.2% 崩到 6.0%（−68.2 个点），抓对球率 79.0% → 19.0%， 平均落点距离 0.251 → 0.876（几乎从未接近过目标）。这个量级的结论，在 π₀ / GR00T 那种规模上根本做不起对照实验 —— 一次训练几百 GPU 时，没人会为了消融再跑一遍。

而 GRPO 那一段作者也没粉饰：

模型 阶段 闭环成功率 抓对球率 OOD 成功率
pocketvla-3m-sft SFT 74.2% 79.0% 34.7%
pocketvla-3m-grpo SFT + GRPO 80.2% 83.4% 36.0%
pocketvla-3m（无辅助头） SFT 6.0% 17.0% 4.0%

RL 只带来 +6.0 个点（OOD 上 +1.3 个点），比辅助头的 68.2 个点小一个数量级。 把这两组数放在一起看，比读十篇 VLA 论文都直观。

个人怎么分步切进去

步骤 做什么 时间 成本
1 conda create -n pocketvla python=3.10 → pip install -r requirements.txt → bash scripts/run_all.sh README 称普通 GPU 10 分钟跑完全流程 0 元
2 改 use_aux_heads: false 复现那 −68.2 个点 半天 0 元
3 攻 OOD：SFT 74.2% → OOD 34.7%，掉一半。作者在「继续探索」里点名了方向（数据增强 / 域随机化 / 干扰物参与训练 / 颜色词与视觉特征的对比学习） 1–2 天 0 元
4 换任务：以 pocketvla-3m 结构为基座做 pocketvla-[x]m-[task] 3–5 天 0 元

第 3 步是本期我最推荐的一件事：固定的 300 场景 OOD 集 + 一条命令 python3 -m pvla.eval_ood，意味着任何改进都有一个客观、可比、别人能复现的分数。 这是"产出可预期"这条标准的教科书式满足 —— 不是开放式研究，是一个有刻度的靶子。

本机 A4000 16G 严重富余（模型 3.02M，观测 64×64）。全程零 API 费。

坑

  • 单次实验有随机性。 README 里的 pat 那组明写是"相同配置的独立重复实验，用于评估训练 随机性的影响"。你复现出来的数不会和表里一模一样；报改进时至少跑两个 seed。
  • 辅助头不在动作通路上。 它只做深监督 + 可解释性（输出球/筐相对末端的归一化偏移）， 推理时不给动作提供输入。别误读成"模型靠辅助头定位"。
  • 加载要求：先 import pvla.model 注册自定义类，再 AutoModel.from_pretrained(..., trust_remote_code=True)，必须在仓库根目录跑。
  • 这是玩具规模，而且作者没装成不是。 2 连杆平面臂 + 吸附式抓取（末端距球心 < 0.09 直接吸住），没有接触力学、没有摩擦、没有夹持力。它教的是 VLA 的结构与训练范式， 不是操作物理。想从这里直接迁移到真机的，会在接触那一步撞墙。
  • 许可已核：根目录 LICENSE 为 Apache-2.0。

★ TOP 1（深度）· dexterous-astra —— 转笔和魔方两套灵巧手环境，权重给了，魔方那半不用装 Isaac

是什么

Jianglong Ye（San Diego），09-17 建仓，12 ★，8.6 MB。两个任务、两套手、两个仿真器：

任务 手 / 仿真器 零样本 训练后
转笔 Sharpa Wave，Isaac Lab 采样手指关键帧规划器 PPO 策略：转三圈并稳住
魔方 Wuji 双手，MuJoCo 双手脚本控制器：两步 单手学到的转面与滚动：解出 U F L

每个任务四件套：sim/（环境）、zero_shot/（脚本）、policy/（跑 checkpoint）、checkpoints/。 四条命令就是全部入口：

ISAAC_PY=... PY=... pen/run_zero_shot.sh runs/pen-zero
ISAAC_PY=... PY=... pen/run_policy.sh    runs/pen-policy
PY=... cube/run_zero_shot.sh runs/cube-zero
PY=... cube/run_policy.sh    runs/cube-policy

为什么现在值得做

1. 魔方那一半不需要 Isaac Sim。 cube/requirements.txt 是 mujoco==3.13.0 + mujoco-warp==3.13.0 + warp-lang==1.17.0 + torch==2.14.0 + stable-baselines3==2.9.0 + gymnasium==1.3.0 —— 一张 A4000 就够， 省掉 Isaac Lab 那 30 GB 的安装和它自己的一堆坑。而灵巧手在手内操作这条线上， 门槛通常就卡在 Isaac 上。

2. 它把不确定性的来源写进了运行脚本。 cube/run_policy.sh 里：

export MUJOCO_GL=egl OMP_NUM_THREADS=1   # single-threaded torch: other thread counts change the rollout
"$PY" policy/solve.py --out "$out" --seed 5005 --scramble "U F L"

注释直接说明"改线程数会改变 rollout" —— 这种细节通常要你自己踩两天才发现。 加上固定 seed 5005 和固定打乱 U F L，复现是确定性的。

3. 有出处记录和验收门。 pen/checkpoints/provenance.json、pen/policy/acceptance.json、 pen/policy/gate.py —— 不是扔个 .pt 就走。

4. 魔方有客观终点。 解开了就是解开了。灵巧手这条线上能给出"可判定成功"的任务不多。

2 · lite3-sdk —— 把云深处绝影 Lite3 的 UDP 线格式逐帧写出来，零依赖，MIT

infodriver（旧金山）｜ MIT ｜ 09-15 建仓，09-17 仍在更新 ｜ 硬件

纯标准库 Python：不用 ROS、不用在机器人上装任何东西、不用 pip install。

通道 方向 端口 内容
命令 UDP 你 → 机器人 43893 auto-mode 0x21010C03；速度 0x140(x) / 0x145(y) / 0x141(yaw) + f64；stand / sit / stop / heartbeat
遥测 UDP 机器人 → 你 43897 帧 0x0901：电量、IMU rpy、速度、充电、错误、超声

帧格式：12 字节小端头 code / value / type + 可选载荷；速度帧 type 1、载荷一个 f64、value 字段 = 8； 动作 stand 0x21010202、sit 0x21010203、stop 0x21010C0B（值 0 和 1）、heartbeat 0x21040001（≥ 2 Hz）。

CLI 一条条都能用：status / stand / hello / drive --vx 0.4 --wz 0.3 --seconds 2 / stop / estop --yes / reset-estop。

安全那段写得很实在：软 E-stop 只停这个 SDK 发帧，物理 E-stop 永远优先； 最后一个 UDP 帧之后约 1 秒机器人回到自己的阻尼控制器；建议牵绳、离 5 米以上。 遥测要改机器人侧 ~/jy_exe/conf/network.toml 的 ip 再 restart， ssh 密码是一个单引号 ' —— 这种细节只有真上过手的人写得出来。

  • 边界，必须说清楚：要一台 Lite3，整机远超本日报「硬件 ≤ 约 5000 元」那条线， 不符合「投入可控」。
  • 那它凭什么进榜：它的真正价值是协议文档。lite3sdk/protocol.py 是目前少见的、把这台机公开协议整理成一页表的实现。没有机器也能读， 想写自己的驱动（Rust / Go / 嵌入式裸机）可以直接抄帧定义，并且能离线写完 帧构造与解析的单元测试。
  • 作者标注了出处：参考 DeepRoboticsLab/Lite3_MotionSDK、EzioPeter/Lite3_UDP 和同工作区的 Lite3 Pilot 网页控制台。

🇨🇳 国内 · dsh-print3d —— 把切片和 G-code 分析做成确定性工具，模型一个 token 都不用花在几何上

MIT ｜ 2 ★ ｜ 09-05 建仓，09-15 仍在更新 ｜ DeepSeek Harness 的树外插件 （与 09-12 推过的 SimpleCADforDSH 同生态、不同仓）

6 个模型工具（注册进全局 tools 注册表）：

工具 输入 → 输出
print3d_gen_parametric_stl 参数 → 水密 ASCII STL（box / cylinder / tube / sphere / cone / rounded_box / gear）
print3d_gen_calibration_gcode 参数 → 校准件 G-code（cube / temp-tower / first-layer / retraction / bridge）
print3d_stl_analyze STL → 包围盒 / 体积 / 表面积 / 悬垂 / 非流形 / 水密性 JSON
print3d_gcode_estimate G-code → 打印时间 / 耗材 / 层数 / 温度 JSON
print3d_gcode_render G-code → 刀路俯视图 PNG
print3d_slice STL 路径 → 桥接本机 PrusaSlicer 出 G-code

5 个技能（Markdown 知识包，按需加载）：切片（12 种材料参数表 + 层高/线宽/温度/回抽/冷却规则）、 G-code（Marlin / Klipper 方言、起收尾脚本、估算口径）、建模（OpenSCAD 写法）、 分析（STL/G-code 指标判读、3MF 策略）、诊断（10 类打印故障「症状 → 原因 → 修复」）。

为什么这条值得单独说

它把「大对象落盘、只回路径」写成了默认行为，并且给了理由。

所有生成类工具（STL / G-code / PNG）默认直接落盘到 桌面/3Doutput/（分 stl / gcode / preview 三个目录）并只返回路径，README 明写这是为了 「避免把大段文本塞进上下文（对本地小模型尤其重要）」。

这正是本专题写了九期一直在念的那件事 —— 这条链路真正的开销是 token，不是耗材。 一个 500 KB 的 ASCII STL 塞进上下文就是十几万 token；落盘只回一个路径是几十个 token。 前面九期里 cadjson、model-forge、cadxray 都是隐含地这么做， 这是第一个把它当成一等设计约束写出来的。

跑一个件大概多少钱（估算，务必自己复核）

几何计算全部是确定性的 Node 逻辑、进程内调用，零模型调用。 花钱的只有对话本身：

环节 token 消耗
「描述件 → 生成 STL → analyze → slice → 看 estimate → 改参数」一轮 约 6–10 次工具调用
每次工具返回 一个路径或一小段 JSON（几十到几百 token）
一轮累计上下文（估算） 3–6 万 token
用本地小模型跑（该插件的 persona 就是为本地模型精简的） 0 元

对照 09-13 的 idea-to-print（混元 3D 生成 + 多轮几何门）动辄几十万 token，差一个数量级。

个人怎么切进去

  1. （20 分钟）装 DSH，pnpm exec dsh plugin --profile web add dsh-print3d，重启。
  2. （半天）不装 PrusaSlicer 也能用 6 个里的 5 个 —— print3d_slice 是唯一调外部进程的， 未装会明确报错而不是静默失败。先把 analyze / estimate / render 这条只读链路跑通。
  3. （几十行代码，最容易被合的口子）print3d_stl_analyze 现在给的是 包围盒 / 体积 / 表面积 / 悬垂 / 非流形 / 水密这一档。 加一项「最小特征尺寸 vs 喷嘴直径」检查 —— 这是 DfAM 里最常翻车的一条，现在这个工具查不出来。

坑

  • 绑死 DeepSeek Harness，不是通用 MCP server。想在 Claude Code / Codex 里用， 得自己把 presets/*/scripts/ 下那 5 个脚本重新包一层 —— 作者把它们保留成可独立调用的 CLI（node scripts/xxx.cjs ...），这条路是通的，但要你自己走。
  • 安装文档是 PowerShell + Windows 路径写的；Linux 下路径和「桌面」目录要自己改。
  • gen_parametric_stl 只有 7 种基础体，不是 text-to-CAD。复杂件还是要走 OpenSCAD 技能手写。
  • 输出是 ASCII STL，体积比二进制大好几倍；批量生成注意磁盘。

🌍 国外 · claude-code-robotics —— 给 URDF 装上 check_urdf 这道硬门，并且不让 agent 往运行中的机器人上写

enesbirlik ｜ MIT ｜ v1.1.0 ｜ 09-15 ｜ 带 CI ｜ 37 KB

结构很紧凑：5 个 skill（ros2-workspace / urdf-xacro-builder / embedded-ros-bridge / nav2-moveit2-config / ros2-ecosystem-packages）+ 2 个 hook 脚本 （verify_urdf.sh、colcon_build_check.sh）+ 1 个只读 ROS 2 MCP server（FastMCP，stdio）。

为什么这条是接口段现在最该看的

README 把问题说得很准：通用 LLM 写机器人代码，会编出看起来合理但错的 URDF 惯量张量、 发明不存在的 rclpy QoS 默认值、靠猜参数名去"修" Nav2 costmap。

它的回答是两道硬门：

  • hook 真的去跑 xacro / check_urdf 和限定范围的 colcon build（用你 PATH 上的工具）， 生成的 URDF 一畸形立刻就知道，而不是等到 RViz 里模型飞了才发现。
  • MCP server 能读运行中的 ROS 2 图或 Gazebo 仿真（节点、话题、实时消息）， 但永远不能 publish、不能 set parameter、不能改节点生命周期状态。

skill 内容也不是泛泛的 ROS 2 教程，README 点名写进去的是"会悄悄弄坏机器人的一致性规则"： costmap 坐标系不匹配、URDF 与 MoveIt 之间的关节限位漂移、micro-ROS executor handle 数量。

这条正好接上本期国外第 3 条 Wobble 的坑 —— 一个 agent 辅助写的 URDF，惯量值该不该信。 两条放一起就是一个完整的检查闭环。

  • 它是知识 + 校验脚本，不是代码生成器。 真正写 URDF 的还是模型； 37 KB、2 ★、单次提交后没再动。

📌 专题分析：这一周这条链路上真正变了的东西（4 点）

1. 「大对象落盘、只回路径」从事后优化变成了写进设计文档的一等约束。 dsh-print3d 把它做成默认行为并给了理由（本地小模型的上下文预算）。 前九期的 cadjson、model-forge、cadxray 都是隐含地这么做，没人把它当成约束写出来。 这条链路的成本模型正在从「几何算力」转向「上下文预算」 —— 这是一个方法论上的转折， 不是某个项目的实现细节。

2. 校验的位置在持续往上游移，但门本身的可靠性还没人管。 09-16 的 detect-agent 在打印之后找缺陷；09-17 的 cadxray 在切片之前查可打印性； 这期的 claude-code-robotics 在 agent 写完文件的那一刻就跑 check_urdf。 门越早，返工越便宜。但没人处理「门没生效」这个失败模式 —— claude-code-robotics 的 hook 依赖 PATH 上有 ROS 2 工具，没装就是静默空转， 而 agent 会当作校验通过了继续往下走。一个"门自检"机制（启动时验证每道门确实可执行） 是这条链路上现在完全空白的一块。

3. 接口段（URDF / SRDF / SDF）仍然只有「检查」，没有「生成」。 claude-code-robotics 是检查已有 URDF；国内的 zc110747/RobotForge（0 ★，09-15， 把 CAD/STEP 转成统一 RobotModel + 原生 MJCF + FK/IK，写了 76 节 spec）方向对， 但还在 v0.1、后端是 MockBackend，MuJoCoBackend 排在 Phase 5。 「从一个自己画的零件，自动长出带正确惯量的 URDF」，到今天仍然没有一个能跑通的开源实现。 这是本专题连续第十期记录的同一个空缺。

4. token 成本这一栏，两期之内从「没人写」变成「两条里两条都写了」—— 但仍然没人在运行时打印它。 09-17 我还把「给任意一个 text-to-CAD 项目加一段累计 token 输出」列为第一号缺口。 这期两条：dsh-print3d 把零模型调用做成了架构（几何全是确定性 Node 逻辑）， claude-code-robotics 因为只产文本天然便宜。方向对了。 但依然没有一个项目在运行结束时打印「本次消耗 X token / 约 Y 元」 —— 所有的成本数字（包括我上面写的）都还是估算。那个缺口还在原地。
