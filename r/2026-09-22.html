🇨🇳 国内

1️⃣ 【深度】FBddcz/embodied-jev「行知」—— 把具身决策实验搬进浏览器，零 GPU 零 API Key 就能跑第一轮

是什么。 embodied-jev（中文名「行知」）是一个 MuJoCo + Franka Panda 的 具身决策工作台：本机起一个服务，浏览器里选任务、选模型、点「运行实验」，看着机械臂把方块搬进托盘。 2026-09-20 建仓，两天 162 ★，MIT。

三个任务：搬运入盘 / 方块堆叠 / 越障搬运。抓取靠双侧夹爪真实接触判定，成功与否由独立的物理条件判， 不是模型自己说了算。四种控制模式：

模式 模型看到什么 模型输出什么
预设技能 结构化状态或 RGB-D 检测坐标 + 可用技能表 阶段与技能选择
逐步 XYZ 状态 / RGB-D 坐标，或已启用相机的原始 RGB 一个 XYZ／夹爪短步候选
分层 XYZ 状态、接触事实、近期动作 先出子目标，再分别选 X／Y／Z／夹爪方向
规则基线 同模式的可用观测 由程序选动作，零模型调用

为什么现在值得做。 这条线上大多数「能跑的东西」都卡在装 Isaac Sim、配 CUDA、申请权重。行知把门槛压到了 Python 3.11 + Node 22.12 + 一次 npm run build：默认规则基线，模型调用数 0、花费 0， 先把「观察 → 决策 → 执行 → 反馈」这个闭环在自己电脑上看一遍，再决定要不要接模型。

它对「实验诚实性」的处理值得单独说，这是同类项目最容易糊弄的地方：

  • 未接通的模型不生成模拟成绩，未知费用不会显示成 0 美元；
  • 普通 Chat API 只返回动作选择，界面不会把模型自报的「信心」当成真实概率（只有原生返回候选概率的接口才显示）；
  • 对比实验按仿真时间对齐回放，README 明说「实际耗时保留模型等待，不能拿回放速度当推理速度」；
  • 候选生成、几何计算和安全检查属于控制程序，不计作模型学到的能力。

作者自己放出的一组真实结果也没修饰：官方 Jev 的分层 XYZ 两局搬运均达到终态， 分别 89 / 88 步、178 / 176 次真实请求、约 72 / 80 秒；但两局下放时都失抓， 方块落进托盘后完成撤离，所以「还不能称为稳定精确放置」。这个口径比「成功率 100%」有用得多。

坑与风险。

  • 项目太新。 两天 162 ★，接口一定会变。要么钉 commit，要么做好每周同步的准备。
  • Windows 未经 CI 验证。 README 给了 PowerShell 命令但明说「当前已验证的环境为 macOS 与 Linux CI」。
  • 官方 Jev 是邀请制。 要先到 TypeSafe 官网排 waitlist，拿到邀请才能建 Key。做对照实验不要把它排进关键路径， 用 OpenAI 兼容 / Claude 原生那两个入口即可。
  • 图像输入的边界要看清。 原始图像目前只走支持图像的 Chat / Claude 逐步模式；Jev 只接收文本， 它读的是本地检测器给出的 RGB-D 坐标，不是相机图。跨模型对比时这一条必须写进方法部分，否则不公平。
  • 别拿回放速度当推理速度（作者已经在 README 里提前堵了这个口子，但导出数据时容易忘）。
  • Key 存在系统钥匙串里，系统存储不可用时页面会退化成「仅本次会话」——不会改存明文，这点做得对，但注意别在共享机器上留 Key。

2️⃣ robot-hint/HINT —— 给长程操作装一个「先决定信哪只相机、再锁定意图」的路由器（浙大等，Apache-2.0）

  • 是什么：HINT（arXiv:2609.02653， 项目页）是长程操作的 agentic 框架。核心是一个 pattern router： 它决定该信哪只相机、以及什么时候更新语义；在这些切换点上，task manager + grounder 解析出当前子任务和目标， tracking 在两次更新之间维持住这个承诺。追踪到的意图再通过视觉高亮 + attention prior 注入动作策略 —— 不给基础模型加任何可训练参数。
  • 为什么值得做：长程任务的失败往往不是动作不行，而是「中途把目标搞丢了」。HINT 把这件事拆成可单独替换的模块 （src/perception/ 是 task manager / grounding / tracking，src/intent/ 是高亮与 attention prior）， 每一块都能单独换掉做消融 —— 对个人来说这是难得的可局部动手的结构。
  • 个人怎么切进去：先别碰真机，也先别训 π₀.₅。 仓库有 src/dataset_export/， 能对已有 LeRobot 数据集离线导出高亮视频和 attention map。README 明确建议 「先跑一个 episode 检查高亮效果，再做完整导出」——这是一条零硬件、单卡就能走完的验证路径。 看懂高亮对不对，再决定要不要投训练。
  • 坑：依赖 GroundingDINO + SAM2 + Qwen3-VL + π₀.₅(OpenPI) 四套权重，显存压力主要在这里； 一个 conda env 同时装了 PyTorch 和 JAX，但 README 明说「不要在同一个 Python 进程里加载两个模型」； YAML 里必须填绝对路径，HINT 不展开 $HOME / $CKPT_ROOT。
  • 相关：OpenPI ｜ LeRobot

🌍 国外

1️⃣ 【深度】Pro2004-a11/real2sim-droid —— 一条 DROID 真机 episode 进去，一个带真值标注的 MuJoCo 数字孪生出来，全自动

是什么。 real2sim-droid（MIT，Python 3.12 / MuJoCo 3.13 / PyTorch 2.6） 吃一条 DROID 数据集里的真机 episode（Franka + Robotiq 2F-85，三台标定过的 ZED）， 吐出一个 MuJoCo 场景：同一条轨迹、同样的相机位姿重放一遍，物体位置由 depth + SAM2 自动摆放， 抓取是物理仿真出来的（不是脚本吸附），逐帧输出 mask / 米制深度 / 6-DoF 位姿 / 接触力。 No human in the loop。

为什么现在值得做。 Real2Sim 这件事，绝大多数公开实现要么半自动（人工对齐物体），要么只交一个「看着挺像」的叠加图。 这个仓库的分量全在它把每一句话都量化成了和真实录像对比的数字：

门 IRIS 7dfa2da3+2023-05-11（把记号笔从碗里拿出来） GuptaLab 553d1bd5+2023-05-19（方块叠方块）
FK 门（DROID 末端位姿 vs MuJoCo FK） 1e-5 mm 1e-5 mm
机器人 mask IoU（外部相机 2，中位） 0.92 0.76
物理抓取：持住比例 / 释放误差 100% 的闭合步 · 2.4 cm 100% · 0.8 cm
反事实（物体挪 5 cm、轨迹不变） 持住 0% · 24 cm 持住 2% · 5.9 cm
跨视角物体摆放（ext1 拟合、ext2 重检测） 中位 4.0 cm n/a（方块在 ext2 里太小）

最后那行反事实是整个仓库最该被抄走的设计：它证明了这个数字孪生不是把抓取写死了。 物体挪 5 cm、轨迹照旧 → 抓不住。任何号称「复现了真机」的仿真，都应该被这么问一次。

坑与风险。

  • 只验过两条 episode。 方块叠方块那条的 mask IoU 只有 0.76（vs 0.92），跨视角摆放在那条上直接 n/a （方块在第二个外部相机里太小）—— 小物体是已知短板，别指望它在精细装配类 episode 上同样好。

  • 钉死 cu124 的 PyTorch + MuJoCo 3.13，和你已有的环境大概率冲突，开独立 venv。
  • 反事实那两个数字（持住 0% / 2%）是特性不是 bug：它说明这不是一个通用抓取模拟器， 只是「这一条轨迹在这一个场景下的物理复刻」。别拿它当抓取策略的训练场。

3️⃣ localai-org/gem-x.cpp —— 把 NVIDIA GEM-X 搬成 C++/GGML，摄像头连续进、3D 骨架连续出（Apache-2.0）

  • 是什么：gem-x.cpp 是 NVIDIA GEM-X 的 C++23 + GGML 本地化移植，Vulkan 走 GPU。两种模式：实时摄像头（连续更新的骨架，可叠在相机画面上或看 3D 视图） 和离线视频（上传或录一段，重建动作，导出带动画的 GLB 给 Blender 之类用，限 120 采样帧）。 自带一个浏览器 demo，./demo/gemx-demo --threads 8 开 localhost:8098。
  • 为什么值得做：人形重定向（retargeting）这条链的上游一直缺一个能在自己机器上跑、不走云、不要 Python 全家桶的动捕入口。 GLB 导出直接接得上 Blender / 各家重定向管线。参数里那个「每 N 帧跑一次人体检测」（默认 5，姿态每帧都跑） 是很实在的算力调度旋钮 —— 人在场景里走动时设 1，站着不动时调大。
  • 个人怎么切进去：装 Vulkan 开发包（libvulkan-dev glslc spirv-headers）→ cmake --preset vulkan → 跑 demo 录一段自己的动作导 GLB → 接进你手上的人形重定向脚本。一个下午的事，0 成本。
  • 坑：README 第一句就写了 "Robot control and SONIC integration are not included yet" —— 它现在只出骨架，不出机器人指令，重定向那一段要你自己接。只在 Linux 上测过， 需要 GCC 13+ / Clang 17+、CMake 3.24+、Ninja、Go 1.23+（浏览器 demo 用）。 离线模式还要 sam3d.cpp 子模块的 Body 模型资产，实时摄像头模式不需要。

🧩 专题 · AI Agent × 3D 打印 / 自动建模

本期两条都落在「自动建模 → 可打印性验证」这一段，而且是同一个骨架的两种实现： AI 提议，程序用真实几何否决。 上一期（09-21）碰的是打印机侧的状态流，这期回到建模侧。

🇨🇳 Jkcode8/patent-3d-demo —— 专利交底书 + CAD 图纸 → 参数化 .scad → manifold STL → 附图 → 配音演示视频（MIT）

是什么。 patent-3d-demo 是一个 Agent skill （Codex / Claude Code 等支持 skills 的运行时都能装），把「用三维视频讲清楚一个专利的结构、原理和施工方法」 这件事做成了一条脚本化流水线，六个阶段：

阶段 产出
① 抽取 交底书正文 + 内嵌图、CAD 实体与文字、图纸页 PNG
② 建模 参数化 .scad，固定接口 device(theta, pull, water_z, step, explode, section)；manifold STL；外加一次投影与原图纸的 overlay 核对
③ 分镜 从交底书推出分段计划，你确认之后才开始渲染
④ 附图 彩色渲染、黑白渲染、正交线稿（SVG / DXF / PNG）+ 参数表
⑤ 视频 逐句 TTS → 时间轴 → 字幕 → 片头 → 配乐 ducking → 响度归一化 MP4
⑥ 交付 说明.md：参数出处、假设清单、复现命令

为什么值得做（对具身的人也一样）。 抛开专利场景，这条链干的事是 「二维工程图纸 + 自然语言描述 → 可打印的参数化三维件」，而且它把 「模型建出来的东西和原图纸对不对得上」做成了一道自动门（②阶段的投影 overlay）。 这正是改件、做转接板、复刻别人图纸时最容易翻车、又最没人做自动检查的一步。 device() 那个固定签名（含 explode 爆炸视图和 section 剖面）也意味着同一份模型能直接出装配图和剖视图。

个人怎么切进去。 ① git clone 进 ~/.claude/skills/ 或 ${CODEX_HOME}/skills/； ② 先跑 python scripts/config.py --check —— 它会打印每个依赖的可用性和缺失时的降级路径 （OpenSCAD 必需；ffmpeg 缺了只出 GIF、edge-tts 缺了退 Windows SAPI 语音、AutoCAD 缺了就读 DXF 不读 DWG）； ③ 拿仓库里那个桥墩防撞装置的案例（8 个索连模块 + 滑套 + 浮力箱 + 外膜，38 秒视频样片）跑通一遍； ④ 把你自己手上一张机加件图纸喂进去，只跑到 ② 阶段，看 overlay 核对能不能抓出你故意改错的那个尺寸。

成本（含 API token 费）。 几何计算全在本地 OpenSCAD，渲染和视频这两段 token 费为 0； 花钱的是「读交底书 + 图纸文字 → 写 .scad → 按核对结果返修」这几轮。 一个中等复杂件按 2–4 轮返修估，累计约 150–400k 输入 + 20–40k 输出 token：

模型 输入 $/M 输出 $/M 一个件约
Claude Sonnet 5 3 15 $0.8–1.8（约 ¥6–13）
Claude Opus 5 5 25 $1.3–3.0（约 ¥9–22）

TTS 走 edge-tts 免费。结论：一个件不到 ¥25，链路上真正贵的不是硬件也不是打印，是这几轮返修。 所以 ③ 阶段「分镜要你确认后才渲染」这个设计是省钱的 —— 别让它在你没看的时候渲一遍。

坑。 依赖 OpenSCAD 这一条是硬的；DWG 要 AutoCAD（没有就得先转 DXF）； .scad 的参数化质量完全取决于模型这一轮写得好不好，overlay 核对只能抓住投影对不上的错，抓不住「投影对得上但拓扑错了」的错。 有 regression 和 full-pipeline 两条 CI，说明作者在意可复现性，但 CI 跑的是仓库自带的虚构样例。 → https://github.com/Jkcode8/patent-3d-demo

🌍 Jinyu-Liu-Jinyu-Liu/Prompt2Print —— AI 画字形，程序用 16 道几何门 + PrusaSlicer 切片检查否决它

是什么。 Prompt2Print 把「输入一个名字 → 拿到四个能打印的桌牌设计」 做成了一条有护栏的流水线。口号是 AI proposes. Geometry rules constrain. Humans choose.

关键在于字形是生成的，不是选的：确定性配方（shapely 算子作用在字体轮廓上，或者模型自己画 SVG glyph path） → polygon() → OpenSCAD。而且在进 OpenSCAD 之前，一个 design harness 就用和最终 STL 相同的平面检查 预筛每一个提案，把判定作为工单回灌给模型（有界轮次，每轮记录）。

底座有五种构型，其中两种是站立式：wedge 桌牌（30–90°）和 stand 垂直脚（45–90°）。 对站立件，程序会自己挑一个无支撑的打印姿态、算悬垂、并量导出实体的倾覆余量—— 这是把「打出来站不站得住」变成了一个可计算的量，而不是打完了才发现。

每个产物过 16 道几何门 + 平面特征筛查 + PrusaSlicer 切片检查，状态是 PASS / WARN / FAIL / UNKNOWN / NOT_RUN 五档，README 一句话点题："nothing is ever simulated as a pass"。

个人怎么切进去。 ① macOS 上作者 2026-09-19 验过完整链路；Linux 能跑出 STL 产物（前端 + OpenSCAD CLI 那部分）； ② brew install --cask openscad@snapshot → uv sync --extra dev → cd frontend && npm run build → python scripts/app.py，开 127.0.0.1:8000； ③ 先跑离线确定性预设模式（完全不调模型），把 16 道几何门和倾覆余量算出来看一遍 —— 这一步 token 费 0； ④ 再接模型，对比「AI 设计的字形」和「预设配方」在同样几道门下的通过率差异。 ⑤ 真正值得搬走的不是这个桌牌产品，是 evidence/ 目录那套「每一个候选都留下实测几何 + 判定」的做法 —— 把它套到你自己的参数化件上。

成本（含 API token 费）。 字形设计的上下文比上一条小得多：四个候选 + 有界返修轮次， 约 30–80k 输入 + 10–20k 输出。Sonnet 5 约 $0.2–0.5（¥1.5–4）一个名字；Opus 5 约 $0.4–0.8。 离线确定性预设模式是 $0。 另外它支持用 ChatGPT 登录走 OpenAI 自家的 Codex app server，不一定要 API Key。

坑。

  • 许可未识别：GitHub 的 license API 返回 NOASSERTION，仓库里那份 LICENSE 不是标准模板。 想拿它的代码做别的用途之前，先问作者。
  • 范围很窄：只做 1–8 个 ASCII 字母的名牌浮雕。中文、复杂几何都不在射程内 —— 但那套「预筛 → 工单回灌 → 16 道门 → 切片检查」的骨架是可迁移的。
  • 2026-09-21 建仓，一天，非常新。
  • 可选的 Minecraft 预览器是个 feature flag，跟主链路无关，别被它带偏。

📌 专题分析（这一周这条链上真正变化的东西）

  1. 验证的重心从「建得出来吗」移到了「打出来站不站得住」。 09-13 那一期的 idea-to-print 是 19 项 DfAM 几何门，09-21 的 gridfinity-designer 把「怎么拿得出来」设计进凹槽， 这一期 Prompt2Print 直接算导出实体的倾覆余量、挑无支撑打印姿态、算悬垂。 门的数量在涨（19 → 16 + 平面筛查 + 切片检查），但更重要的是门的性质变了： 从「网格合不合法」变成了「这个物理对象在重力下的行为」。这是几何检查在往物理检查靠。

  2. 「工单回灌」正在成为这条链的标准骨架。 两个项目、两个国家、两种 CAD 后端（OpenSCAD 参数化 vs OpenSCAD + CAD 图纸）， 但结构一模一样：模型提议 → 程序用真实几何测量 → 不过就把测量结果（不是「你错了」，是具体数字）当工单退回去 → 有界轮次。 这比「让模型自己检查自己」靠谱得多，也是 token 费真正花在哪的答案 —— 钱花在返修轮次上，不是花在第一次生成上。 两个项目都显式限制了轮次上限，这不是小事。

  3. 成本结构已经稳定了，而且比想象中低。 连续几期量下来： 纯参数化 code-CAD 链，一个件 ¥2–25；mesh 生成链（混元 3D 那类）另算 API 生成费。 硬件（打印机、耗材）反而是一次性的。这条链现在的瓶颈不是钱，是「程序能不能测出这个件的问题」 —— 所以值得投入的方向是往门里加测量，不是往提示词里加要求。

  4. 今天这两条都还没碰「和具身智能的接口」那一段（URDF / SRDF 自动生成、改件→打印→上机的闭环）。 上一次碰是 09-20 的 text-to-cad（同源产出 STEP/DXF/STL/3MF 和 URDF/SRDF）。 这一格连续两期空着，下期优先补。

🇨🇳 yuexinyang526-coder/TacBench-Lite —— 一台笔记本上跑完的视触觉闭环基准，用「冻结触觉」证明了策略要的是动态反馈

是什么。 TacBench-Lite 是一条 纯 CPU 的「仿真环境 → 多模态数据 → 多模态模型 → 闭环评测」最小闭环： MuJoCo 物理 + 自研的轻量视触觉渲染器（射线几何穿透 + 力致弹性体压缩 + 三色 LED 光度立体 + 标记点阵）、 3 自由度笛卡尔龙门 + 40 mm 方形视触觉垫、四个接触密集型任务、658k 参数的 TacLite 策略。 代码 MIT，数据集 CC-BY-4.0（344 MB / 800 episode），50 个 checkpoint 走 Release 附件。

作者的硬件现实写在 README 里：RTX 3050 Laptop（4 GB）+ 16 GB 内存 + i5-11400H， Isaac Sim 系（含 TacEx、Tabero 官方栈）跑不动，所以选了纯 CPU MuJoCo 并自己写渲染器。

可量化的口子。 动作是 [dx, dy, dz, f_des]，由底层混合力/位置控制器以 50 Hz 执行， 单步 8.3 ms；渲染器自检：16 mm 方孔平移 0/3/6/10/14 mm 下，孔心恢复误差 ≤ 0.6 mm 且单调； 力 → 形变 0.57→10.8 N 对应 0.14→2.71 mm；剪切 → 标记位移 0→1.04 N 对应 0.22→0.37 mm。 评测 = 每任务 30 episode × 4 任务 = 150 episode/格，每个 seed 重新采一整套数据（5 个独立数据集）， 配对精确 McNemar + Holm–Bonferroni 校正。

为什么值得做（这才是这条专题要的东西）。 6.2 节那张传感器失效表是整个仓库的重点：

条件 press align_hole slide_ridge
正常 85.3% 56.7% 46.0%
触觉置零 57.3% 0.0% 36.7%
触觉冻结（冻在首次接触帧） 75.3% 0.0% 36.7%
触觉加噪（σ=25/255） 72.0% 40.7% 48.0%
替换语言指令 8.0% 28.7% 38.0%

「触觉冻结」和「触觉置零」一样把 align_hole 打到 0%。 也就是说：给策略一个恒定的、正确的触觉画面（它确实在接触），和干脆不给，结果完全一样。 策略要的不是「有没有接触」这一个 bit，是这一路信号在持续变化。 这是我在这个专题里见过最干净的一次「连续流不可替代」的证据 —— 而且它跑在纯 CPU 上。 （口径也写得很严：冻结发生在法向力首次 > 0.3 N 的那一帧，此前照常送实时帧；早期版本在 episode 第一帧就冻结， 那时垫子还没接触，该口径已废弃。这种自我纠正在个人项目里很少见。）

另外两条同样有迁移价值：去触觉后 align_hole 56.7% → 1.3%（校正后 p = 5.6e-24，两路视觉撑不起 1.5 mm 容差）； 粗触觉编码（6×6 token）下 align_hole 只剩 2.7% —— 表征的空间分辨率必须和任务容差同量级。

个人怎么切进去。 ① pip install -r requirements.txt（174 个包，含 torch 2.5.1+cpu 和 mujoco 3.13）； ② 约 1 分钟的最小验证：python -m sim.validate_tactile（渲染器自检）+ python -m sim.eval_expert （脚本专家上界 100/100/96/100%）；③ 从 Release 拉 344 MB 数据 + 127 MB 权重，python -m model.degrade 复现那张失效表；④ 交付：把「冻结 vs 置零 vs 加噪」这套协议搬到你自己的传感器模态上 （力矩、事件相机、关节编码器都行）—— 这是一套可以直接复用的「这一路信号到底是不是必须连续」的测法。

坑（作者自己列的负面结果，非常硬）。 6.3 节：渲染器对真实 GelSight Mini 的外部效度是负面的。 100/100 帧-几何精确配对下，本渲染器 vs 真实 NCC = +0.27，而「真实 vs 另一个数字的渲染」这个随机下限是 +0.29 —— 匹配值不高于随机下限。渲染器给出正确的接触轮廓，但不携带可区分数字的内部结构。 光度域差距：亮度 ×0.51，逐通道对比度比约 [1.2, 3.5, 1.6]（真实传感器绿通道几乎是平的，std 9.1； 渲染器三通道都放了几乎相同的结构，std ≈ 33）。所以：这是一个做消融和协议设计的台子，不是一个 sim-to-real 的台子。 另外一键脚本是 PowerShell（run_all.ps1 / ablation.ps1），Linux 上要自己拆成 shell。 还有一条诚实得少见：分类迁移实验（纯渲染训练 → 真实测试）作者故意不报数字， 因为两个域的触点分布差一个量级，渲染训练 13.3% 与真实训练 1.7% 都落在噪声带内，此时报数字是误导。

🌍 Vigilant-CRS/Inference-Governor-QoS —— 不是算得更快，是不算已经过期的那一帧

是什么。 Inference-Governor-QoS 是一个 Rust 写的 推理 QoS 调度器，坐在 NVIDIA Triton（或 TF Lite）前面，在请求到达 GPU 之前做六个决定：

决定 为什么重要
🗑️ 丢掉已被取代的工作 —— 同一路相机来了新帧就替掉还在排队的旧帧 旧帧的结果机器人反正会扔掉，算它等于抢新帧的 GPU 时间
⏱️ 拒绝一定会迟到的工作 —— 算完就已经过期的，干脆不启动 迟到的答案不是「慢」，是「错」
🛡️ 压住后台长任务 —— 受保护的流马上要来，长任务就不开工 这是唯一一处它故意让 GPU 空着，也正是相机保持新鲜的原因
🎚️ 切到还塞得下的小模型变体 —— 压力下宁可精度略低但准时
✂️ 把长任务切块续跑 —— 声明 cooperative: 的生成式模型按实际空出的时间切片，块与块之间让出槽位，状态走 prompt 传递 内部实测：不可守承诺的拒绝 221 → 0，受保护相机 795 → 891 / 910 帧，总算力不变
🎯 兑现一个能写下来的承诺 —— contract 可带 objective:，同时约定占比和最长容忍间隔 「98% 新鲜，且绝不出现整整一秒空白」这种话运维能讲、调度器能查

它说的是 Open Inference Protocol（和 Triton 同一个 gRPC 接口），客户端只改一个东西：连接地址。

可量化的口子（作者自己给的口径很克制，值得抄）。 RTX 3070 Laptop (8 GB)、Triton 2.70、真实模型（RF-DETR @ 512 px、ResNet pose、depth，外加一个 95 ms 不可中断块）， 对手是调过的 Triton（同模型、同 instance group、同共享内存数据通路、开了带优先级的 rate limiter）：

流 Triton（调过） Vigilant 未覆盖周期
detector (RF-DETR) 84–85% 99% 少 20–22×
pose 91% 99% 少 10–12×
depth 97–98% 90–100% 无增益 —— 作者明说「不算作胜利」

六轮、两个驱动版本各三轮。对上 Triton 的最强配置（全局受限共享资源）时 detector 是 12.9–15.1×， 作者给区间不给最好看的那个数，并注明那次比较是 09-10 的 gap 计账修正之前测的、之后没重跑。 还有诚实的另一半：同一轮里后台语言模型覆盖率是 0% —— 95 ms 不可中断块塞不进 33 ms 周期，有没有调度器都塞不进， 区别只是「调度器决定了谁输，并且说出来」。开了 cooperative 切块后：detector 98% → 91%，语言模型 2 代 → 40 代。

换算到本机。 它测的是 3070 Laptop（8 GB）。A4000 算力更高但基线已被别的进程占 ~4.4G， 而这个工具要解决的恰恰就是「多个东西抢一张卡」—— 本机就是它的目标场景。 延迟数字按 ×1.5～2 折算到 A4000 的多任务负载上看即可（它不是模型推理，是调度开销，绝对值很小）。

为什么这条值得单独列。 前三期这个专题写的全是「让一次前向更快」（Triton kernel、CUDA graph、投机解码、流式解码）。 这条是正交的另一个维度：一帧 33 ms 进来一次，检测器要 15 ms，本来塞得下 —— 直到一个语言模型在同一张卡上开了个 95 ms 的活。 更快的 GPU 只会更快地算过期的帧。 这句话（"A faster GPU computes stale frames faster"）是整个仓库的论点， 也是「流式感知 → 连续决策」里一直被忽略的一环：连续性不只是模型的事，是排队的事。

个人怎么切进去。 ① 先不装，读 README 里那张 ASCII 时序图（F1..F5 四帧被 95 ms 块挤掉的过程），三分钟就懂了； ② vig autotune --endpoint 127.0.0.1:8001 -c vig.yaml -o qualification —— 它会在你的机器上量你的模型、 拿你的 contract 试配置、只保留背靠背重跑还站得住的那些，并且在你的负载根本不需要调度器时直说； ③ 交付：在本机（A4000 + 那 4.4G 的占用）上跑一遍 autotune，把「一个 VLA 推理 + 一路相机检测」 这种真实具身负载下的覆盖率数字发出来 —— 作者测的是通用感知负载，具身场景的数据点是空的。
